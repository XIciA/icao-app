# 产品更新与发布流程

状态：长期规则；用户于 2026-10-21 明确要求建立。
适用范围：用户通过聊天要求实施的产品功能更新、新需求和 Bug 修复。当前用户的具体要求优先。

## 总体路径

```text
用户提出更新 / 需求 / Bug，并要求实施
→ 完成实现和必要检查，合入 main
→ iOS 上传 TestFlight；Android 交付官网测试版；受影响的产品 Web 直接上线
→ 用户测试，继续修复并更新测试版本
→ 用户明确确认正式上线
→ 发布当前最新候选：提交 Apple 审核，更新 Android 正式下载
→ 各平台正式版本实际可用后更新正式渠道清单，旧版用户获得更新提示
```

用户只讨论想法、要求排查或编写方案时，按该范围工作，不自行启动实现或发布。
普通改动不因本流程增加需求文档、逐步审批或多套中间验收环境。

## 默认测试交付

用户要求实施产品更新或修复，即按本流程完成受影响平台的测试交付，不必再次询问是否上传测试版本。
只涉及单个平台的改动不自动构建其他平台。

| 平台 | 默认交付目标 | 边界 |
| --- | --- | --- |
| iOS | 构建并上传 TestFlight，确认 Apple 处理完成及目标测试组可访问 | 不提交 App Store 审核，不发布 App Store 正式版 |
| Android | 构建独立测试 APK，更新 `android-test` 渠道，并在 `readyoufife.com/download` 提供测试版下载入口 | 不替换正式 APK、正式下载主按钮或 `android-apk` 渠道 |
| 产品 Web | 受影响的 `readyoufife.com` 页面通过必要检查后直接部署 EdgeOne | 是用户明确指定的直接上线例外，不等待移动端正式上线确认；不包括宣传站或其他独立站点 |

Android 测试入口置于下载页右上角、左上角等次要位置，清楚标注“测试版”，与正式版下载分开。
具体位置遵守[UI 风格规范](ui-style-guide.md)，不要求用户每次重新选择。
测试包复用已有独立包名和渠道实现，保留正式安装包与正式更新入口，不让正式版用户误装测试版。
测试入口指向已上传、可下载且校验通过的最新测试包；不能只放一个占位链接。

iOS 和 Android 测试渠道可以提示对应测试用户更新；正式渠道不能因为测试包上传或版本号变化而提示升级。
产品 Web 已上线不等于移动端已获正式发布授权。

## 正式上线确认

在用户明确表示“正式上线”“发布正式版”等同意本轮正式发布的指令前，
不得提交 Apple 正式审核、替换 Android 正式下载或把新候选写入正式更新渠道。
“修好了”“上传测试版”“先给我测试”等指令不代表正式上线确认。

用户确认正式上线后，发布本轮当前最新、已完成必要验证并可追溯的候选；
先核对各平台候选的源码、版本、构建号和测试结果，不沿用较早任务记录中的旧候选。
若最新候选仍有未完成修复或检查失败，先解决并验证；不能因“最新”跳过检查。
正式发布准备所需的构建或渠道配置调整仍走现有主干流程，不夹带未验证的功能改动。

| 平台 | 正式发布动作 | 正式更新提示生效条件 |
| --- | --- | --- |
| iOS | 提交本轮最新候选到 App Store 审核，按本轮授权完成审核后的发布 | Apple 审核通过且新版实际可下载后，才更新 `ios-app-store` 正式清单；待审、审核通过但尚未可用时均不提前提示 |
| Android | 生成或使用对应正式包名、正式签名的已验证 APK，发布并切换官网正式下载 | 公开 APK 可下载、身份 / 签名 / 摘要及升级条件验证通过后，更新 `android-apk` 正式清单 |

不能直接把独立 Android 测试包当作正式包覆盖发布。发布保留账号、学习数据和既有权益，
不把测试渠道清单改名为正式渠道来替代正确的正式制品。
两端按各自实际可用时间更新正式清单，不因 Android 已发布就提前宣称 iOS 已上架。
旧正式版通过既有更新检测机制获得提示：iOS 前往 App Store，Android 下载正式 APK 并由系统确认安装。
更新检查频率、忽略版本等既有行为保持不变，不承诺清单切换后所有设备立即弹窗。

## App Store 更新说明

提交 Apple App Store 时，面向用户的“此版本的新增内容 / 更新说明”默认只填写：

> 修复了已知问题。

不逐项列出具体 Bug 修复、新增功能或其他更新细节；只有用户明确另行指定文案时才调整。
内部发布记录仍保留实际改动与验证证据，不用这句简短说明替代发布追溯。

## 与既有规则的关系

- 本规则明确授权上述产品更新任务中的 TestFlight、Android 官网测试渠道交付，以及受影响的
  EdgeOne 产品 Web 上线；不需要重复取得相同授权。当前用户缩小范围或要求暂停时，以当前要求为准。
- 后端生产部署、数据库迁移、批量业务数据 / 内容发布仍按[项目长期边界](project-boundaries.md)
  核对明确授权，不能由“Web 直接上线”推导。若测试交付依赖这些操作且未获授权，说明具体依赖，不伪报交付完成。
- 旧 Vercel 端已退役，其冻结约束已撤销；宣传站、后台等独立站点不因本规则自动获得改动或部署授权。
- 源码合并、干净主干构建、版本 / 标签与发布追溯遵守[仓库管理规则](repository-and-github-management.md)；
  检查与目标包验收遵守[交付与验收规则](delivery-and-acceptance.md)，本规则不增加固定验收阶梯。
- 交付后更新已有发布记录与[项目管理概览](../resources/project/product-state.md)，分别写明
  检查通过、测试渠道可用、用户验收、正式审核和正式可下载的实际状态，不新建平行进度台账。

本文规定后续工作流程，不代表下载页测试入口或所有渠道已按新流程完成实现；具体任务仍需核对当前代码与线上证据。
