# 产品更新与发布流程

状态：长期规则；用户于 2026-10-21 明确要求建立。
2026-11-02 用户更新：正常开发默认优先交付 TestFlight；Android 明确要求后再对齐与交付。
适用范围：用户通过聊天要求实施的产品功能更新、新需求和 Bug 修复。当前用户的具体要求优先。

## 总体路径

```text
用户提出更新 / 需求 / Bug，并要求实施
→ 完成实现和必要检查，合入 main
→ 默认优先交付 iOS TestFlight；受影响的产品 Web 按既有范围直接上线
→ 用户测试，继续修复并更新测试版本
→ 如用户明确要求 Android，以当前苹果端为基准完成对齐并交付官网测试版
→ 用户明确确认相应平台正式上线
→ 发布获授权平台的当前最新候选：提交 Apple 审核或更新 Android 正式下载
→ 各平台正式版本实际可用后更新正式渠道清单，旧版用户获得更新提示
```

用户只讨论想法、要求排查或编写方案时，按该范围工作，不自行启动实现或发布。
普通改动不因本流程增加需求文档、逐步审批或多套中间验收环境。

## 默认测试交付

正常开发中，用户要求实施产品更新或修复且没有特别指定平台时，默认优先完成 iOS TestFlight
交付，不必再次询问是否上传。Android 不作为默认并行构建或交付任务，也不得成为 TestFlight 的等待前置。
只涉及单个平台的改动不自动构建其他平台；用户明确指定平台或交付顺序时，以当前指令为准。

只有用户明确要求 Android 开发、对齐或交付后，才启动 Android 对齐与测试交付，具体标准见下节。

| 平台 | 默认交付目标 | 边界 |
| --- | --- | --- |
| iOS | 构建并上传 TestFlight，确认 Apple 处理完成及目标测试组可访问 | 不提交 App Store 审核，不发布 App Store 正式版 |
| Android（用户明确要求后） | 对齐当前苹果端后构建独立测试 APK，更新 `android-test` 渠道，并在 `readyoufife.com/download` 提供测试版下载入口 | 不默认启动；不替换正式 APK、正式下载主按钮或 `android-apk` 渠道 |
| 产品 Web | 受影响的 `readyoufife.com` 页面通过必要检查后直接部署 EdgeOne | 是用户明确指定的直接上线例外，不等待移动端正式上线确认；不包括宣传站或其他独立站点 |

Android 测试入口置于下载页右上角、左上角等次要位置，清楚标注“测试版”，与正式版下载分开。
具体位置遵守[UI 风格规范](ui-style-guide.md)，不要求用户每次重新选择。
测试包复用已有独立包名和渠道实现，保留正式安装包与正式更新入口，不让正式版用户误装测试版。
测试入口指向已上传、可下载且校验通过的最新测试包；不能只放一个占位链接。

iOS 和 Android 测试渠道可以提示对应测试用户更新；正式渠道不能因为测试包上传或版本号变化而提示升级。
产品 Web 已上线不等于移动端已获正式发布授权。

## TestFlight 版本号与构建号

本节由用户于 2026-11-02 明确要求。区分面向用户的版本号（如 `1.3.1`）和 TestFlight 的
七位构建号（如 `3596166`）；同一个版本号可以反复交付多个测试构建。

- **同一轮默认保持版本号。** 本轮 TestFlight 后续修复、功能调整和重复上传均沿用已确定的
  版本号，只递增 iOS 七位构建号。不得因为完成一次任务、合并一次 PR、改动较大或上传新包，
  就自行把 `1.3.1` 改成 `1.3.2`，也不得让 App 内展示版本与本轮安装包版本无故分叉。
- **新构建号保持递增。** 每次上传前核对 App Store Connect 已使用的构建号及仓库配置，选取
  更大的七位数，不复用旧号；只准备本次 iOS 构建所需的版本配置，不顺带调整 Android 或其他
  渠道。构建号仍须按仓库规则提交并合入 main 后构建，不能在发布过程中临时改源码。
- **审核通过后，下一轮才更新版本号。** 默认等待本轮版本已经提交 App Store 正式审核并确认
  审核通过，下一轮产品更新才进入新的版本号。TestFlight 上传成功、Apple 构建处理完成、
  测试组可用、用户测试通过，以及正式审核待审、被拒或撤回，都不能代替这个条件；其他旧版本
  的历史审核通过也不能作为提前提升本轮版本的理由。用户明确指定版本号时按其指令执行。
- **不确定才询问，不逐包重复确认。** 先核对当前任务已确认版本、现有发布记录和必要的平台
  状态；仍无法判断当前属于哪一轮或应采用哪个新版本号时，只向用户确认“这一轮 TestFlight
  使用哪个版本号？”。一旦确定，同一轮后续构建直接沿用，不反复询问，也不自行猜测加号。
- **本轮约定：** 当前版本保持 `1.3.1`；后续测试构建在已上传 `3596166` 的基础上按实际最新
  构建号递增，例如 `1.3.1（3596167）`、`1.3.1（3596168）`。这些是示例，不是预先占用的号。

本规则控制测试版本迭代，不授权提交 App Store 审核、正式发布或提前更新正式渠道清单。

## Android 开发与苹果端完全对齐

本节由用户于 2026-11-02 明确要求。Android 必须从代码、功能、业务逻辑和实际使用体验四个层面
完全看齐当前苹果端，只保留原生系统限制导致无法消除的必要差异。“基本一致”“功能大致都有”
或“能成功打包”均不构成完成对齐。

1. **确定同一个基准。** 默认使用本轮当前最新已交付的 iOS 候选及其源码；用户指定版本时使用
   指定版本。在已有任务或发布记录中写明 iOS 版本、build 和 commit。对齐期间苹果端发生相关
   变更时同步核对，交付前再次确认，不沿用过期页面或旧业务行为。发现苹果端缺陷时修复共享
   根因、同步两端并记录，不复制已知缺陷，也不擅自让安卓形成另一套产品行为。
2. **代码层面共用实现。** 同一功能复用同一套业务逻辑、状态管理、数据合同、权限判断和公共
   组件；不得为了赶进度复制出安卓业务分支或维护两套状态负责人。检查 `.ios` / `.android`
   平台文件、`Platform.OS` 判断、原生模块和配置差异，清理没有系统必要性的分叉。确需调用
   不同系统 API 的实现收敛在最小平台适配层，对上提供相同的业务合同和状态语义。
3. **功能与业务规则完全一致。** 入口、功能范围、登录与会员权益、离线访问和播放、下载任务、
   学习与进度保存、数据同步、失败恢复等，必须遵循同一规则。相同账号、内容和操作前提应得到
   相同业务结果；不能出现某功能只有苹果可用、安卓少一步校验、不同到期规则或不同数据处理。
4. **页面和操作体验完全看齐。** 对照苹果端检查页面结构、信息层级、控件位置与状态、提示文案、
   加载/空态/错误态、按钮反馈、进入与返回、弹层、滚动位置、进度保留和切换连贯性。不得因
   安卓实现方便而增加中间页面、额外步骤、不同提示或闪烁跳动；整体流畅度和交互完整性也须
   对齐，不能只比较静态截图或功能清单。
5. **系统差异仅限不可避免部分。** 只允许原生系统能力、强制要求或限制导致的必要差异，例如
   系统返回手势、系统权限弹窗、系统支付能力、安装更新和后台执行限制；这些只是可能的差异
   来源，不是整类功能的豁免。逐项说明具体限制、受影响行为以及适配办法，将差异限定在最小
   范围，应用自己的业务规则和系统操作前后体验仍须对齐。框架默认、历史代码或实现成本不是
   保留差异的理由。
6. **从代码和实际体验两侧验证。** 对共享规则与平台分支做代码检查及风险匹配测试；在最终
   Android 候选中对照同样的用户操作验证正常流程、返回/中断、无网/恢复、失败重试等相关场景。
   不用编译成功或单元测试代替体验检查，也不把模拟器结果写成真机通过。暂无法验证的设备体验
   明确交给最终用户验收，不能伪报完成。
7. **交付说明可核对。** 在已有任务或发布记录中列明对齐基准、检查范围、已消除的差异、仍保留
   的必要系统差异及原因、验证证据与待用户验收项。存在未解决且非系统必要的差异时继续修复，
   不宣称已完成对齐；先交付测试候选的，应明确候选状态。默认仍为独立 Android 测试包与
   `android-test` 渠道，正式安卓发布需要单独的明确授权。

## 正式上线确认

在用户明确表示“正式上线”“发布正式版”等同意本轮正式发布的指令前，
不得提交 Apple 正式审核、替换 Android 正式下载或把新候选写入正式更新渠道。
“修好了”“上传测试版”“先给我测试”等指令不代表正式上线确认。

用户确认正式上线后，发布本轮当前最新、已完成必要验证并可追溯的候选；
先核对各平台候选的源码、版本、构建号和测试结果，不沿用较早任务记录中的旧候选。
若最新候选仍有未完成修复或检查失败，先解决并验证；不能因“最新”跳过检查。
正式发布准备所需的构建或渠道配置调整仍走现有主干流程，不夹带未验证的功能改动。

| 平台 | 正式发布动作 | 正式更新提示生效条件 |
| --- | --- | --- |
| iOS | 提交本轮最新候选到 App Store 审核，按本轮授权完成审核后的发布 | Apple 审核通过且新版实际可下载后，才更新 `ios-app-store` 正式清单；待审、审核通过但尚未可用时均不提前提示 |
| Android | 生成或使用对应正式包名、正式签名的已验证 APK，发布并切换官网正式下载 | 公开 APK 可下载、身份 / 签名 / 摘要及升级条件验证通过后，更新 `android-apk` 正式清单 |

不能直接把独立 Android 测试包当作正式包覆盖发布。发布保留账号、学习数据和既有权益，
不把测试渠道清单改名为正式渠道来替代正确的正式制品。
两端按各自实际可用时间更新正式清单，不因 Android 已发布就提前宣称 iOS 已上架。
旧正式版通过既有更新检测机制获得提示：iOS 前往 App Store，Android 下载正式 APK 并由系统确认安装。
更新检查频率、忽略版本等既有行为保持不变，不承诺清单切换后所有设备立即弹窗。

## App Store 更新说明

提交 Apple App Store 时，面向用户的“此版本的新增内容 / 更新说明”默认只填写：

> 修复了已知问题。

不逐项列出具体 Bug 修复、新增功能或其他更新细节；只有用户明确另行指定文案时才调整。
内部发布记录仍保留实际改动与验证证据，不用这句简短说明替代发布追溯。

## 与既有规则的关系

- 本规则明确授权上述产品更新任务中的 TestFlight 和受影响的 EdgeOne 产品 Web 上线；Android
  对齐与官网测试渠道交付须有用户明确指令，取得后不重复确认。当前用户缩小范围或要求暂停时，以当前要求为准。
- 后端生产部署、数据库迁移、批量业务数据 / 内容发布仍按[项目长期边界](project-boundaries.md)
  核对明确授权，不能由“Web 直接上线”推导。若测试交付依赖这些操作且未获授权，说明具体依赖，不伪报交付完成。
- 旧 Vercel 端已退役，其冻结约束已撤销；宣传站、后台等独立站点不因本规则自动获得改动或部署授权。
- 源码合并、干净主干构建、版本 / 标签与发布追溯遵守[仓库管理规则](repository-and-github-management.md)；
  检查与目标包验收遵守[交付与验收规则](delivery-and-acceptance.md)，本规则不增加固定验收阶梯。
- 交付后更新已有发布记录与[项目管理概览](../resources/project/product-state.md)，分别写明
  检查通过、测试渠道可用、用户验收、正式审核和正式可下载的实际状态，不新建平行进度台账。

本文规定后续工作流程，不代表下载页测试入口或所有渠道已按新流程完成实现；具体任务仍需核对当前代码与线上证据。
