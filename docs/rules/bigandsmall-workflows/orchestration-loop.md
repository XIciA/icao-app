# 通用小流程：路线图驱动的自动执行循环

## 极简速览

```text
读取大流程文档
-> 定位当前阶段
-> 选择最小可验证闭环
-> 执行
-> 只读审查 diff
-> 运行验证
-> 失败则在当前边界内自主诊断、修复并重新验证
-> 写必要阶段记录
-> 满足标准则自动进入下一阶段
-> 触碰硬约束或重大风险则回到大流程
```

一句话：**小流程是 Codex 执行官，不是重新讨论需求或方案。**

## 适用前提

进入小流程前，应已有或等价具备：

- `requirements.md`：目标、边界、明确不做、验收标准。
- `technical-plan.md`：技术路线、关键模块、选择理由。
- `roadmap.md`：阶段顺序、阶段目标、核心产出、进入下一阶段标准。
- `technical-audit.md`：复杂任务需要真实项目现状、缺口和风险。

路线图必须由人确认后才能进入小流程。文档缺失或明显不完整时，先回到大流程补齐。

## 核心原则

1. 不改变已确认的需求结果、范围、禁止事项和宏观技术方向。
2. 在不触碰硬约束的前提下，Codex 可以根据真实工程状态、兼容性和验证结果调整实现细节与阶段内部执行顺序。
3. 已确认路线图是小流程的执行授权；路线图已明确允许的范围内操作，不重复请求人工确认。
4. 默认自动推进，不反复请求人工确认。
5. 只有触碰硬约束或出现重大风险时才回到大流程。
6. 每阶段必须可验证、可审查、可收口。
7. 保证效果和节约成本同等重要。
8. 不为形式感创建不必要的 agent、文档或报告。

## 三层约束与实现自主权

小流程按以下三个层级判断哪些内容必须保持，哪些内容可以由 Codex 自主调整：

### 第一层：硬约束

不得由小流程自行改变：

- 用户已确认的需求、最终效果、范围和明确不做。
- 项目总战略、宏观架构和职责边界。
- 路线图的阶段目标、核心产出和进入下一阶段标准。
- 数据安全、权限、隐私、付费、生产环境和不可逆操作边界。

需要改变第一层内容时，必须暂停并回到大流程。

### 第二层：方案默认

技术方案中的推荐框架、模块方向、实现路径和关键取舍是默认执行依据，但不是对实现细节的绝对锁定。

如果真实工程状态、依赖兼容性、构建测试或最终效果证明默认实现不合适，Codex 可以在不改变第一层硬约束的前提下调整，并在阶段记录中简要说明原因、收益和影响。

### 第三层：实现细节

具体库和稳定版本、目录和文件拆分、组件组织、数据结构细节、算法、测试工具以及阶段内部切片顺序，默认由 Codex 自主决定。

判断标准是：更容易稳定实现、验证、维护，并达到已确认的最终效果。无需为了第三层调整重复请求人工确认。

## 路线图授权继承

用户确认路线图后，视为已经授权执行路线图中明确包含的、当前任务范围内的正常操作。

- 已写入路线图的文件修改、普通依赖安装、数据处理、环境配置、验证、Git操作或外部动作，不重复询问。
- 如果路线图已经明确了删除、迁移、提交、推送、部署或发布的对象、范围与环境，可按路线图执行；不得自行扩大到未授权对象或生产范围。
- 路线图没有覆盖的可逆、低风险实现细节，由 Codex 按第三层自主权处理。
- 只有超出路线图授权、触碰硬约束或引入重大风险时，才暂停请求用户决策。

## Agent 使用与成本控制

主线程负责阶段定位、范围控制、结果整合、验证和最终判断。是否使用子 agent，由主线程根据任务规模、并行收益、风险和验证成本自主决定。

适合使用子 agent 的典型条件：

- 子任务能并行推进。
- 边界清楚，输入、输出和文件范围明确。
- 写入范围不冲突。
- 主线程能快速复查、验证和整合。
- 能明显节约时间、降低风险或提高质量。

可选角色示例：

- 主线程：执行官，负责阶段定位、范围控制、整合、验证和最终判断。
- explorer：只读查入口、数据结构、调用链。
- worker：按明确范围实现脚本、组件或数据切片。
- reviewer：只读审查高风险 diff。

这些角色只是示例，不要求固定编组。主线程可以根据任务实际情况调整角色、数量和分工，也可以完全不使用子 agent。

成本规则：

- 不让多个 agent 重读完整文档组。
- 只给子 agent 当前阶段必要摘要、目标、禁止范围和相关路径。
- 子 agent 输出保持短，只写结论、改动文件、风险和验证结果。
- 子 agent 不做最终决策；是否触碰硬约束或形成重大风险，由主线程判断并决定是否回到大流程。

## 阶段启动

每个阶段开始前，主线程读取：

- 需求文档。
- 技术方案。
- 路线图当前阶段。
- 与当前阶段相关的技术盘点。
- 项目级指令，例如 `AGENTS.md`。

阶段启动时明确：

- 当前阶段目标。
- 允许修改范围。
- 禁止范围。
- 验收标准。
- 验证命令。
- 是否需要子 agent。

如果路线图已写清楚，不再请求人工确认。

## 阶段规划

规划输出应短而硬：

```text
当前阶段：
阶段目标：
相关文件：
最小可验证闭环：
风险点：
验证方式：
禁止提前做：
```

规划只服务执行，不重新做方案。

## 阶段执行

执行要求：

- 每次完成能够独立运行、审查和验证的最小闭环；允许为了闭环同时修改多个相关文件，不为了形式把工作拆成无法运行的碎片。
- 只做当前阶段必需内容。
- 先保留旧行为，再切换入口。
- 复用现有结构和工具。
- 批量和重复操作优先脚本化。
- 数据修改必须有校验和回滚意识。
- 代码修改必须遵守项目既有架构和命名。
- 不提交、不推送、不部署，除非路线图或用户明确要求。

大批量模型、外部 API 或子 agent 输出：

- 必须分批处理。
- 必须缓存或保留可恢复中间结果。
- 约每 200-300 条做结构、规则和样本抽查。
- 发现系统性问题时暂停合并，重跑受影响批次。
- 不把未校验的模型输出直接写入正式数据。

数据删除、合并、迁移或覆盖：

- 路线图或用户已明确确认对象、范围和回滚方式时，不重复询问；否则必须暂停确认。
- 执行时优先脚本化。
- 必须同步更新数量、manifest、索引或引用。
- 必须保留处理报告或可审查清单。

## 自主诊断与修复循环

执行或验证失败时，Codex 默认继续完成以下循环：

```text
读取错误和现场状态
-> 定位根因
-> 在当前阶段与硬约束内修复
-> 重新运行相关验证
-> 检查是否引入回归
-> 通过后继续执行
```

普通类型错误、构建错误、测试失败、兼容性问题、UI偏差和资源引用错误，不应直接返回用户处理。

只有同一根因持续出现、修复需要改变硬约束、明显扩大阶段范围，或引入重大风险时，才暂停回到大流程。

## 阶段审查

审查关注问题，不写长篇背景：

```text
结论：通过 / 带条件通过 / 阻塞
问题：
越界风险：
遗漏验证：
是否可以进入下一阶段：
```

主线程默认承担审查；高风险或可并行时可用只读 reviewer。

## 阶段验证

验证由项目、路线图和最终验收环境决定，并遵守
[`交付与验收最简规则`](../problem-solving-and-maintenance/delivery-and-acceptance.md)。不得默认把模拟器、
Development Build、Dev 真机和 Release/TestFlight 串成固定阶梯；先做与改动直接相关的快速检查，
再进入用户指定的最终验收环境。

常见验证：

| 类型 | 验证 |
| --- | --- |
| TypeScript / React / Next.js | 类型检查、构建、关键路由或显示抽查 |
| Python | 语法检查、样例输入输出、单元测试 |
| 数据处理 | JSON/schema/数量/引用一致性、抽样检查 |
| 文档 / PDF / PPT / Excel | 渲染检查、格式检查、内容抽样 |
| 部署 | 构建日志、部署状态、线上 URL 验证 |

涉及前台显示时，不能只看字段和类型；必须抽查真实页面、截图或等价渲染结果。

验证命令可能产生框架生成物变化。验证后必须检查 git diff，恢复与任务无关的生成物变化。

验证失败且修复会扩大范围时，暂停回到大流程。

## 阶段记录

阶段记录服务 Codex 接续执行，不是给人看的流水账。

只有能帮助后续阶段、后续 agent 或恢复上下文时，才写 `phase-log.md`。

只记录：

- 阶段名称。
- 完成内容。
- 关键文件。
- 验证结果。
- 明确未做。
- 剩余风险。
- 是否满足进入下一阶段标准。

决策文档从“待判断”变成“已执行结果”后，后续审计脚本不得覆盖 tracked 决策结果；临时候选输出应写入 `.generated`。

## 自动进入下一阶段

满足以下条件时，可以自动进入下一阶段：

- 当前阶段目标完成。
- 阶段验收标准满足。
- 审查无阻塞问题。
- 必要验证通过，或无法验证原因已说明且不影响继续。
- 下一阶段不需要新的人工决策。

如果下一阶段的操作已经包含在确认路线图的授权范围内，并且没有触碰硬约束或引入新的重大风险，可以自动进入；否则暂停回到大流程。

## 暂停判断

小流程不再因为遇到某一种工作事项就机械暂停，而是判断该事项是否触碰硬约束或形成重大风险。

### 必须暂停

- 需要改变已确认的需求、最终效果、范围、禁止事项、阶段目标或宏观架构。
- 需要执行路线图未授权的不可逆数据操作、生产环境操作、发布、支付或对外行为。
- 需要新的账号、密钥、付费资源、隐私授权或外部平台选择，且现有文档没有授权与边界。
- 发现安全、隐私、合规、成本、数据丢失或生产稳定性风险明显超出原方案。
- 真实项目状态证明当前阶段路线无法成立，继续执行会造成明显返工或扩大范围。
- 用户或其他 agent 的并行改动与当前写入范围发生实际冲突，无法安全绕开。
- 自主诊断修复后，同一根因持续存在，继续处理必须触碰以上边界。

### 可以继续

- 当前需求范围内的澄清、补全和缺失实现。
- 可逆、低风险、可验证的实现调整或普通依赖变更。
- 不改变用户效果的技术替换、文件重组和阶段内部顺序调整。
- 已经由路线图授权的数据处理、Git操作、外部动作和验证。
- 能在当前阶段范围内修复的构建、测试、兼容性、UI和数据问题。

暂停后回到大流程，由人确认需求、方案、路线或高层文档是否需要调整。

## 交接和状态检查

多 agent、多账号或多人接力后，接手者先做只读状态检查：

- git 状态。
- `phase-log.md` 和 `closeout.md`。
- 正式数据数量和核心字段覆盖。
- 关键脚本和验证结果。
- 前台接入点。

不要只相信文档里的“已完成”声明。

## Token 节约规则

1. 先读 workstream 文档，再读代码。
2. 只读当前阶段相关文件。
3. 子 agent 输出短结论，不输出过程长文。
4. 审查输出问题和结论，不复述背景。
5. 批量处理优先脚本化。
6. 阶段记录只写接续需要的信息。
7. 不把完整聊天记录作为执行上下文。

## 阶段完成标准

一个阶段只有满足以下条件才算完成：

- 阶段目标达成。
- 禁止范围未触碰。
- 第一层硬约束未被改变；第二层方案默认如有调整，已记录原因、收益和影响。
- 必要验证完成或无法验证原因已说明。
- 审查结论不是阻塞。
- 必要阶段记录已写清楚。
- 是否进入下一阶段已经判断清楚。
