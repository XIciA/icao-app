# GitHub 单主干与版本维护规则

状态：长期规则
用户批准：2026-08-22

本文是仓库 GitHub、分支、提交、标签、PR、发布来源和清理操作的唯一长期规则。旧工作流、
历史记录和平台文档不得另行定义相互竞争的 Git 规则。

## 1. 唯一主干

- `main` 是唯一长期分支、唯一持续开发基线和唯一正式代码事实来源。
- iOS、Android、EdgeOne Web、Vercel Web、ECS API、数据库迁移、内容和热修均不得建立长期
  平台分支、发布分支或第二主线。
- 所有任务从最新 `origin/main` 开始，并在任务完成前回到 `main`。
- 正式代码不得只存在于本机、额外 worktree、未推送提交或未合并分支。

## 2. 临时任务分支

标准生命周期：

```text
origin/main → codex/<任务名> → 实现与验证 → PR → main → 删除任务分支
```

- 一个任务使用一条短期分支；不要按平台或环境拆成长驻分支。
- `main` 不承载未经验证的开发提交。即使是单人开发，也先使用短期任务分支隔离改动。
- 分支名称描述任务，不使用 `ios-main`、`android-main`、`production`、`release-current` 等
  可能被误解为长期来源的名称。
- 普通分支在当前任务结束时删除。超过 7 天仍未收口时，必须记录原因、负责人和收口日期。
- 分支不是备份。需要长期追溯时使用 commit、PR、annotated tag 和发布记录。

## 3. 提交、推送与合并

- 每个提交只包含一个可解释的逻辑改动；不得混入其他任务或 worktree 的文件。
- 提交前检查 `git status`、目标路径 diff、生成物和敏感信息。只暂存已确认路径，不使用
  `git add .`、`git add -A` 或 `git add --all`。
- 禁止 force-push 或删除 `main`，禁止重写已发布或已打 tag 的提交。
- 中高风险、跨端、运行时、内容批量变更和发布准备必须通过 PR；普通任务也优先使用 PR。
- 合并前同步最新 `main`、解决冲突并完成风险匹配检查。检查失败不得合并。
- GitHub 的干净 runner 使用 `pnpm check:ci`：它验证题库结构、清单、内嵌数据和文本审计，
  但不读取未纳入 Git 的历史媒体二进制。具备完整媒体源的本地发布环境仍必须运行
  `pnpm check`，不得以 `check:ci` 代替正式发布校验。
- 日常 PR 使用 squash merge；一次性历史整合或确需保留父提交关系时可以使用普通 merge，
  并在 PR 中说明原因。
- PR 合并后立即删除本地和远端任务分支，并移除不再需要的 worktree。

## 4. 正式发布来源

以下新发布只能使用已经进入 `origin/main` 的干净提交：

- TestFlight 和 App Store；
- Android 正式签名制品；
- EdgeOne Production 与冻结的 Vercel 旧站；
- ECS API 生产镜像；
- 数据库迁移；
- 对外发布的正式题库、内容和资源。

发布前必须确认当前分支为 `main`、`HEAD` 等于 `origin/main`、工作区干净。版本号或 build
number 的准备属于源码改动，必须先在临时分支提交并合入 `main`，不得在构建过程中临时修改
源码后直接发布。回滚只能使用已经验证的不可变产物或 annotated release tag。

生产部署和数据库迁移仍需用户明确授权；进入 `main` 不自动授权线上动作。Vercel 项目继续
默认冻结，不因 `main` 更新自动构建或部署。

## 5. 版本标签与发布记录

正式标签使用 annotated tag，并绑定精确提交。建议命名：

```text
release/ios-testflight/v<版本>-b<构建号>
release/ios-app-store/v<版本>-b<构建号>
release/android/v<版本>-b<构建号>
release/web-edgeone/<日期>-<短SHA>
release/web-vercel-legacy/<日期>-<短SHA>
release/api-production/<日期>-<短SHA>
```

每次发布记录平台、commit SHA、tag、版本、构建号、迁移版本、时间、验证证据和回滚目标。
无法精确映射 Git 提交的历史部署必须明确标记为历史例外，禁止伪造 tag；下一次发布时恢复
精确映射。

## 6. 热修

```text
main → codex/hotfix-<问题> → 聚焦验证 → main → 发布 → 删除分支
```

- 热修不得成为第二主线，也不得只停留在生产容器或本机。
- 原则上先进入 `main` 再部署。若用户明确批准先行紧急处置，同一任务必须把完全相同的修复
  合回 `main`，否则任务不能关闭。
- 禁止把局部文件复制到旧源码后构建成无法映射完整 commit 的正式镜像。

## 7. 分支与旧规则清理门禁

删除分支前必须确认：

1. 所需独有提交已进入 `main`，或已证实被更新实现替代；
2. 已发布版本有精确 commit/tag，无法映射的历史例外已记录；
3. 对应 worktree 干净且没有未推送修改；
4. 没有构建、部署或 PR 仍引用该分支；
5. 删除范围已经获得用户授权。

与本文冲突、重复、引用旧工具/旧服务器或允许长期平行分支的旧规则直接删除。只有具有事故、
迁移或回滚价值的材料才转入 `docs/records/`，并明确不具规则效力。

## 8. 任务完成标准

- 请求的代码和文档已进入 `origin/main`；
- 必要检查通过，工作区干净；
- 临时本地/远端分支和 worktree 已删除；
- 正式产物可通过 commit/tag 追溯；
- 没有本机独有正式提交、第二现行规则或未说明的发布来源例外。
