# GitHub 三层分支与版本维护规则

状态：长期规则；用户于 2026-11-27 确认替代原单主干流程。

## 分支职责

| 分支 | 职责 | 允许进入的内容 |
| --- | --- | --- |
| `main` | 正式发布主线 | 已完成整合测试、准备正式发布的代码及正式版紧急修复 |
| `develop` | 下一版整合与测试 | 已完成基本验证、能够一起测试的功能 |
| `feature/<功能名>` | 单功能独立开发 | 功能开发、修改、试验和本地测试 |

普通任务从最新 `origin/develop` 创建功能分支，通过 PR 合入 `develop`。
下一版测试完成且用户明确发令正式发布后，才将选定候选合入 `main` 并执行授权平台的发布。
不要求增加长期平台分支、客户分支或第四层 release 分支。
紧急修复可以从 `main` 创建 `feature/fix-<问题>`，完成必要检查后进入 `main`，并同步回 `develop`。

## 当前正式基线

正式运行版本以各组件发布记录中的精确提交、构建号和制品为准；主分支的最新提交不等于每个组件已经部署。
本次结构整理以现有成果为起点，保留当前生产服务，不因创建分支而重新部署。
当前正式制品冻结；后续发布更新 `main`，旧的精确发布提交及标签保持不变。
初始源码基线和各端记录见 [版本管理迁移](../workstreams/version-management/README.md)。

## 提交与整合

- 检查目标 diff、生成物和敏感信息，只暂存本任务明确路径；不使用 `git add .`、`git add -A` 或 `git add --all`。
- 正式代码不能仅存在于未提交修改、本机或额外 worktree；日常开发在功能分支完成。
- 不 force-push、删除 `main` / `develop`，不改写已发布提交和标签。
- 功能进入 `develop` 前完成风险匹配检查。GitHub 干净 runner 使用 `pnpm check:ci`；完整媒体发布环境按需使用 `pnpm check`，两者不冒充彼此。
- 功能 PR 可 squash；`develop` 到 `main` 的版本整合保留父提交关系，避免两条长期分支反复产生不必要差异。发布后将正式修复和版本准备同步回 `develop`。
- 不为普通任务强制增加验收阶梯或人工审批。开发和测试可连续执行，正式上线必须有用户明确指令。

## 发布来源与环境

| 用途 | 源码 | 运行数据 |
| --- | --- | --- |
| 功能本地验证 | `feature/*` | 本地或独立开发数据 |
| 下一版 TestFlight / 测试后端 | 干净且已同步远端的 `develop` 提交 | 独立测试数据库、身份服务和存储 |
| 正式发布候选及生产部署 | 干净且已同步远端的 `main` 提交 | 正式环境 |

构建号和源码配置在功能分支准备并整合后构建，不在发布过程中临时改源码。
构建前同步远端，再验证 `HEAD` 与对应 `origin/main` 或 `origin/develop` 相同；本地缓存 ref 本身不能证明远端没有变化。
TestFlight 只是分发渠道，既可以分发开发测试包，也可以分发正式环境的待审候选。
连接测试环境的包不可直接提交正式发布；正式发布必须重新用正式配置构建、校验并完成所需验收。
源码合入 `main` 不自动触发生产部署、迁移或正式渠道更新。

## 数据与迁移

正式用户数据长期保留并继续增长。测试数据库独立，可重建或从正式快照恢复；测试数据不自动回写正式环境。
每次数据库结构变更随代码记录迁移脚本，测试后端只能迁移测试数据库。
发布前用近期正式快照在测试环境演练候选迁移，并记录快照时间、迁移版本和检查结果。
发布时备份当前正式库，在持续维护的正式库上执行验证过的迁移；不得用测试库覆盖正式库。
按需安排短维护窗口；暂不建设复杂自动回滚或高可用恢复系统。

## 标签、记录与清理

发布使用精确 commit、不可变制品及 annotated release tag，记录平台、版本、构建号、环境、迁移版本、摘要和验证证据。
沿用 `release/<平台>/<版本或日期>-<构建号或短 SHA>`；测试记录必须清楚标注环境，不冒充正式发布。
清理已被替代的功能分支、构建缓存、旧包和项目服务器冗余资源，保留当前正式制品、源码、用户数据、媒体原件和必要备份。
删除前核实运行引用、文件性质和精确范围，不直接删除 `.git` 对象，不运行无范围的 Docker volume 清理。

## 完成状态

分别说明：本地改动完成、远端整合完成、测试环境部署完成、测试包交付、用户验收、正式发布。
未获得实际证据的环节不能标记完成。访问权限阻塞时保留可应用的改动和准确接续记录。
