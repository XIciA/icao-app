## 分支职责

| 分支 | 职责 | 允许进入的内容 |
| --- | --- | --- |
| `main` | 正式发布主线 | 已完成整合测试、准备正式发布的代码及正式版紧急修复 |
| `develop` | 下一版整合与测试 | 已完成基本验证、能够一起测试的功能 |
| `feature/<功能名>` | 单功能独立开发 | 功能开发、修改、试验和本地测试 |

普通任务从最新 `origin/develop` 创建功能分支，通过 PR 合入 `develop`。
下一版测试完成且用户明确发令正式发布后，才将选定候选合入 `main` 并执行授权平台的发布。
不要求增加长期平台分支、客户分支或第四层 release 分支。
紧急修复可以从 `main` 创建 `feature/fix-<问题>`，完成必要检查后进入 `main`，并同步回 `develop`。

## 代码任务开工状态

2026-11-28 用户确认：每个涉及代码修改的聊天，在开始实施、首次修改代码前，先向用户展示当前工作位置与代码状态。
纯需求讨论、规划或文档修改不要求这项输出；同一聊天后来转为代码实施时，再执行本节。

- 先读取实际 Git 状态，核实工作目录、分支、当前提交及未提交修改，不用旧聊天记录代替现场检查。
- 普通新任务从最新 `origin/develop` 准备 `feature/<功能名>`；接续任务核实并沿用已有对应功能分支，不重做已完成工作。
  若初始位于 `main`、`develop` 或 detached HEAD，先说明当前状态，再准备功能分支并展示实际结果，之后才修改代码。
  存在其他任务的未提交修改时保留它们，必要时使用独立 worktree，不为切分支清空或搬走他人的工作。
- 简洁展示：工作目录／worktree 的绝对路径、实际分支、当前提交短 SHA、开发基线（同步核实的 `origin/develop` 提交及接续分支与它的关系）、工作区是否有未提交修改，以及本次开发／测试目标环境。
  无法同步远端时说明基线尚未核实；不得把缓存引用写成已确认的最新代码。环境未核实也应如实说明，并在运行前按下节核实测试配置。
- 状态说明是开工告知，不增加用户审批。无需每条回复重复；本轮切换工作目录、分支或目标环境时，及时更新说明。

在本项目中新建聊天或进入规划模式，不会自行切换 Git 分支，也不自动授权代码实施。
开始已获授权的代码工作时，由执行者按上述规则准备功能分支；功能分支开发、develop 整合测试、main 正式发布的职责保持不变。

## 一套代码、两套运行环境

客户端、API、共享契约与迁移脚本在同一仓库维护。测试端与正式端共用完整业务实现，
不另外维护精简测试版或复制一套业务代码。两个环境可以运行不同阶段的提交：develop 用于
下一版测试，正式服务继续运行已经发布的制品，直到用户明确要求上线。

| 层次 | 开发与测试环境 | 正式环境 |
| --- | --- | --- |
| Web 入口 | 本机 `http://localhost:8081`，运行现有 Expo Web；不要求另建公网测试域名 | `https://readyoufife.com`，沿用正式 Web 部署 |
| 业务 API | `https://test-api.readyoufife.com` | `https://api.readyoufife.com` |
| 登录与文件服务 | `https://test-cloud.readyoufife.com` | `https://cloud.readyoufife.com` |
| 数据 | 独立测试数据库、账号会话及文件副本 | 持续维护正式用户数据 |
| 源码职责 | feature 开发，develop 整合与测试交付 | main 管理正式发布候选与已发布源码 |

完整链路为：本地测试网页／连接测试环境的客户端 → 测试 API → 测试登录、数据库和存储。
正式网页与正式客户端继续连接正式 API 及正式数据。API 和登录／文件域名是服务地址，不是产品操作页面。

- 日常开发默认使用测试配置；启动前核对数据环境与 API、登录服务地址一致，不允许缺少测试配置时自动回落到正式数据。
- 本机配置保存在不提交的 `.env.local`，日常 Web 启动命令为 `pnpm web --port 8081 --localhost`。
  入口依赖本地进程运行，关闭进程或重启电脑后需重新启动；“本地”只表示网页运行在本机，后端仍为独立测试服务。
- 测试服务与正式服务当前运行于同一台服务器的独立服务、数据库和文件目录。隔离的重点是运行配置、权限和数据归属；服务器位置及精确部署版本以执行记录为准。
- AI、短信、支付及第三方登录复用现有业务实现和可复用的供应商账号配置，不因测试环境身份而统一停用。
  数据库连接、会话密钥、内容签名、凭据加密及回调地址保留必要的环境差异。复用真实供应商账号不等于模拟调用或免计费。
- 测试数据可以来自正式快照，但两边后续独立变化，不自动双向同步。客户端测试／正式环境的缓存、登录会话与待同步数据也应隔离。
- 本地网页可用、测试后端可用、测试安装包已交付是不同状态；不得把其中一个写成另外两个已经完成。

正式上线复用测试通过的同一业务代码，用正式配置构建和部署；保留正式用户数据，
不得整目录覆盖正式运行配置、把测试包直接当正式包，或用测试库替换正式库。

## 当前正式基线

正式运行版本以各组件发布记录中的精确提交、构建号和制品为准；主分支的最新提交不等于每个组件已经部署。
本次结构整理以现有成果为起点，保留当前生产服务，不因创建分支而重新部署。
当前正式制品冻结；后续发布更新 `main`，旧的精确发布提交及标签保持不变。
初始源码基线和各端记录见 [版本管理迁移](../workstreams/version-management/README.md)。

## 提交与整合

- 检查目标 diff、生成物和敏感信息，只暂存本任务明确路径；不使用 `git add .`、`git add -A` 或 `git add --all`。
- 正式代码不能仅存在于未提交修改、本机或额外 worktree；日常开发在功能分支完成。
- 不 force-push、删除 `main` / `develop`，不改写已发布提交和标签。
- 功能进入 `develop` 前完成风险匹配检查。GitHub 干净 runner 使用 `pnpm check:ci`；完整媒体发布环境按需使用 `pnpm check`，两者不冒充彼此。
- 功能 PR 可 squash；`develop` 到 `main` 的版本整合保留父提交关系，避免两条长期分支反复产生不必要差异。发布后将正式修复和版本准备同步回 `develop`。
- 不为普通任务强制增加验收阶梯或人工审批。开发和测试可连续执行，正式上线必须有用户明确指令。

## 发布来源与环境

| 用途 | 源码 | 运行数据 |
| --- | --- | --- |
| 功能本地验证 | `feature/*` | 测试环境或明确隔离的本地开发数据 |
| 下一版 TestFlight / 测试后端 | 干净且已同步远端的 `develop` 提交 | 独立测试数据库、身份服务和存储 |
| 正式发布候选及生产部署 | 干净且已同步远端的 `main` 提交 | 正式环境 |

构建号和源码配置在功能分支准备并整合后构建，不在发布过程中临时改源码。
构建前同步远端，再验证 `HEAD` 与对应 `origin/main` 或 `origin/develop` 相同；本地缓存 ref 本身不能证明远端没有变化。
TestFlight 只是分发渠道，既可以分发开发测试包，也可以分发正式环境的待审候选。
连接测试环境的包不可直接提交正式发布；正式发布必须重新用正式配置构建、校验并完成所需验收。
源码合入 `main` 不自动触发生产部署、迁移或正式渠道更新。

## 数据与迁移

正式用户数据长期保留并继续增长。测试数据库独立，可重建或从正式快照恢复；测试数据不自动回写正式环境。
每次数据库结构变更随代码记录迁移脚本，测试后端只能迁移测试数据库。
发布前用近期正式快照在测试环境演练候选迁移，并记录快照时间、迁移版本和检查结果。
发布时备份当前正式库，在持续维护的正式库上执行验证过的迁移；不得用测试库覆盖正式库。
按需安排短维护窗口；暂不建设复杂自动回滚或高可用恢复系统。

## 标签、记录与清理

发布使用精确 commit、不可变制品及 annotated release tag，记录平台、版本、构建号、环境、迁移版本、摘要和验证证据。
沿用 `release/<平台>/<版本或日期>-<构建号或短 SHA>`；测试记录必须清楚标注环境，不冒充正式发布。
清理已被替代的功能分支、构建缓存、旧包和项目服务器冗余资源，保留当前正式制品、源码、用户数据、媒体原件和必要备份。
删除前核实运行引用、文件性质和精确范围，不直接删除 `.git` 对象，不运行无范围的 Docker volume 清理。
