# 交付与验收最简规则

状态：长期开发规则

## 目标

用最短、最能证明用户目标的路径完成交付。验证用于阻止明确回归，不为流程完整而重复构建、
重复安装或重复验收。

本文规定验证和交付边界。复杂任务可按需选用 [工作工具](../tools/README.md) 中的方案与执行方法，
不要求普通任务先建立需求、方案或路线文档。

## 默认流程

```text
明确最终目标
→ 实现最小完整方案
→ 运行与改动直接相关的快速确定性检查
→ 直接交付到最终验收环境
→ 用户验收最终效果
```

不得默认采用以下固定阶梯：

```text
模拟器 → Development Build → Dev 真机 → Release → TestFlight
```

这些环境不是必须逐级通过的质量门。是否使用某一环境，只取决于它是否能以最低成本发现当前
问题，或是否是完成最终交付不可缺少的步骤。

## 验收环境由目标决定

| 用户目标 | 默认交付路径 |
| --- | --- |
| iOS TestFlight | 相关代码检查 → iOS Release 构建并上传 TestFlight → 用户真机验收 |
| Android 测试包/商店测试 | 相关代码检查 → 目标 Release 包或测试渠道 → 用户真机验收 |
| Web 线上效果 | 相关代码检查 → 用户明确授权的目标环境 → 用户浏览器验收 |
| 本地功能或工具 | 相关代码检查 → 最接近真实输入的本地结果 |
| 文档、数据、脚本 | 格式、引用、样例或确定性输出检查；不构建 App |

不得因为仓库里已有模拟器、E2E、Development Build 或全量检查命令，就把它们全部加入当前
任务。共享代码只检查受影响合同；不自动构建未受影响的平台。

## TestFlight 任务

当用户明确把 TestFlight 作为验收目标时：

1. 先完成本次功能所需的相关静态检查、类型检查和聚焦测试。
2. 不以模拟器、Development Build 或 Dev 真机作为上传前置条件。
3. 直接生成使用正式 Bundle ID、Release 配置和递增 build number 的候选包。
4. 校验签名、权限、生产运行时地址和包身份后直接上传 App Store Connect。
5. Apple 处理完成后，由用户在 TestFlight 真机验收。
6. TestFlight 通过后再记录该候选包的真机结果；不得要求尚未生成的候选包预先提供真机证据。

用户已经明确要求“完成后上传 TestFlight”时，该任务内的候选包构建和上传不再重复请求确认；
这不授权提交 App Store 审核或正式发布。

## 必要检查

检查数量按风险决定，但必须保持聚焦：

- 静态边界或格式检查：防止已知危险调用和结构错误。
- 受影响模块测试：验证核心状态、输入输出和失败路径。
- 类型检查：跨 TypeScript 合同变化时执行。
- 目标包校验：发布包必须检查身份、签名、权限、环境和版本。

全项目测试、全平台构建和完整发布矩阵只在改动确实跨越这些范围，或正式发布规则明确要求时
执行。测试通过只代表代码检查通过，不得写成用户效果已经验收。

## 允许增加中间环境的条件

只有以下情况可以增加一个最小的中间诊断步骤：

- 最终环境无法提供定位问题所需的证据。
- 直接构建或上传被签名、配置、编译或平台限制阻塞。
- 改动涉及只能在特定设备能力下观察的底层行为，且等待一次错误的正式候选代价明显更高。
- 用户明确要求该中间环境。

增加时必须说明它要回答的唯一问题；回答后立即回到最终交付路径，不扩展成完整验收阶梯。

## 完成标准

任务完成必须区分三件事：

- **代码检查通过**：自动化和静态检查通过。
- **候选包已交付**：目标构建已上传或目标产物已生成。
- **用户验收通过**：用户已在最终环境确认效果。

三者不得互相替代。默认追求的是尽快把正确候选交到最终环境，而不是累计最多的中间证据。
