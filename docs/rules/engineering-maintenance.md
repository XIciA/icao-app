# 工程维护要求

用户于2026-10-24明确要求纳入长期维护文档。

- 先定位根因：从数据结构、状态管理、共享逻辑和接口链路寻找问题，在合适职责层修复；不以各页面判断、延时、重试或隐藏异常掩盖问题，不扩大为无关重构。
- 及时调整方向：同样方法反复失败、没有新证据或投入与进展失衡时检查假设、换方法；方向正确的必要工作持续解决，不因困难省略功能和验收。
- 将 App 视为整体：功能、分类或交互理念改变时，先梳理所有受影响的入口、关联模块与数据链路，再同步适配；图标、字体、布局和操作遵循全局规范，跨页面采用一致的业务规则，复用同一数据来源与核心机制。验收覆盖关联功能及原有行为，不能只完成当前页面、等待用户逐一指出遗漏。适配范围以实际关联及用户授权为准，不扩大为无关改造。
- 以完整业务流程交付：标注覆盖编辑、保存同步、显示筛选和返回原题；AI覆盖录音、授权、转写编辑、分析展示、额度及失败恢复。孤立功能通过不能代替整体完成。
- 协调受影响的客户端、后端、数据协议和原生配置，兼容旧客户端，不能假设所有用户同时升级；具体维护和发布范围以当前用户授权及项目边界为准。
- 复用现有录音、播放、请求、存储、同步的唯一机制；审查竞态、重复请求、取消、切题、切账号、历史数据及异常恢复，保留无关修改和其他任务成果。
- 长任务按依赖分阶段完成可运行、可审查的闭环，保存必要进度与证据；已授权阶段自主继续，接续时不遗漏、不重复推倒重来。
- 人工决策只阻塞相关部分。常规技术选择与已授权排错自主处理；必须人工认证或重要决策时说明原因、影响、建议，同时继续独立工作。
- 验收反映真实效果及异常恢复；构建、测试、HTTP成功只是部分证据，代码检查、候选交付和实际体验分别记录。发布来源、版本标签、证据、回滚及渠道授权遵守已有仓库和交付规则，不沿用旧任务授权。
