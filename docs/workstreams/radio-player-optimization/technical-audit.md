# 随身听播放系统技术盘点

状态：已完成，待路线图确认

更新时间：2026-07-16

## 1. 盘点结论

当前仓库具备实现随身听正式播放系统的主要基础：三个目标题库已有统一数据 contract 和 `radioEligible` 能力声明，音频经统一资源服务解析，`expo-audio`、本地 KV、共享进度条、Bottom Sheet 和原生导航均已存在。

当前实现不能直接视为完整播放器。主要缺口是页面私有播放器、50 条截断、没有真实播放模式和自动续播、字幕模式不全、不可拖动进度、无全局迷你播放器、无后台/锁屏媒体控制，以及多处组件独立修改全局音频模式。

本次盘点还发现题库内容正在进行另一条未提交迁移：当前候选随身听曲目已经由旧基线的 1,827 条增长到 2,559 条，既有时长索引缺少新增 732 条。随身听开发必须先与该迁移收口后的正式内容版本对账，不能按旧数量或当前 dirty worktree 临时状态写死实现。

## 3. 当前随身听实现

入口与页面：

- 发现页入口：`src/features/content/DiscoverHomeScreen.tsx`。
- 路由：`src/app/content/[slug].tsx` 的 `radio` 分支。
- 页面：`src/features/content/RadioPlayerScreen.tsx`。

已经具备：

- 听力、900 句、故事复诵切换；
- 从嵌入题库读取真实音频、英文和中文；
- 播放/暂停、上一首、下一首；
- 0.75×、1×、1.25×、1.5× 倍速入口；
- 简单进度显示、加载超时和重试；
- 播放列表 Bottom Sheet。

已确认缺口：

| 项目 | 当前状态 | 影响 |
| --- | --- | --- |
| 曲目范围 | `slice(0, 50)` | 三个模块绝大多数内容不可达 |
| 播放模式 | “顺序播放”按钮只打开列表 | 无顺序续播、单曲循环、随机播放 |
| 自动续播 | 未处理 `didJustFinish` | 每首结束后停止 |
| 字幕 | 只有 `off` / `bi` | 缺少“仅英文” |
| 进度 | 只画宽度，不可拖动 | 不符合常规播放器体验 |
| 生命周期 | 播放器由页面 hook 持有 | 离开页面后实例释放，无法迷你播放器承接 |
| 后台 | `shouldPlayInBackground: false` | 后台和锁屏体验不成立 |
| 锁屏 | 未注册锁屏媒体控制 | 系统媒体中心无可靠控制与元数据 |
| 队列 | `ScrollView` 渲染、非当前项显示 `--:--` | 数千曲目性能和信息完整度不足 |
| 布局 | 顶部负 margin、字幕定高、控制区随内容挤压 | 长文本和不同屏幕尺寸有遮挡风险 |
| 恢复 | 状态仅在页面内存 | App 重启后模块、曲目、进度和偏好丢失 |

## 5. 时长索引状态

只读设计仓库已有 `radio-duration-index.json`：

- 共 1,827 条；
- 听力 631、900 句 900、故事复诵 296；
- 以卡片 ID 关联音频路径和秒数；
- 当前 1,827 条均能匹配 App 候选数据，无多余条目。

与当前 2,559 条候选曲目对账：

- 已匹配时长：1,827；
- 缺少时长：732；
- 旧索引多余：0。

结论：既有索引值得复用，但不能直接作为最终完整运行时数据。应把它作为历史基线导入当前内容工程，并从当前规范音频资源补齐 732 条及未来新增曲目的时长；最终由题库内容构建和校验统一发布，不能在随身听 feature 再维护一份私有索引。

## 6. 可复用的共享能力

### 6.1 题库内容与能力声明

- `content/question-banks/` 已是题库维护源，按 bank/category/topic/card 拆分。
- 五套题库共用 schema、registry、构建和检查工具。
- 三个目标题库的 `bank.json` 已有 `capabilities.radioEligible: true`；陆空通话和 OPI 为 `false`。
- 当前生成到 App 的 `QuestionBankDataset` 尚未保留该能力字段，随身听仍用页面内三个 ID 过滤；共享运行时 contract 需要补上这一发布步骤。
- App 运行时已有 `loadQuestionBank`，支持远程、ETag、本地 cache 和 embedded 回退。

可复用结论：随身听应先把既有能力声明发布进统一运行时 contract，再通过 repository 加载正式数据集，从能力声明、卡片字段和稳定 ID 构建播放队列，不继续直接依赖 `getEmbeddedQuestionBanks()`。

### 6.2 音频资源解析

- `resource-service.ts` 已支持开发资源基址、生产签名地址、本地 KV 缓存、过期检查和强制刷新。
- `useQuestionBankAsset` 已包装本地/远程解析和重试。
- 音频加载超时 hook 已在题库播放器和随身听中使用。

可复用结论：资源地址和重试逻辑应下沉为可供全局播放控制器调用的共享接口，沿用同一 cache key 和刷新规则，不能另写随身听 URL 逻辑。

### 6.3 播放与进度组件

- `StudyAudioPlayer` 已有真实进度拖动、倍速、加载/缓冲/失败和重试交互。
- `AudioTimeline` 是可复用的原生进度组件。
- `expo-audio` 已锁定在 SDK 55 对应版本，当前 App 已使用 `useAudioPlayer` 和播放状态订阅。

可复用结论：全屏随身听应复用进度和错误语义，但不能把 `StudyAudioPlayer` 整体嵌入，因为它是题卡内、前台、随组件卸载的短音频播放器。

### 6.4 本地保存与 UI

- `expo-sqlite/kv-store` 已用于题库 cache、资源地址 cache 和其它本地状态。
- App 已有 TopBar、BottomSheet、AppText、CenteredState、主题令牌和安全区基础。
- 根布局可挂载在受保护路由生命周期内持续存在的 Provider 和迷你播放器宿主。

## 7. 音频生命周期冲突

当前至少三处直接或间接持有音频能力：

- `RadioPlayerScreen`：页面播放器并在挂载时设置音频模式；
- `StudyAudioPlayer`：每个学习页播放器并在挂载时设置音频模式；
- `SpeakingPracticePanel`：录音与回放期间多次切换全局音频模式。

这不是内容数据重复，但已经形成多个全局音频模式写入者。随身听开启后台播放后，如果继续保留这种结构，题库音频或录音可能把后台模式改回 `false`，也可能出现两个播放实例同时出声。

结论：本任务必须建立共享音频会话协调层，明确“随身听长播放、题卡短播放、录音、录音回放”四类角色的互斥和音频模式切换。各 feature 可以保留满足自身用途的 player/recorder 实例，但不能继续各自无协调地拥有全局音频模式。

## 8. Expo SDK 55 能力核对

官方文档确认：

- `useAudioPlayer` 适合组件生命周期播放器；跨页面持久播放器可放在长期挂载 Provider，必要时才使用需要手动释放的 `createAudioPlayer`。
- `AudioStatus.didJustFinish` 可驱动自动切歌；`replace`、`seekTo`、`setPlaybackRate` 支持本需求的核心控制。
- 后台播放需要 config plugin、运行时 `shouldPlayInBackground: true` 和适当的 interruption mode。
- Android 持续后台播放必须启用锁屏控制；锁屏控制同一时间只能由一个 player 持有。
- `AudioPlaylist` 支持 gapless 和 `none` / `single` / `all` 循环，但没有直接提供本需求的随机历史语义。

当前 `app.json` 只登记了字符串形式的 `expo-audio` plugin，代码运行时明确关闭后台播放；因此后台和锁屏属于需要更新原生配置并重建 Development Build 的能力，不是 Metro 热更新即可完成。

## 9. 文档与实现偏差

`rn-web-mobile-parity/phase-log.md` 曾记录“随身听完成题库切换、真实音频、倍速、字幕和播放列表 Sheet”。这准确描述了当时的视觉对照范围，但不能证明本次需求中的完整播放模式、全量队列、后台、锁屏、迷你播放器和时长索引已经完成。

本工作流收口时需要补充新的 phase-log 和 closeout，以真实功能验收结果为准，不覆盖旧复刻记录的历史语境。

## 10. 风险与前置门槛

### P0：进入实现前必须解决

- 等待或协调当前题库内容迁移，冻结正式 `radioEligible` 曲目集合和发布版本。
- 明确时长元数据进入现有内容 schema、构建产物和 App contract 的位置，并保证只有一个维护源。
- 建立共享音频会话所有权，禁止多个组件继续竞争 `setAudioModeAsync`。
- 冻结顺序、单曲、随机、上一首和冷启动恢复的明确行为。

### P1：核心实现阶段必须验证

- 签名资源地址按需解析，不一次为 2,559 条曲目请求 URL。
- 自动切歌不会因重复状态事件、快速点击或资源失败跳两首。
- 随机模式保存历史并避免连续重复。
- 迷你播放器和全屏播放器订阅同一状态，离开页面不释放当前 player。
- 录音、题卡音频和随身听互斥，不出现意外自动恢复。

### P2：真机验收持续处理

- iOS/Android 后台、锁屏、耳机、蓝牙、来电、音频焦点行为差异。
- Android 前台媒体服务与系统通知表现。
- 长字幕、数千条队列、低端设备滚动和内存占用。
- 内容更新后保存曲目不存在、时长变化和签名 URL 过期的恢复。

## 11. 总体判断

任务可以进入实施，但必须先经过用户对四份大流程文档的确认。建议顺序为：冻结共享内容与时长 contract → 建立队列和音频会话核心 → 接入全局播放状态 → 重构全屏播放器与队列 → 接入迷你播放器和后台/锁屏 → 双端真机与视觉验收 → 收口。

当前不需要新增第三方播放依赖，也不需要新建随身听内容 API。若 Expo SDK 55 在真实设备上无法满足已确认的后台或锁屏行为，应带证据返回大流程重新选型，而不是在小流程中临时引入另一套播放器。
