## 推荐方案概览

保留现有全局管理器与本地资源缓存，采用持久化任务队列、受限并发、下载与落盘连续衔接、失败局部重试。页面只展示和操作，不拥有任务生命期。本轮始终按文件传输与增量更新，不新增资源包格式、打包发布链或解包逻辑。以下现状中的“包”指现有逻辑下载范围，不指压缩资源包。

用户效果：点击即有反馈，可离开页面继续使用 App；多个任务按顺序进行；断网等待、恢复网络自动继续；主动暂停不自动恢复；已完成文件复用；完成状态必须对应真实可用内容。后台持续传输是另一个平台能力议题，本轮明确保证的目标是 App 内换页不影响下载。

## 公开成熟实现参考

以下为 2026-11-02 查阅的官方资料，只用于选取设计，不宣称存在适用于所有项目的最快方案。

- [Android Media3 下载架构](https://developer.android.com/media/media3/exoplayer/downloading-media)：管理器统一控制任务，索引持久化状态，运行条件与主动停止原因分开，并发数有上限。参考其职责划分，不为普通加密音频下载直接引入整套播放器缓存系统。
- [Apple 后台下载指导](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background?language=objc)：建议少量共享会话；大量任务存在自身开销，数千任务时考虑更少、更大的传输。后台逐个完成后再启动下一项还可能遭遇系统调度延迟。这为分块打包提供依据，不代表前台也应无限并发。
- [Android 数据传输选型](https://developer.android.com/develop/background-work/background-tasks/data-transfer-options)：明确区分用户主动传输与可延迟后台工作，按需求选择原生机制。不能用 JS 定时器或简单监听页面退出实现可靠后台下载。
- [Expo SDK 55 文件系统旧接口](https://docs.expo.dev/versions/v55.0.0/sdk/filesystem-legacy/)：支持暂停数据保存与恢复，并说明 iOS 后台会话行为。项目锁定 Expo 55、expo-file-system 55.0.23；不能将 latest 文档里的新 API 默认视为当前已安装能力。原生传输可后台继续也不等于 JS 队列、校验加密在进程挂起后持续执行。

## 下载速度：优化现有按文件流程

### 首选：现有文件下载路径优化

1. 正文准备采用小规模受限并发，消除逐主题串行；批量正文接口仅在请求成本显著时考虑。媒体只在对应正文和授权准备好后调度，不必等待整个题库全部正文完成。
2. 保留批量解析资源地址，但不把 24 个文件的完成作为下一批开始的硬屏障；及时准备后续地址，让空闲传输名额有工作可做。签名即将到期时按需合并刷新，不预取大量即将失效的地址。
3. 传输并发与校验加密的并发分别受限。下载完成的文件进入有容量上限的落盘队列，下载后续文件与处理前面文件重叠；队列满则暂停分配新传输，控制磁盘与内存。不把整库读入内存。
4. 并发值通过代表性设备和网络对照选择，可先对照 2、4、6 等测试点，数字不是已确认配置或行业统一最优值。避免复杂的自适应算法，优先少量清晰参数；播放时保留资源，暂停播放后不能长期误判为忙碌。
5. 授权与索引在同一有效上下文内复用，减少每文件重复读取/解密正文；仍保留账号、范围、到期和取消边界。不要把性能问题误归因于每个文件都联网查询会员。
6. 文件大小、哈希、加密与可靠保存仍需验证；将必要验证尽量在单文件完成时结束，并记录与内容摘要绑定的完成结果。最后确认清单所有资源完整，不在没有依据时重复全量读盘，也不直接删除落盘完整性验证。
7. 区分无进展超时与总时限，避免健康但较慢的传输固定两分钟被取消；连接故障采用有限退避重试。明确权限拒绝不盲目重试，过期签名重新解析，文件损坏只重取相关资源。

### 明确的执行顺序

接受任务并保存用户意图 → 读取清单、核对账号权限与空间 → 复用已完成资源，有限并发准备缺失正文和授权 → 将已就绪音频持续交给传输队列 → 单文件完成后进入有界校验保存队列，同时传输后续文件 → 汇总确认指定范围完整 → 标记已下载。

网络传输槽与处理槽分开，临时文件按数量和字节总量设上限；校验加密初期保留低并发，避免大幅增加内存。网络状态由统一监听更新，关键请求边界核对，不在每个循环重复查询原生网络接口。读取/权限结果只在当前账号与有效授权上下文中复用，切换账号、授权变化和任务取消立即失效。

先保留跨题库按序调度，集中加速当前题库；每个题库内部连续并行，不为了多个任务看起来同时动而争抢同一网络。当前任务结束、主动暂停或失败后，调度下一个符合条件的任务。

## 任务状态：少量事实统一推导

每个下载任务只维护必要事实：任务与账号标识、目标清单、用户是否要求继续、已可靠完成的资源、当前阶段与失败原因。网络和前后台是管理器统一感知的运行条件，不由各页面复制保存。

- 一个管理器决定开始、暂停、继续、取消和删除，所有页面订阅同一结果。
- 任务关键变更可靠保存，进度展示与落盘节流分开。已确认落盘的完成量与当前传输临时字节分开，恢复时不把整个任务归零；未完成小文件重下不承诺字节完全不回退。
- 正常按包顺序执行，包内有限并发。当前包的单个失败有界重试，无法恢复则该包暂停/失败，允许队列处理其他可执行包。网络或磁盘等全局条件不满足时停止调度，不逐包制造失败。
- 主动暂停必须保留用户意图；因网络/生命周期等待的任务在条件恢复后继续。重复点击不重复排队，账号切换和删除后旧回调失效。
- 清单刷新失败不盖住已有任务进度。保存失败不得伪造完成，也不得把已经可靠完成的其他包全部改成待重下；按真实持久化边界恢复。
- 小文件优先实现资源级恢复：完整文件不重下，未完成文件重取。现有大文件才按收益考虑持久化字节断点；恢复需核对资源版本和服务器支持，签名 URL 不能作为资源永久身份。

### 状态判定与恢复

不把每一种原因创建成独立流程。用任务意图（继续/主动暂停）、执行阶段（等待/准备/传输/收尾/完成/失败）和运行条件推导一个显示结果。已保存可用版本与正在下载的新目标分开，更新失败不改变旧版本已可用的事实。

- 已完成且无新目标：已下载；普通更新作为现有状态位的更新信息。
- 未完成且用户主动暂停：已暂停，任何自动恢复事件都不覆盖它。
- 用户希望继续，但有明确不可自动恢复的故障：显示对应短原因，用户重试后重新调度。
- 用户希望继续，网络或流量许可不满足：等待网络/等待 Wi-Fi，不记作下载失败；恢复条件后重新调度。
- 条件满足但还未轮到：等待下载；轮到后按阶段显示准备中、下载中、校验中。
- 前台暂不可执行时保留继续意图，回来后恢复；账号不一致则不恢复原账号任务。

进度以同一目标清单为基准，区分已可靠保存字节与当前传输字节；不以“重新进入页面”或“点击继续”清零。若清单变化先重算真实缺失量；暂停丢失的单文件临时字节允许真实回退，不伪造单调进度。收尾展示校验中，完成前不展示已下载。

重复点击同一任务只受理一次；同一题库下载期间不另建竞争范围任务。一个文件的可恢复网络失败自动有限重试，超过上限才将该任务记为失败。等待网络不消耗失败重试额度。页面清单请求、后台更新检查和下载任务各自错误不能互相覆盖。

## 落地顺序与验证标准

未来获得实施授权后，先同时解决页面独立性、自动恢复和状态污染，再沿测量结果优化传输流水与重复开销。本轮不使用资源包；真正原生后台持续下载另行讨论，避免为本轮目标大规模改架构。

测量选同一清单、同一设备和网络，对照冷下载、已下载恢复、少量更新、多任务和边播放边下载；统计准备时间、总用时、有效传输速度、请求次数、最终处理时间、失败率、峰值内存与临时空间。核对真实资源数量及大小分布，不以“小文件多”的描述直接替代清单数据。未测量前不承诺提速倍数。

验收必须证明：App 内切页不断；断网恢复可继续且主动暂停不被恢复；重启后完整资源不重下；单任务错误不污染其他完成任务；不串账号；显示已下载的范围可离线读播。方案阶段未启动下载、测速、构建或发布。

## 当前流程

页面获取清单 → 用户点击下载 → 持久化排队状态 → 全局队列逐包执行 → 再取最新清单、检查网络与空间 → 获取目录、逐主题正文及授权 → 每批 24 项解析资源地址、最多 2 个资源并行下载 → 每个文件哈希校验、加密落盘 → 全包逐项解密和哈希复核 → 标为完成 → 再检查更新。

## 慢的已知机制与待验证边界

- 一个包完成后才执行下一个包；多选任务不代表多个包同时传输。
- 正文按主题串行请求、加密保存与建立资源索引，全部完成后才进入媒体阶段；开头可能长时间无明显字节进度。
- 音频并发为 2；检测到音频会话所有者时，新批量传输的准入上限降为 1。此信号不完全等同于用户耳中正在播放，需要验证暂停播放器等状态是否仍占所有权。
- 资源分成 24 项一批，当前批次全部收尾后才准备下一批，慢文件可能拖住批次边界。
- 文件下载后的校验、加密、写盘全局串行，而且处理结束前仍占用传输槽。文件逐个检查授权、索引与网络，也会产生额外开销。
- 完成时又逐文件解密并计算哈希，可能造成最后阶段等待；不能为提速直接取消必要完整性验证。
- 每次继续任务重置显示计数；已完成音频通过逐项检查复用，进度可能先回零再跳升。未完成首次下载的正文，复用路径主要依赖 `saved`，可能重新获取。
- 单文件固定 120 秒总时限；取消后清理临时文件，未持久化断点信息。使用了名为 resumable 的 API 不代表当前实现有跨暂停字节断点续传。

以上证明存在串行等待与重复工作，不能据此量化速度或断言服务器/CDN是主因。实施时先记录准备、请求、传输、校验、写盘耗时及资源数量/体积，再调整瓶颈。

## 离开下载页面为什么可能停

下载由模块级队列持有，页面卸载只停止自身更新，没有取消下载。因此“在 App 内返回其他页面就停止”不是这段代码的预期行为，需在实际发生时核对任务是否暂停、账号上下文是否变化、是否只是进度显示未同步或速度下降。

明确存在的暂停条件：AppState 任何非 active 状态（包含 inactive）、断网、未经允许切换移动网络、用户主动暂停、账号/环境上下文改变。恢复前台或网络没有自动恢复流程。重启恢复持久化记录时，排队、下载中和校验中均转为暂停。

运行中的包暂停后，队列仍会尝试后续包；如果 App 仍非活跃或仍无网，后面的包也会陆续进入暂停，而不是保持等待。这能形成“几个任务一起变状态”的体验，但尚未证明就是用户反馈的设备现象。

## 多任务状态风险

- 下载包状态、清单请求错误、当前选中范围共同决定展示；页面局部清单错误可能盖住真实任务状态。获取说明信息失败不应让正常下载看起来失败。
- 任一次全局状态保存失败，当前 `save` 的错误处理把所有包置为 error，并为已完成包补上 target。共享存储失败需要说明，但不能由此推断所有已下载文件损坏或都需重下。
- 正文准备阶段主要更新项目数量，已有总字节数时 UI 优先使用字节比例，容易显示长时间 0%；恢复下载从零重新统计，最后校验又最多显示 99%，会增加“卡住/重来”的感觉。
- 断网/后台暂停、用户暂停、一般故障主要复用 paused 加错误文字，缺少可靠的恢复意图区分；不能直接给所有 paused 自动恢复，否则会违背用户主动暂停。
- 普通题库每库一个任务身份，所选范围绑定在该任务上；单词按书独立。应保留明确粒度，避免同库范围竞争覆盖。
- 当前已有任务 token、账号 generation、请求合并及共享传输取消保护，可继续使用。不能据状态复杂就整体推翻。

## 建议的用户体验

| 用户操作/遭遇 | 目标效果 | 简短显示 |
| --- | --- | --- |
| 点一个下载 | 立即明确已受理，准备后开始传输 | 准备中 → 下载中 |
| 连点几个不同下载 | 按队列依次进行，一个完成后自动接下一个；不要求页面停留 | 下载中 / 等待下载 |
| 返回题库或进入其他 App 内页面 | 持续下载，回下载页看到真实进度 | 下载中 |
| 一边学习一边下载 | 播放优先，下载适当让速；暂停播放后恢复正常下载能力 | 保持下载中，不增加横幅 |
| 主动暂停某个任务 | 只暂停这一项，其他允许的任务继续；不擅自恢复 | 已暂停；继续 |
| 断网 | 保存已完成部分，其余等待，不把每个任务都变成故障 | 等待网络 |
| 网络恢复 | 原本希望继续的任务自动恢复；用户主动暂停的仍暂停 | 下载中 / 等待下载 |
| Wi-Fi 切换到未授权移动网络 | 不偷偷消耗流量；用户同意或回 Wi-Fi 后继续 | 等待 Wi-Fi |
| 离开 App、锁屏、短暂非活跃 | 需与 App 内换页区分。基础建议为尽量保留任务，受系统限制暂停后回前台自动恢复；是否要求真正持续后台传输另行讨论 | 暂停期间保留进度，回前台恢复 |
| 关闭 App 后重开 | 恢复任务和已完成资源；建议在账号及网络条件允许时恢复原本未主动暂停的任务 | 恢复后显示真实状态 |
| 一个资源暂时失败 | 有界重试，仅当前任务受影响；其他任务仍可进行 | 无法恢复时显示下载失败；继续 |
| 空间不足或本机保存失败 | 停止不能安全持久化的新工作，保留已确认完成的文件；不得把所有完成包改成未完成 | 空间不足 / 保存失败 |
| 下载接近完成 | 明确进入校验阶段，校验成功才显示完成 | 校验中 → 已下载 |
| 扩展范围或继续下载 | 复用已完成资源，不表现成全部重下 | 真实已完成量与进度 |

继续遵循现有卡片状态位，避免增加多行说明或全局横幅。内部暂停原因服务恢复逻辑，对用户只显示必要的短状态。后台持续下载尚未作可行性验证，不承诺 iOS/Android 被系统终止后仍持续传输。

## 最小完整调整建议

1. 保留全局下载管理器与现有缓存所有者，页面只订阅和发出操作。核实并修复 App 内换页停止的真实触发链。
2. 区分用户意图和运行条件：用户希望下载/主动暂停，与正在执行/等待网络/等待前台分开；全局条件不满足时暂停调度，不把队列逐个失败。恢复由同一管理器负责。
3. 保留逐包调度作为初始方案，先优化包内耗时，避免简单地让所有包无限并发。正文适度并发、跨批次连续供给、重复读取减少均以测量为依据，限制内存和磁盘占用，保留播放优先。
4. 保留文件完整性校验和加密。用可证明的校验记录减少重复工作，优化传输与处理衔接；不以删校验换速度。
5. 将准备/传输/校验如实展示；已落盘完成量在恢复时复用，不先把已确认进度清零。未完成单文件是否实现真正字节断点续传，按体积与收益再决定。
6. 页面清单加载错误不能覆盖任务真实进度；存储错误不能无差别污染所有已完成包。任务失败、账号切换、删除后的迟到回调继续受现有 token/generation 约束。
