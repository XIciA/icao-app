## 1. 文档目的与授权边界

本文件记录本轮讨论中已经确定的需求，作为后续继续讨论、制定方案及交接上下文的依据。已确认需求、只读检查事实和待定实现分别记录，不能相互替代。

2026-11-27 用户明确要求“开始执行”，并授权必要的电脑、网络和配置操作，连续完成已确认的结构整理与项目冗余清理，不再逐项请求人工确认。这不等于发布新产品版本；当前正式服务、用户数据和未来正式上线发令边界继续保留。用户授权不改变当前会话实际可用的系统及连接权限，执行状态见第 16 节。

## 2. 大任务与目标

本轮优化统一归为一个大任务：**版本管理**。

目标：在保持当前已上线版本稳定、正式用户数据连续的前提下，让 Codex 可以并行开发多个功能，分别测试、按完成情况整合，并经过验证后受控发布；同时解决后端版本兼容、数据库演进、备份恢复和发布追溯问题。

本任务不是一次无边界代码重构。三端同步故障修复、UI 重构、学习统计、AI 评测等具体功能，不因本文自动纳入实施范围；其中几个功能仅用来说明版本管理场景。

## 3. 已确认：采用三层分支结构

**用户明确选择：`main` 管正式发布，`develop` 管下一版整合，`feature/功能名` 管单功能独立开发。后续方案以这三层为固定主体，不再改回“仅 main 的单主干方案”。**

| 分支 | 负责什么 | 什么内容可以进入 |
| --- | --- | --- |
| `main` | 正式发布主线 | 完成整合测试、准备正式发布的代码，以及正式版紧急修复 |
| `develop` | 下一版的功能整合 | 已完成基本验证、可以与其他功能一起测试的代码 |
| `feature/功能名` | 单个功能独立开发 | 该功能的开发、修改、试验和测试 |

### 3.1 main

- 维护正式发布主线，不作为日常新功能试验区。
- 新版本完成整合测试并确定发布范围后，才进入 main。
- 合入 main 与实际部署、上传或正式发布是不同动作，不能因为合并代码就自动改变线上版本。
- main 可以包含已准备但尚未在所有平台正式可用的代码。各平台实际线上版本以发布清单中的具体提交和产物为准。

### 3.2 develop

- 长期维护下一版整合代码，是多个已完成基本验证功能的汇合位置。
- 接收可整合的功能，进行组合使用、共享接口和跨端影响验证。
- develop 的更新不自动部署至正式环境。
- 某功能尚未完成时，保留在自己的功能分支；不能仅为“汇总代码”而把不具备整合条件的功能提前混入下一版。

### 3.3 feature/功能名

- 从明确的 develop 基线创建，每个功能独立开发和测试。
- 一个功能涉及客户端、API、共享接口定义和数据库变更时，可以在同一功能分支内配套修改。
- 功能通过基本验证后合入 develop，随后进行整合测试。
- 功能分支是临时分支；完成合并且确认没有独有工作或仍在使用的构建引用后，按后续确定的收尾方式删除。提交历史继续保留。
- 并行开发应隔离工作目录与任务改动；采用 worktree 等工具的具体操作流程在实施方案中确定。

### 3.4 不增加已确认结构的层级

本轮只确认上述三层。此前提到的 `release/*`、`hotfix/*` 仅是助手提出的可选实现，**不作为已经确认的第四层或必建分支**。候选稳定、紧急修复和修复同步的具体操作方式另行确定，并保持三层主体清楚。

## 4. 已确认：当前发布版本作为冻结基线

- 以实际已经发布的版本为基线，不能直接把存在未提交修改的本机目录当作上线源码。
- 新功能的开发、测试及合并不自动替换当前正式 App、正式官网或正式 API。
- 冻结基线需要可追溯到源码提交、标签、安装包或部署产物、后端镜像及相关配置。
- 数据库结构版本、远程内容版本和正式更新清单也需要纳入发布状态记录，避免只冻结客户端而改变其依赖。
- 正式用户正常登录、学习、购买及新增记录继续发生。冻结不等于把业务数据库设为只读。
- 正式版本冻结至后续明确授权发布新版本或进行特定修复；已有冻结基线仍保留用于追溯。
- iOS、Android、Web、API 和运营后台可能来自不同提交，应分别记录，不强行视为同一个源码快照。

## 5. 已确认：支持并行开发、独立测试与按需整合

必须支持以下使用场景：

1. 当前正式版本继续运行，同时开发 UI 重构、学习统计和 AI 评测等不同任务。
2. 各功能独立开发与验证，不必等待其他功能完成。无需新后端支持的功能可单独交付测试包；需要后端改动的功能，未合入 develop 前先在本地验证，达到可整合状态后进入 develop，并通过共用测试后端联调。
3. iOS 测试版本可以通过 TestFlight 交付；其他平台采用相应测试渠道或测试网站。
4. 已完成的功能可以进入 develop 联合测试，尚未完成的功能继续独立开发。
5. 本次版本可以只包含已成熟且依赖完整的功能，不必等待所有功能一起上线。
6. 代码合并成功不等于功能兼容、测试通过或已经上线，相关状态必须分开记录。

示例：UI 和学习统计已经完成，则两者进入 develop 整合测试；AI 评测继续留在 feature 分支。本次发布可以选择前两项，但如果其中一项实际依赖 AI 功能，则需先处理依赖，不能仅凭分支隔离认定它可独立发布。

## 6. 测试与正式交付要求

| 阶段 | 代码来源 | 预期用途 |
| --- | --- | --- |
| 单功能测试 | feature 分支的确定提交 | 本地验证单个功能 |
| 整合测试 | develop 的确定提交 | 使用共用测试后端与独立测试库验证组合功能 |
| 发布演练 | 本次确定的候选提交 | 在正式数据副本上演练升级，验证历史数据及关键功能 |
| 正式发布 | 已进入 main 的经验证提交及对应产物 | 用户明确发令后，更新获授权的平台或服务 |

- 每个测试包记录提交、构建号、功能范围和连接环境。
- TestFlight 是分发渠道；测试包明确连接独立测试环境，测试记录不自动回写正式环境。
- 不为每个功能分支长期部署服务器后端；依赖未合入后端改动的功能先在本地验证。
- 测试与正式配置不同；正式候选的配置或产物变化后，应按影响范围补充验证。
- 测试包交付不自动授权正式发布。正式发布要明确对应平台、服务、提交和数据库变更。

### 6.1 已确认的验收分工

| 检查内容 | 负责方 | 检查范围 |
| --- | --- | --- |
| 本次新功能 | Codex 验证，用户体验验收 | 功能符合需求，操作和展示符合预期 |
| 受影响的原有功能 | Codex 尽量自动检查 | 关联页面、接口及业务逻辑 |
| 发布前关键检查 | Codex 执行并汇报 | 登录、会员权限、学习记录读写及本次数据升级 |

- 按改动影响确定检查范围，不要求每次全面重测无关功能。
- Codex 如实区分通过、失败、未验证和已知问题，用户主要负责功能体验与最终上线决定。
- 上线前提供简短说明：本版功能、验证结果与未决问题、是否改库／维护／强制更新，以及本次发布的端和服务。
- 用户明确说“可以上线”后，再执行对应正式发布。具体用例和自动化实现随任务确定。

## 7. 已确认的后端、数据与发布闭环

### 7.1 两套 API／后端程序，分别使用独立数据库

最新决定取代 V1.1 的“两套 API 共用正式库、测试写入正式系统”方案。

| 项目 | 正式环境 | 测试环境 |
| --- | --- | --- |
| 后端代码来源 | main 中确定的正式发布提交 | develop 中确定的测试提交 |
| 运行程序 | 一套正式 API／后端程序 | 一套共用测试 API／后端程序 |
| 谁来访问 | 正式 App、正式网站 | TestFlight 等测试版本 |
| 数据库 | 唯一权威的正式用户数据库，数据持续增长 | 独立测试数据库，可以重建或导入经过处理的正式数据副本 |
| 写入归属 | 持续保存真实业务数据 | 测试写入留在测试环境，不自动回写正式环境 |
| 更新方式 | 明确正式发布时更新 | 随功能整合需要反复部署 |

- 正式用户数据长期保留并随业务持续更新；唯一权威来源不排斥测试副本或备份。
- 测试库可修改结构、试验和重建，但数据副本仍需保护。测试数据库不会在发布时变成正式数据库。
- 隔离要覆盖数据库连接与权限，并检查账号、文件、后台任务、支付及其他外部服务，防止测试操作触及正式资源。
- 部署位置和容量待核实；同机逻辑隔离不消除服务器资源争用和共同故障。
- 不是每发布一版就永久增加容器，也不要求所有旧后端版本长期运行。

### 7.2 多功能共用一个测试后端（已确认选择 A）

- 功能从 feature 分支本地开发、验证；达到可整合状态后进入 develop，部署到同一个测试后端联调。
- 本阶段不为每个功能创建长期服务器测试实例。
- 测试包与后端接口需匹配；多个功能有依赖时协调合入和部署顺序，不随意覆盖共享测试后端。
- 正式发布后，测试后端继续服务下一轮开发。

### 7.3 数据库版本与正式数据连续性

- 管理数据库结构变更脚本、必要的数据转换规则及其执行记录；这些内容随功能代码纳入版本管理。
- 发布时在现有正式数据库执行已验证的变更，保留真实数据，不以测试库覆盖正式库，也不合并测试学习记录。
- 正式数据库变更独立管理，不由测试后端启动时执行。
- 发布顺序由新旧程序和结构的兼容关系确定，不能机械规定每次都先改库或先部署。
- 当前正式基线冻结不阻止用户正常登录、学习、购买和新增记录。

### 7.4 兼容与强制更新（已确认选择 B：按改动决定）

- 普通更新允许仍能正确工作的旧版继续使用。
- 重大接口或业务规则变化导致旧客户端无法正确工作时，可以强制更新，不要求所有历史版本永久兼容。
- 数据库结构改变本身不必然要求强制更新；若后端仍能兼容旧接口，可以继续支持旧客户端。
- 强制更新需等对应平台的新版本实际可安装，并具备适当提示或拦截路径。
- 具体最低版本、平台差异、接口识别和过渡安排留待实施设计。
- 强制更新不能代替正式数据库迁移验证。

### 7.5 简单备份与人工恢复边界

- 正式用户数据库定期单独备份；涉及数据库结构或批量数据修改的发布，执行前额外备份。
- 采用简单、可维护的方式，明确保存位置、是否成功、保留规则及基本恢复方法。
- 本阶段不新增复杂自动回滚、容灾、分钟级恢复或高可用建设，不以详细的数据损失时间／恢复时间指标阻塞版本管理。
- 出现问题由人工判断处理；程序回退与数据恢复是不同操作，不默认整库恢复旧备份覆盖发布后新增数据。
- 备份频率、保留期、位置及已有工具实际状态待核实；复用可用工具，不因本次收敛范围擅自删除已有保护。

### 7.6 允许重大升级短暂维护

- 普通更新尽量不中断。
- 少数重大升级允许提前通知用户，安排短暂暂停全部或部分服务。
- 维护时间根据演练评估，不预设所有变更都能在几分钟内完成。
- 维护不代替备份和发布前验证。

### 7.7 已确认的发布闭环

1. 正式环境持续服务用户，正式数据库持续增长并定期备份。
2. feature 本地开发，成熟后合入 develop，在独立测试后端和测试库完成整合测试。
3. 功能测试通过后，在隔离环境还原正式数据库某一时刻的副本，执行本次准备上线的结构变更和数据转换脚本，再用新版后端及客户端验证历史记录和关键业务。
4. 演练可以复用测试环境，不要求永久增加第三套后端。重建测试数据前保全仍需保留的测试材料。
5. 演练通过后固定候选代码、迁移脚本和构建对应关系。后续相关修改应补充验证。
6. 由用户明确发令上线，按授权范围将候选合入 main，进行必要备份、数据库变更、程序部署及上线检查。
7. 正式库始终保留，副本生成后新增的真实数据留在正式库，由正式升级处理；不从测试库同步回来。

验证通过表示通过约定范围的检查，不保证不存在任何遗漏。真实最新数据上的迁移仍须遵循验证过的规则和发布顺序。

### 7.8 Codex 操作方式与授权

- 已确定工作方式：开发和测试尽量自动完成，正式上线由用户明确发令。
- 对用户明确交办的功能任务，后续按约定在 feature 开发验证，达到整合条件后进入 develop，交付测试结果供用户验收。
- 正式发令前应准备好具体候选、验证结果和发布范围，避免用户批准抽象动作。
- 2026-11-27 用户已明确授权实施本次结构改造与已确认范围的清理；不因用户此前授权不足而重复请求确认。正式产品上线仍须针对候选明确发令。
- 技术检查、用户体验验收和上线决定的分工已确认，见 6.1；具体用例与自动化实现随任务确定。
