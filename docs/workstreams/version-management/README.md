# 版本管理迁移需求与实施状态

用户确认：2026-11-27。目标是按现有已发布成果建立三层分支和独立测试环境，保持正式服务稳定。

完整讨论需求快照见 [requirements.md](requirements.md)。

## 已确定的需求

| 层次 | 正式用途 | 测试用途 |
| --- | --- | --- |
| 分支 | `main`，仅正式发布准备与修复 | `develop` 整合；`feature/*` 独立开发 |
| API / 后端 | 当前正式程序保持运行，明确发布时更新 | 长期一套独立测试后端，整合后部署 |
| 数据库 | 唯一权威用户数据，长期增长、定期备份 | 独立库，可重建、可导入正式快照；不回写正式 |
| 客户端 | 正式 App 和网站 | TestFlight 等测试包连接测试服务 |
| 发布 | 用户明确发令后进行 | 开发、必要检查、测试部署尽量自动完成 |

普通更新尽量支持旧客户端；重大接口或结构变化可以强制升级，但新版需先实际可安装。
正式上线前，将近期正式数据快照恢复进测试库，再演练候选迁移和关键功能。
正式发布是在现有正式库上迁移，绝不把测试库变成正式库，也不覆盖快照之后新增的用户数据。
保留简单的定期备份和变更前备份；按需短维护，不扩展成复杂自动回滚系统。

## 接续执行顺序

1. 在具备项目 SSH、Git 写入和仓库写权限的会话，使用本次提交或补丁；先核对远端仍基于记录的 main，若已有新提交则正常整合，禁止强推。
2. 运行 `scripts/audit-version-management-server.sh` 取得容器、镜像、卷、端口、项目目录和备份定时器实况。脚本只读，不输出环境密钥。
3. 核实当前生产镜像、挂载、数据库和备份；完成一份可校验的新备份后再清理旧服务器资源。已有备份机制能够满足要求则复用，不新增重复机制。
4. 为测试用途创建独立 Compose 项目、网络、数据库角色和数据卷；独立 Auth / Storage 也不可指向生产。复制数据前暂停测试后台任务，使用测试通知和支付配置，防止复制数据触发真实发送或扣款。
5. API 初始源码采用基线，与生产并行运行；功能变化由 develop 更新。具体容器名、端口、域名在实际检查后确定，不猜测现有配置。
6. 完成客户端本地状态隔离和在线验收脚本环境化。用快照恢复、迁移、登录、会员、学习记录、存储读写验证隔离；测试产生的数据不可进入正式系统。
7. 填写已验证测试环境配置，交付 develop 的 TestFlight 测试包。涉及 Apple / 微信的配置复用条件需要按真实身份服务验证。
8. 更新远端三层结构和规则，正常 PR 整合；清理确认无引用的旧分支和 worktree。不要把无权限或未检查的部分写成已完成。
