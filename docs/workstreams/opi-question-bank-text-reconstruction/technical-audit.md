# OPI 题库文本梳理与重建技术盘点

状态：已完成

更新时间：2026-07-17

## 1. 盘点目的

确认已确认的 `requirements.md` 能否在当前统一题库架构中安全实施，并明确正式执行前必须补齐的数据工具、质量校验、稳定卡片身份和发布边界。

本盘点只检查现状并形成技术结论，不修改 OPI 题库内容。

## 2. 总体结论

本项目已经具备统一题库维护源、构建脚本、发布产物、学习页和服务端题库接口，能够承载本次 OPI 文本重建。现有学习页也已经按独立字段显示“英文—分隔线—中文”，无需为目标展示效果重做 UI。

当前主要缺口不在页面，而在内容本身和内容级质量控制：现有校验只能确认 JSON、数量、ID 和资源结构，不能判断一卡多问、语义重复、话题错位、问答不匹配、中英混排或翻译失配。因此不能直接在 144 个话题文件中人工批量修改后发布，必须先建立可审查、可恢复、可重复验证的专用处理管线。

## 3. 当前权威数据与构建链路

### 3.1 权威维护源

OPI 正式维护源位于：

```text
content/question-banks/registry.json
content/question-banks/banks/opi/bank.json
content/question-banks/banks/opi/categories/*.json
content/question-banks/banks/opi/topics/*.json
```

维护规则已经明确：

- 只修改 `content/question-banks` 下的维护源。
- 不手工修改 `dist/question-bank-release`。
- 不手工修改 `src/features/question-bank/data/question-bank.json`。
- 已发布的 bank、category、topic、card ID 不得重新编号或挪作其他含义。
- 修改后通过 `pnpm content:build` 生成发布产物，再通过 `pnpm content:check:full` 对账。

### 3.2 当前发布结构

当前题库 registry 为 release version 6。OPI 使用统一的 bank、category、topic、card 层级，题目字段为：

```text
audioText       英文问题
audioTextZh     中文问题
referenceText   英文参考答案
referenceTextZh 中文参考答案
```

OPI 的 `audioMode` 为 `generated`。重建 `audioText` 后，系统会基于新文本生成朗读，不需要迁移旧 OPI 音频文件，也不需要修改播放器、录音器或音频生命周期。

## 5. 当前文本质量基线

对 1333 张文本问题卡进行只读扫描后，得到以下基线：

| 检查项 | 当前结果 | 说明 |
| --- | ---: | --- |
| 缺少中文问题 | 20 | 无法形成统一双语问题展示 |
| 英文问题字段含中文 | 1 | 中英文未分字段保存 |
| 问题包含斜杠备选表达 | 55 | 多数需要定稿为单一正式表达 |
| 包含至少两个问号 | 173 | 是拆分候选，不能按问号数自动拆分 |
| 包含至少三个问号 | 21 | 高优先级人工判断对象 |
| 疑似问号后粘连 | 5 | 存在基本格式问题 |
| 缺少英文参考答案 | 0 | 仅表示字段有内容，不表示答案有效 |
| 独立保存中文参考答案 | 64 | 其余大多仍把双语写在一个字段中 |
| 英文参考答案字段含中文 | 1261 | 当前答案结构与目标格式严重不一致 |
| 纯英文答案但无独立中文答案 | 8 | 中文答案覆盖不完整 |
| 带编号或版本式答案 | 89 | 与“一题一份最优答案”冲突 |
| 使用空行分段的答案 | 243 | 分段本身允许，需检查是否为自然段而非多版本 |
| 同话题完全重复问题 | 3 组 | 仍需从最佳版本原则处理 |
| 疑似依赖具体图片内容的问题 | 8 | 需要在图片专项前保持待定标记 |

已确认的同话题完全重复包括：

- 风切变：`opi-core-040` 与 `opi-core-047`。
- CRM 与机组协作：`opi-core-146` 与 `opi-core-369`。
- 颠簸：`opi-core-427` 与 `opi-core-433`。

这些统计是建立路线图和验收基线的依据，不直接等同于最终修改数量。例如，173 张多问号卡中既有必须拆分的独立问题，也有必须保留在一起的 `Yes/No + Why` 或依赖追问。

## 6. 现有校验能力与缺口

### 6.1 已有能力

`tools/question-bank-content.mjs` 当前可以验证：

- bank、category、topic、card ID 的全局唯一性。
- 声明数量与实际数量。
- JSON 结构和必填基础字段。
- 资源路径、资源清单和构建产物一致性。
- 维护源、发布目录和 App 内嵌题库之间的一致性。

### 6.2 尚不能验证

现有 schema 和构建检查不能判断：

- 一张卡片是否包含多个可独立回答的问题。
- 两道问题是否语义高度相似。
- 问题是否属于正确话题。
- 英文是否自然、完整、准确。
- 中英文是否混排或逐条对应。
- 参考答案是否真正回答最终问题。
- 参考答案是否包含多个编号版本。
- 航空知识、术语和处置逻辑是否可靠。
- 英文锁定后，中文或答案阶段是否反向改动了问题。

不能把 `audioTextZh`、`referenceText` 和 `referenceTextZh` 直接提升为全题库 schema 必填项，因为其他题库有不同展示和内容规则。本次应增加 OPI 专用的严格校验，而不是改变五套题库的全局字段要求。

## 7. 现有展示与功能影响

### 7.1 学习页

统一 OPI 学习页已经分别读取四个字段：

```text
audioText
分隔线
audioTextZh

referenceText
分隔线
referenceTextZh
```

因此本次目标可以通过规范数据达成。只有在最终真机或模拟器检查发现长文本、自然段或分隔显示异常时，才允许进入单独的 UI 缺陷修复，不把 UI 改造预设为本轮任务。

### 7.2 模拟考试

当前模拟考试仍使用静态示例，不从 OPI 正式题库抽题。本次无需迁移模拟考试数据，也不能以 `mockExamEligible` 字段推定已有运行依赖。

### 7.3 生成音频

OPI 问题使用生成音频。英文问题变更会自然进入新的朗读文本，但本轮不改变：

- 音频依赖或权限。
- 播放和录音会话。
- `AudioSessionOrchestrator`。
- 录音文件与转写触发机制。

## 8. 卡片 ID 与学习数据决定

卡片 ID 不只是展示编号。当前多个功能以 ID 或完整目标定位持久化数据：

```text
bankId + categoryId + topicId + cardId
```

受影响对象包括：

- 本地 SQLite 学习状态与完成进度。
- 云端 `user_card_states`。
- 学习记录同步版本键。
- 标签、笔记和单词高亮标注。
- AI 请求使用的 `questionId`。

如果要求保留既有数据，会存在以下风险：

- 删除重复卡会让旧卡的学习状态失去可见目标。
- 移动卡片会改变 topic 维度，旧状态和标注不能自动跟随。
- 拆分问题如果复用或重新编号旧 ID，会错误继承同一份进度。
- 大幅重写文本后，基于 `wordIndex` 的旧高亮可能落在错误单词上。
- 云端旧状态如果未经别名归一，可能在后续同步中重新写回旧目标。

项目负责人已经确认不需要保留任何 OPI 学习进度、笔记或高亮，有旧数据时可以按 OPI 范围清理。因此本轮不开发本地状态迁移、云同步归一、笔记合并或高亮重定位。

稳定 card ID 仍须保留，拆分、合并、移动和删除仍要生成完整目标映射，但映射只用于内容审计、ID 防复用和变更复核，不进入运行时兼容代码。环境中的实际数据清理由项目负责人在最终发布阶段执行；如涉及云端数据，仍按备份、范围核对和清理后验证规则处理。

## 9. 发布与运行环境边界

本地 App 使用构建后的内嵌题库；登录用户也可能从 API 获取当前激活的题库 release。服务端题库由 `services/api/scripts/import-content.mjs` 导入数据库中的 `question_bank_releases`。

由此得到以下边界：

- 本地内容重建和本地验收不要求修改 `services/api` 代码。
- 正式发布前需要递增 registry release version，并重新构建完整 release。
- 把新 release 导入 ECS 会改变线上数据，必须作为单独的发布步骤执行，不能在内容清洗过程中反复导入。
- 本轮路线图先以本地正式候选和 App 验收为终点；线上导入需在本地验收完成后单独确认并按部署规则执行。
- 本次不包含数据库 schema 迁移。若最终发布时发现云端存在旧 OPI 学习数据，可按已确认决定清理，但必须另行备份、核对 OPI 范围并验证清理结果。

## 11. 风险分级

### P0：必须在正式改源前解决

- 没有逐卡决策记录就直接覆盖 1333 张文本卡。
- 重排或复用已发布 ID。
- 拆分、合并、删除、移动后没有可审计的旧目标到新目标映射。
- 中文或答案阶段反向修改已锁定的英文问题。
- 未完成结构与内容校验就构建正式 release。

### P1：必须在正式发布前解决

- 中英字段混排、翻译缺失或段落不对应。
- 问答语义失配或航空内容不可靠。
- 高相似候选未经规则判断或抽样复核便自动删除。
- 图片依赖答案被猜测性补写，或者因答案延期而跳过问题清洗。
- 本地内嵌题库与 API 激活 release 不一致。

### P2：可在小批次迭代中优化

- 问题和答案的风格一致性。
- 简单题与复杂题之间的答案长度控制。
- 长答案在移动端的阅读密度。

## 12. 技术盘点结论

本次重建可在现有统一题库框架内完成，且无需先修改 UI、音频架构或 API 代码。正式执行需要新增四类能力：

1. 可冻结旧数据、生成逐卡工作项并记录所有决策的 OPI 专用工具。
2. 严格遵守四阶段锁定顺序的批次处理机制。
3. 覆盖语言纯度、字段完整、重复候选、问答对应和图片答案延期项的 OPI 专用校验。
4. 保留稳定 ID 和审计映射，并明确不开发旧学习状态与标注迁移。

具体实现方式见 `technical-plan.md`，执行顺序与阶段验收见 `roadmap.md`。
