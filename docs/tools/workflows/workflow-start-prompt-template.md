# 大流程 / 小流程启动 Prompt 模板

> 可选工作方法：仅在当前任务采用本流程时使用；不构成项目长期规则，不自动增加审批或扩大授权。入口见 [工作工具](../README.md)。

用途：把下面模板复制给一个全新的 Codex agent，用于启动一次新的中大型 workstream。

使用方式：

1. 替换 `【...】` 占位内容。
2. 如果任务只需要做大流程决策层，保留“先不要进入小流程”。
3. 如果需求、方案、路线已经确认，删除决策层等待确认部分，并明确“直接进入小流程”。

```text
项目路径：
【填写项目绝对路径】

任务名称：
【填写任务名称】

任务目标：
【用 3-8 条写清楚最终要解决什么问题、达到什么效果】

本次使用流程：
使用“通用大流程 + 通用小流程”。

必须先阅读：
- AGENTS.md
- docs/tools/workflows/document-driven-development-workflow.md
- docs/tools/workflows/orchestration-loop.md
- 【可选：项目内类似 workstream 的范例文档路径】
- 【可选：本任务已有草稿或旧文档路径】

建议工作目录：
docs/workstreams/【workstream-name】/

建议文档：
- requirements.md
- technical-plan.md
- technical-audit.md
- roadmap.md
- phase-log.md
- closeout.md

核心约束：
- 先从大流程第一步开始。
- 先完成决策层文档，再进入执行层。
- requirements.md 只写需求：目标、范围、模块要求、明确不做、验收效果。
- technical-plan.md 只写方案：怎么做、关键取舍、可选方案、不采用方案。
- technical-audit.md 只写真实项目现状、已有能力、缺口和风险证据。
- roadmap.md 只写阶段顺序、阶段目标、阶段产出、验收标准和进入下一阶段标准。
- 文档保持短而准，同一原则只写一次。
- 用户中途新增要求时，先分流到对应文档；如果影响已确认决策，暂停并说明要回到哪个决策层。
- 不能删除、迁移、覆盖重要数据或资源，除非路线图明确写入并经过人工确认。
- 新增生产依赖不得超出已确认方案的范围、成本或风险边界。
- 不提交、推送、部署，除非我明确要求。

大流程执行方式：
1. 问题登记：
   - 明确要解决什么问题。
   - 明确对象、范围、非目标、风险和暂停条件。
   - 旧文档只能作为参考，不能直接继承为最终结论。
2. 需求文档：
   - 生成 requirements.md。
   - 第一版只记录最核心、最明确的需求。
   - 写完后必须等待我确认需求。
3. 技术方案：
   - 需求确认后，生成 technical-plan.md。
   - 写完后必须等待我确认方案。
4. 技术盘点：
   - 方案确认后，做真实项目只读盘点。
   - 生成 technical-audit.md。
5. 技术路线图：
   - 生成 roadmap.md。
   - 每个阶段必须有目标、主要工作、产出、验收标准、暂不做、进入下一阶段标准。
   - 写完后等待我确认路线。

进入小流程条件：
- 只有当 requirements.md、technical-plan.md、technical-audit.md、roadmap.md 都完成，并且我确认需求、方案、路线后，才进入小流程。

小流程执行方式：
- 按 docs/tools/workflows/orchestration-loop.md 执行。
- 默认 Codex 自动推进，不反复询问我。
- Codex 是执行官，负责阶段规划、执行、审查、验证和必要记录。
- 只有触发暂停条件时才停下来问我。

每个阶段必须：
1. 读取需求、方案、盘点和路线图。
2. 定位当前阶段。
3. 自动做阶段规划。
4. 自动执行当前阶段。
5. 自动只读审查 diff。
6. 自动验证。
7. 必要时写入 phase-log.md。
8. 满足进入下一阶段标准时，自动继续下一阶段。

Agent 使用与成本控制：
- 默认主线程完成，不自动开启多个 agent。
- 只有子任务能并行、边界清楚、结果可快速复查，并且能节约时间或提高质量时，才使用子 agent。
- 子 agent 只接收当前阶段必要摘要、目标、禁止范围和相关路径。
- 子 agent 输出必须短，只写结论、改动文件、风险和验证结果。

批量处理规则：
- 大批量处理必须脚本化。
- 涉及外部 API、模型或子 agent 重复劳动时，必须先小样本验证，再分批扩大。
- 必须有缓存或可恢复中间结果。
- 约每 200-300 条做结构、规则和样本抽查。
- 模型或子 agent 输出不能未经校验直接写入正式数据。

验证要求：
- 文档-only 改动不需要构建。
- 只运行与改动直接相关的快速确定性检查，不默认运行全项目测试或全平台构建。
- 涉及 TypeScript 合同变化时运行类型检查；涉及具体模块时运行该模块的聚焦测试。
- 涉及 JSON / 数据整理时，必须做 JSON/schema/数量/引用一致性校验。
- 用户指定 TestFlight、目标 Release 包或线上环境时，完成必要检查后直接进入该最终验收环境，
  不默认串联模拟器、Development Build 和 Dev 真机。
- 涉及前台显示时，在用户指定的最终环境验收真实效果。
- 验证后检查 git diff，恢复与任务无关的生成物变化。

暂停条件：
- 需求文档没有覆盖的新决策。
- 技术方案与真实项目冲突。
- 路线图阶段顺序不合理或缺少关键阶段。
- 需要改变已确认的用户体验。
- 需要删除、迁移、合并或覆盖重要数据。
- 需要新增生产依赖。
- 需要提交、推送、部署。
- 需要外部账号、密钥、付费资源。
- 外部 API 调用范围、成本或风险扩大。
- 验证失败且修复会扩大范围。
- 发现用户或其他 agent 的未完成改动影响当前任务。

最终完成后：
1. 输出 closeout.md。
2. 总结完成了什么、验证结果、未做事项和剩余风险。
3. 如本次真实暴露了流程问题，再少量优化：
   - docs/tools/workflows/document-driven-development-workflow.md
   - docs/tools/workflows/orchestration-loop.md
4. 只写真实暴露的问题和改进，不做空泛扩写。

第一条回复应该做什么：
- 说明你会按大流程从问题登记和需求文档开始。
- 读取必要文档和相关旧资料。
- 不直接改业务代码或正式数据。
- 第一轮产出优先是新的 requirements.md 草稿，并请求我确认。
```
