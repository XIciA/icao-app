# 通用小流程：最小可验证执行循环

这是普通开发、修复、文档和局部优化的默认流程。

## 循环

1. **定目标**：确认用户要得到的结果、非目标和权限边界。
2. **查事实**：读取直接相关代码、配置、测试和少量当前文档；不遍历全部历史。
3. **找复用**：定位已有来源、共享模块、相邻实现和适用规则。
4. **选闭环**：选择能产生可验证进展的最小改动；复杂任务再写短计划。
5. **实现**：保持改动聚焦，保留无关用户修改，不建立平行来源。
6. **验证**：按 `docs/engineering/verification-matrix.md` 运行与风险匹配的检查。
7. **审查**：查看差异、生成物、引用和用户可感知状态。
8. **记录**：只更新后续需要的当前事实、决策、阶段状态或事故证据。
9. **继续或交付**：若安全且仍有明确闭环则继续；满足目标后交付结果和风险。

## 自主执行边界

在已知产品与架构边界内，Codex 可自主决定局部实现、重构顺序、测试选择和可逆修复。
以下情况需要用户决定或新的明确授权：

- 产品范围或设计方向发生实质变化；
- 数据删除、迁移、付费、隐私或其他不可逆风险；
- 生产部署、对外发布、提交/推送或外部消息不在当前任务范围；
- 多个方案会产生明显不同的用户结果；
- 需要覆盖或丢弃无法安全绕开的用户修改。

## 文档尺度

- 简单任务不创建 workstream、phase log 或 closeout。
- 中等任务可以只维护一份短任务文档或现有 phase log。
- 只有符合大流程进入条件时才建立完整阶段资料。
- 历史档案、开发者笔记和未被选中的 workstream 不自动成为执行要求。

## 完成标准

- 请求的结果已实现；
- 直接受影响的路径已验证；
- 无已知第二来源、明显回归或未说明的高风险；
- 必要的当前文档与实现一致；
- 最终报告明确说明结果、验证和任何未覆盖范围。
