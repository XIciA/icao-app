## 1. 结论

现有 React Native + Expo SDK 55 + TypeScript、NestJS API、PostgreSQL/Drizzle 和自托管 Supabase
可以承载正式商业化，不需要重写客户端或更换后端技术栈。账号会话、多设备同步、题库发布、私有
资源签名、AI 调用、反馈、双端签名和 Release 校验已经提供了可复用基础。

在本文启动盘点时，实现仍是“邀请码内测产品”，不能通过补几个购买页面直接上线。当时的正式
商业化主要阻断项是：

1. 正式身份仍依赖邀请码，API 也会拒绝非邀请码账号；
2. 缺少手机号 OTP、短信风控、年龄与协议版本记录；
3. 同步缺少服务端数据代次，清除学习数据后旧设备仍可能回灌；
4. 没有商品、订单、渠道交易、权益、退款和 AI 点数账本；
5. Native 安装包仍内置约 6 MB 完整题库，登录账号也能获取整库正文和所有资源签名地址；
6. AI 当前只记录旧 `quotaUnits`，没有用户点数预占、结算、真实成本、并发锁和全局熔断；
7. 注销流程仍用邀请码复核，且没有处理订单、权益、点数和法定留存隔离；
8. 没有管理员/客服后台、审计日志、自动保留期清理和商业监控；
9. Android Build Tools 与 `apkanalyzer` 当前缺失，无法完成最终 Android Release 验收；
10. Vercel 若仍保持 Git 自动生产部署，后续仓库提交可能违反“网页冻结”要求。

因此正确路线是先建立服务端商业领域模型和原生/Web 隔离门禁，再替换身份、内容和 AI 授权，最后
并行接入 iOS 与 Android 支付渠道，而不是按 D1—D9 的讨论顺序逐页开发。

## 3. 当前可复用能力

### 3.1 账号与会话

- `src/features/auth/` 已有安全会话存储、自动刷新、登录恢复、当前/全部设备退出和账号切换隔离。
- `services/api/src/auth/` 已有 JWT 验证、会话撤销和统一 Guard。
- 启动盘点时 Supabase `auth.users.id` 是学习、AI、反馈和同步数据的统一用户 ID；新 D2 只把它保留为
  认证身份 ID 和既有账号兼容回填值，正式业务归属改为永久 `accountId`，不能继续假定两者始终相等。
- 启动盘点时 `RequireAuthGuard` 在验证 JWT 后还强制检查 `invite_accounts`；本地候选现已改为验证合法
  会话并解析活跃 `accountId`，邀请码和手机号都不再是普通业务 API 的硬门槛。

#### D2 双登录覆盖更新后的本地审计

本节是 2026-08-12 对新 D2 的增量审计，不改变上文作为启动前快照的性质：

- 仓库锁定 `@supabase/supabase-js 2.110.2`。官方 API 已支持 `signInWithPassword({ phone,
  password })`、已登录用户 `updateUser({ password })`，以及 `signInWithOtp` 的
  `shouldCreateUser=false`，因此无需更换 Auth 产品或建立第二账号体系；
- `src/features/auth/auth-service.ts` 已实现现有账号 OTP、OTP 优先注册、重发、验证码校验、手机号密码
  登录和同会话更新密码；Native 登录页已提供双入口、真实倒计时、注册、找回和错误状态，账号安全页
  已提供首次设密/修改/重置页面；
- 当前本地 API 要求合法且未撤销的 token，并将认证身份解析为活跃 `accountId`；不把手机号、OTP 或
  password 写死为普通业务授权条件，符合多入口账号要求；
- 新增的阿里云链路由 Supabase Send SMS Hook 调用 NestJS，服务端验证 Standard Webhooks 原始签名、
  规范化 `+86` 手机号后调用官方阿里云 SDK，日志不记录完整号码或 OTP；关键配置缺失时失败关闭；
- 基础 Supabase override 仍关闭公开注册；TestFlight overlay 只打开 phone signup 和可到期的白名单测试
  OTP，阿里云 production-style overlay 与它互斥。启动盘点时两者均未部署；此后真实阿里云链路已由
  当前 TestFlight 验证可达，但测试 OTP 与真实发送仍必须保持互斥；
- 当前基础预算/号码限额和 Hook 重放记录位于单 API 进程内，重启会清空且多实例不共享；Send SMS Hook
  本身也不含设备/IP 上下文。正式多实例或公开用户前必须使用 Redis/数据库持久化计数，并在请求入口
  增加设备/IP 风控和告警；
- 当前注销按负责人此前要求采用简单确认，未实现手机号 OTP/近期密码重认证。它可用于当前本地技术
  预览，但不满足正式双登录的敏感操作安全门槛，需在 D2 后续阶段补齐。

因此当前下一步是评审并演练永久账号迁移，完成 Apple 的新发布描述文件/Supabase 配置与微信开放
平台配置，在隔离环境验证多身份解析、手机号绑定和冲突归并，再生成新双端构建。短信继续使用已审核
且真实收件的“云启航科成都”，仍需补三网到达和多实例共享风控；“听你五个”因当前没有注册商标且
不满足平台来源要求而延期。手机号 OTP 与密码必须继续解析到同一 `accountId`。

### 3.2 多设备同步

- 已有服务端版本、增量 cursor、幂等 mutation、账号归属检查和客户端离线 outbox。
- 当前支持题卡状态、学习记录、标注/笔记文档和词汇文档；原始录音没有进入同步链路，符合 D3。
- 客户端已有切号时停止旧身份同步的 `identityEpoch`，可以继续作为端侧防串号机制。
- 服务端没有 account-level `dataGeneration`，也没有全量清除 API。客户端本地清空并不能阻止长期离线
  设备携带旧 outbox 重新写入，必须在服务端补齐代次。

### 3.3 内容发布和资源

- `content/question-banks/`、生成工具、release checksum 和稳定内容 ID 可以继续作为唯一内容来源。
- `question_bank_releases`、`resource_objects`、ETag 和 Supabase Storage 签名 URL 可以扩展，不需要
  建立第二套题库或资源表。
- 当前 `src/features/question-bank/data/question-bank.json` 约 6 MB，并被 Native repository 作为
  fallback 静态导入；这会把完整会员内容编入正式包。
- 当前 `/v1/question-banks/:bankId` 向任一有效邀请码账号返回整个题库；`/v1/resources/resolve` 仅按
  路径存在性签名，没有免费/会员/内容范围授权。

### 3.4 AI

- AI 同意、供应商适配、取消信号、请求日志、模型/提示版本和临时录音清理已有可用基础。
- `ai_usage_logs` 的唯一键只能避免重复写日志，不能避免重复调用供应商；调用发生在日志落库之前，
  重试或并发仍可能产生重复成本。
- `ai_quota_buckets` 是旧的日期桶，不表达用户可见点数、会员批次、累计有效期或退款；不能直接改名
  冒充新点数账本。
- 当前 `costMicrounits` 没有实际结算，模型价格、音频秒数和预占成本尚未形成完整账本。

### 3.5 构建与发布

- iOS/Android 已有独立 Release 脚本、正式运行时检查、旧域名拒绝、签名校验和音频敏感变更门禁。
- iOS 已有个人 Team 真机 Release 冒烟基础，但公司 Team、App Store Connect 商品和正式提交尚未
  就绪。
- Android 正式签名元数据已准备，但当前机器没有 Android SDK Build Tools 和 `apkanalyzer`，所以
  不能把“生成过备案预填字段”当作“最终 APK 已验收”。
- 当前发布脚本会拒绝脏工作树；实施完成后需要形成可审查的干净发布提交，不能携带无关用户改动。

## 4. 必须新增或重构的领域

### 4.1 正式账号

保留 Supabase Auth：手机号 OTP/密码、Apple ID Token 和微信会话桥接各自产生可验证认证身份，再由
映射层解析到同一永久 `accountId`。当前本地已实现 Native OTP/密码双登录、首次设密/修改/短信找回、
多入口候选、阿里云发送适配和 Hook 验签；阿里云外部资质、现用签名/模板及代表号码真实发送已完成，
仍需完成 Apple/Supabase 与微信平台配置、生产迁移、持久多实例限流/幂等、设备/IP 风控、三网、
手机号换绑、敏感操作重认证和正式账号状态。邀请码已退出 Native App 和 API 认证链路，但历史表暂不
在同一迁移中破坏性删除。

### 4.2 商业账本

必须新增服务端权威的商品、渠道商品、订单、支付事件、权益事件和当前权益投影。客户端只展示服务端
状态，Apple/支付宝/微信的“客户端支付成功”不能直接延长会员。

权益必须按订单顺序累计，支持重复购买、退款重算和跨 iOS/Android 恢复。交易原始证据与用户可见
订单分层保留，注销不能删除法定必须留存的隔离记录。

### 4.3 AI 点数与内部成本

点数使用不可变流水和余额投影；会员点数批次与31天权益段绑定。内部人民币成本使用独立微单位流水，
不能从用户点数反推或向用户展示。每个 AI 操作需要统一的预占、执行、结算、失败释放和幂等状态机。

具体免费点数、各套餐批次点数和各能力扣点仍是唯一未锁定的核心商业参数；数据结构和测试可以先按
版本化配置完成，但正式商品和用户文案不能使用临时值。

### 4.4 内容授权与离线

同一题库来源生成：公开目录/免费正文、会员内容包和资源访问映射。Native 不再导入整库 fallback，
但冻结的 Web 继续读取现有 Web 来源。会员下载、缓存密钥、离线凭证和本机索引按账号隔离；服务端
凭证最长72小时且不越过会员到期时间。

### 4.5 隐私、注销与运营

需要统一注销编排、保留期清理、数据导出、学习数据清除、AI 结果删除、第三方清单、第一方最小事件、
工作人员账号、管理员/客服权限和不可删除审计日志。内部后台必须独立于用户 App 和冻结的 Vercel。

## 5. Web/Vercel 冻结风险

冻结不是“暂时不点部署”这么简单。仓库同时包含 Expo Web 和 Native 共享代码，如果直接改共享路由、
repository 或组件，未来任何一次误部署都可能改变网页。实施前必须建立以下边界：

- 不修改或执行 `vercel.json`、`api/`、Web 物化脚本、Web 发布脚本和现有 Web 专属模块；
- 商业化 UI、身份、支付、内容授权优先放入 `.native`、`.ios`、`.android` 模块；冻结的 `.web` 实现
  保持原行为；
- 为 Web 拥有文件和当前生产部署标识建立冻结清单，CI/发布检查发现变化立即失败；
- 禁止运行 Vercel preview/production 发布，禁止把内部运营后台部署到现有 Vercel 项目；
- 负责人需在 Vercel 控制台确认 Git 自动生产部署已停用或生产版本已固定，否则 Git push 本身仍可能
  触发线上网页变化。

公司 App 法律页、Android APK 下载和内部后台如果需要公开 URL，应使用与现有 Vercel 项目隔离的
独立托管与域名，并分别获得外部操作授权。

## 6. 外部依赖和人工前置条件

以下工作无法仅靠仓库代码完成：

- 阿里云国内短信服务、签名、验证码模板和余额；
- Apple 公司开发者团队、付费协议、税务/银行信息、IAP 商品和 App Store Server API 密钥；
- 支付宝开放平台移动应用与 App 支付签约；
- 微信开放平台移动应用、微信支付商户号、AppID 绑定、APIv3 密钥/证书；
- App 备案主体核验、短信核验和备案号；
- 异机/对象存储备份资源、DNS、证书和告警联系人；
- 隐私政策、用户协议、商标/内容授权和 AI 合规材料的负责人终审；
- 生产数据库迁移、ECS 发布和最终商店提交授权。

完整拆分见 [人工事项清单](manual-actions.md)。外部账号未就绪时，代码仍可通过本地适配器、模拟通知、
StoreKit 配置和沙盒环境继续开发，不应让整个工程停在等待账号阶段。

## 7. 风险排序

| 等级 | 风险 | 处理原则 |
| --- | --- | --- |
| P0 | 完整会员内容进入安装包或任意账号可整库下载 | 支付上线前先完成内容拆分和服务端授权 |
| P0 | 客户端支付结果直接发权益、通知重放或跨用户串单 | 全部渠道只写入统一服务端账本，唯一键幂等 |
| P0 | 旧同步队列在清除/注销后恢复数据 | 服务端 `dataGeneration` 拒绝旧代次 |
| P0 | 点数重复扣、供应商重复调用、预算无限消耗 | AI 操作状态机、数据库锁、点数/成本预占和全局熔断 |
| P0 | 仓库提交触发 Vercel 生产变化 | 外部关闭自动部署 + 仓库冻结门禁 |
| P1 | 同机备份随 ECS 一起丢失 | 上线前恢复异机或对象存储加密副本并演练 |
| P1 | 短信轰炸、撞库和号码枚举 | 多维限流、统一错误、模板审核、发送预算和告警 |
| P1 | 退款误伤其他重复购买订单 | 不可变订单事件 + 按有效订单重算投影 |
| P1 | 注销删除法定交易证据或反向恢复旧账号 | 活跃数据删除与隔离留存分层 |
| P1 | 内部后台越权或无审计 | 独立工作人员账号、MFA、最小权限、强审计 |

## 8. 实施前的技术门槛

进入代码阶段前应满足：

1. [技术方案](technical-plan.md) 和 [路线图](roadmap.md) 获得负责人确认；
2. 现有工作树改动被完整识别，商业化改动不得覆盖无关用户修改；
3. Vercel 生产自动部署状态由负责人确认，仓库建立 Web 冻结基线；
4. 所有数据库变化先生成迁移和回滚/前滚方案，不直接操作生产；
5. 支付、短信和 AI 密钥只进入受保护环境，不写入仓库、日志或聊天；
6. 未取得外部账号时使用模拟/沙盒继续，只有对应真实渠道验收项保持待完成。
