# RN 与 Web 手机端 1:1 对照复刻路线图

状态：阶段 1–9 已完成
更新时间：2026-07-11

## 1. 执行原则

本路线图采用“大流程负责决策、小流程负责执行”：

- 本文确认前，不开始截图采集和 RN 改造；
- 确认后，Codex 按阶段自动推进，不反复请求已明确范围内的确认；
- 每阶段只做最小可验证闭环，逐状态关闭差异；
- 设计稿仓库始终只读；
- 不提交、不推送、不发布，除非用户另行明确要求；
- 触碰需求、宏观架构、原生允许差异或新增产品能力时，暂停回到大流程。

## 2. 阶段总览

| 阶段 | 目标 | 核心产出 | 进入下一阶段标准 |
| --- | --- | --- | --- |
| 0 | 冻结基线与保护现场 | 双仓库基线、目录、设备与验证约定 | 基线可追溯，现有改动受保护 |
| 1 | 全量发现 Web 页面状态 | `state-inventory.md`、首版矩阵 | 全部页面族和可见状态有稳定 ID |
| 2 | 校验并采用既有 Web 金标准 | `docs/records/evidence/ui-screenshots/2026-07-11/` 覆盖检查 | 截图库可直接驱动 RN 对齐 |
| 3 | 校准 RN 视觉原子件 | 共享令牌、组件与三类标杆页 | 标杆页对齐且不破坏原生能力 |
| 4 | 对齐主导航与题库首页 | 题库/发现/我的壳层与课程选择 | 三主 Tab 和首页状态全部关闭 |
| 5 | 对齐题库学习核心闭环 | 目录、学习卡、工具、报告、记录 | 五题库核心状态和轨迹全部关闭 |
| 6 | 对齐发现与内容流程 | 单词、随身听、内容、热点、模考 | 发现页面族全部关闭 |

| 9 | 收口 | `phase-log.md`、`closeout.md` | 文档与真实工程一致，可进入后续阶段 |

## 3. 小流程通用闭环

阶段 3–7 中，每个页面状态组必须执行同一闭环：

```text
读取 stateId 和 Web 证据
-> 读取既有 Web 标准图和记录的操作轨迹
-> 定位 RN 路由、组件与数据状态
-> 实现最小视觉/交互改动
-> 同步修复当前页面可确定的简单逻辑错误
-> 生成 RN 同状态截图
-> 生成并列/叠加差异图
-> 重放交互、返回与恢复
-> 运行相关测试和 pnpm check
-> 更新矩阵为 aligned / native-exception / needs-fix
-> 当前状态组全部关闭后进入下一组
```

任何状态不得仅因路由可进入或功能可用而跳过截图与操作轨迹验收。

## 4. 阶段 0：冻结基线与保护现场

### 目标

建立可追溯、可恢复且不覆盖现有工作区改动的执行现场。

### 主要工作

- 记录 Web/RN 提交、分支、Git 状态、依赖版本和关键数据散列；
- 确认 Web 基线提交为执行时仍有效的设计源；
- 建立 workstream 证据目录、状态文件 schema 与命名规则；
- 记录 RN 当前未提交改动，划定本 workstream 可修改路径；
- 确认本地 Web、iOS 375 × 812 对照模拟器和现有 iPhone 真机条件；
- 定义截图裁切、系统 UI 排除和原生例外记录方式。

### 验收标准

- 双仓库基线信息完整；
- Web 工作树保持只读且干净；
- RN 既有用户改动没有被覆盖；
- 目录、状态 ID、截图命名和设备基准可直接用于阶段 1。

### 暂不做

- 不采集全量截图；
- 不改 RN 视觉或业务代码。

## 5. 阶段 1：全量发现 Web 页面状态

### 目标

把 Web 的路由、Flow、弹层与数据状态转成完整状态清单。

### 主要工作

- 扫描六个顶层页面，排除 `/curriculum`；
- 盘点 AppShell、AuthFlow、AccountFlow、InfoFlow、StateFlow；
- 盘点题库、单词、随身听、内容、模考、标注和记录中的交互状态；
- 为每个状态分配 `stateId`、优先级、前置条件、操作步骤和 RN 候选承载；
- 建立 `state-inventory.md` 和 `parity-matrix.md`；
- 对重复状态合并，对视觉或返回结果不同的状态拆分。

### 验收标准

- 需求范围中的每个页面族均有状态；
- 每个可见弹层、选择器、校验、加载、失败和完成状态均有记录；
- 清单能由浏览器实际进入，不含仅从代码猜测的虚构状态；
- 不存在“后续再看”的无归属页面。

### 暂不做

- 不改 RN；
- 不因发现差距而提前修复。

## 6. 阶段 2：校验并采用既有 Web 金标准

### 目标

确认现有 `docs/records/evidence/ui-screenshots/2026-07-11/` 可作为 375 × 812 Web 视觉标准，不重复截图。

### 主要工作

- 校验 PNG 数量、尺寸、目录结构与 `manifest.json`；
- 将截图目录映射到 `state-inventory.md` 和 RN 页面族；
- 标记已有截图覆盖、截图缺口和明确排除项；
- 后续 RN 截图沿用标准库目录语义与文件名。

### 验收标准

- 已有 375 × 812 PNG 可正常读取；
- 核心页面、Flow、题库、单词、随身听和状态页均有标准图；
- 截图缺口被明确记录，不复制或重新生成第二套 Web 截图库。

### 暂不做

- 不改 Web；
- 不重新执行 Web 截图任务。

## 7. 阶段 3：校准 RN 视觉原子件

### 目标

先消除会扩散到全项目的字体、间距、导航、卡片与弹层差异。

### 主要工作

- 选取题库首页、认证页、题库学习卡三类标杆状态；
- 对齐画布、背景、环境光、字体、颜色、间距、圆角、边框和阴影；
- 对齐 Screen、AppText、Card、Button、Tag、TextField、TopBar、FloatingTabBar、BottomSheet；
- 补齐通用 Popover/Dialog/固定底栏等必要原子件；
- 建立 RN 截图裁切和差异图生成方式；
- 重跑现有组件和核心路由测试。

### 验收标准

- 三类标杆状态无未解释的结构和视觉差异；
- 通用组件可复用，不需要每页重复硬编码同一视觉规则；
- 原生安全区、返回、键盘、音频和录音能力没有退化；
- `pnpm check` 通过，相关 Development Build 可运行。

### 暂不做

- 不批量修改全部页面；
- 不接第二阶段服务。

## 8. 阶段 4：对齐主导航与题库首页

### 目标

关闭用户进入 App 后最先看到的结构性差距。

### 主要工作

- 题库首页：用户入口、课程选择器、选择列表、模块筛选、卡片和状态标签；
- 发现首页：功能网格、资源列表、课程强调卡和滚动关系；
- 我的首页：资料卡、统计、菜单、底部导航与返回恢复；
- 三 Tab 的选中态、按压态、安全区、滚动保留和全屏详情返回；
- 375 基准及 360/390/430 宽度检查。

### 验收标准

- 主导航页面族的全部状态为 `aligned` 或有明确原生例外；
- 课程选择会产生与 Web 相同的模块列表和可见状态；
- Tab/详情返回后页面和选中状态一致；
- iOS 基础冒烟通过；本 workstream 不执行 Android 模拟器测试。

## 9. 阶段 5：对齐题库学习核心闭环

### 目标

完成产品最核心、状态最密集的题库与学习体验 1:1 对齐。

### 执行切片

1. 五题库目录、分类、题组、模块切换；
2. choices 学习卡、音频、原文/译文、答案与翻卡状态；
3. speaking / retell、录音、回放、重录与权限结果；
4. 工具选择、查词、标签、高亮、笔记、答题卡；
5. 退出确认、完成/中止报告、失败与重试；
6. AI 查词、口语反馈等未接复杂能力的完整示例 UI 与可替换状态；
7. 学习记录、我的标注和原题回跳。

### 验收标准

- 五题库共享架构保留，没有复制五套页面；
- 每类学习交互和所有弹层状态均有 Web/RN 对照证据；
- 真实音频、录音、SQLite 保存和恢复继续通过；
- 核心轨迹“题库 → 目录 → 学习 → 报告”在 iOS 真机通过；
- `pnpm check`、相关原生构建和回归测试通过。

### 暂不做

- 不接真实 AI、云同步或上传录音；
- 不改题库内容和资源结构。
- 不用通用占位页替代 Web 已有的 AI/复杂功能设计流程。

## 10. 阶段 6：对齐发现与内容流程

### 执行切片

1. 单词选择、详情、词表、学习、测试、完成；
2. 随身听题库下拉、播放器、进度、模式、速度、字幕、播放列表抽屉；
3. 文章、资源、课程列表与详情 Sheet；
4. OPI 热点列表、详情与题库跳转；
5. AI 模考设置、进行、退出、加载/失败与演示报告，使用明确标注的稳定示例内容。

### 验收标准

- 发现页面族全部状态完成对照；
- 随身听真实音频能力与 Web 视觉/交互同时成立；
- mock 能力提示与 Web 用户认知一致；
- 暂未接入的复杂功能具备完整可替换 UI，不伪装为真实服务结果；
- 返回、Sheet、抽屉和长页滚动状态通过。

## 11. 阶段 7：对齐认证、账户、信息与状态

### 执行切片

1. AuthFlow 七个主状态及表单校验；
2. AccountFlow 九个主状态与退出 Dialog；
3. InfoFlow 六个主状态及协议返回来源；
4. StateFlow 八个主状态及重试/关闭结果；
5. 键盘、系统权限、系统设置与原生返回适配。

### 验收标准

- 四组 Flow 的所有状态均有 RN 对应项；
- 表单、Dialog、协议返回和状态重试轨迹一致；
- 真实权限入口只在原生例外范围内产生差异；
- 未接服务继续明确为演示或待接入。
- 当前页面范围内可确定的简单逻辑错误已经修复并有操作轨迹证据。

## 12. 阶段 8：全量回归与 iOS 验收

### 目标

验证单页对齐没有引入跨页面、跨尺寸和原生能力回归。

### 主要工作

- 重放全部 P0/P1 操作轨迹；
- 检查所有状态的 Web/RN 截图、差异图与结论；
- 全量检查 375，代表长文本/表单/弹层补查 360/390/430；
- iOS 真机验证核心学习、音频、录音、返回、键盘和生命周期；
- 不启动或使用 Android 模拟器；如共享代码涉及 Android 原生配置，只保留必要的非模拟器构建检查；
- 运行 `pnpm check`、Doctor、三平台导出和相关原生构建；
- 扫描 WebView、DOM、浏览器存储等越界实现。

### 验收标准

- 没有 `needs-fix` 的 P0/P1 状态；
- P2 状态没有未记录差异，延期项有用户确认；
- 所有原生例外有证据且不改变 App 内容体验；
- 工程、测试、构建和真机门禁通过；
- Web 设计稿工作树无变化。

## 13. 阶段 9：收口

### 主要工作

- 更新 `phase-log.md`；
- 生成 `closeout.md`；
- 汇总状态覆盖率、关闭差异、允许原生差异、设备和验证结果；
- 更新原第一阶段执行文档中已被本 workstream 修正的视觉验收结论；
- 复查总战略、架构决策和 Git diff。

### 完成标准

- 需求文档的最终验收效果均有证据；
- 文档与真实代码、截图和设备状态一致；
- 当前 Web 的每个纳入页面状态均能在 RN 中找到对照结果；
- 后续功能开发可以在已对齐视觉基础上继续，而不需要重新做页面结构。

## 14. 路线门

用户确认本路线图后，四份大流程文档视为完成，Codex 可进入阶段 0 并按小流程自动推进。若用户要求调整范围、顺序、平台验收或截图标准，应先更新对应大流程文档，再启动执行。
