# Web 三类题库优化与增量迁移技术方案

状态：已确认，已完成

更新时间：2026-07-15

## 1. 方案结论

本任务采用“Web 只读候选池 → 可解释去重 → 规则化决定冻结 → 条件式增量写入”的独立工作流，不把 Web 数据整库覆盖到 App，也不重新处理 App 现有题目。不中途等待试审；难判但可用的候选保守迁移，全部完成并上线后再集中提供人工审核清单。

执行开始时的正确来源包含 2288 条候选：`banks/` 2251 条和 `quarantine/` 37 条。当时尚未执行与 App 的全量内容去重，因此方案没有预先猜测净新增数量。执行中排除确定重复候选，难判的中间相似区间采用保守保留并记录，最后集中人工审核，不作为中断执行的闸门；实际结果见阶段日志和发布报告。

## 3. 独立迁移工具

迁移工具为 `tools/web-question-bank-content-migration.mjs`，按以下阶段提供可恢复命令：

- `audit`：读取两端数据和资源，生成基线、候选清单及重复证据，不写正式题库。
- `prepare`：只为已批准的唯一候选生成规范化后的待迁移数据、分类和资源计划，不写正式题库。
- `translation-status / verify-translations / merge-translations`：校验并合并全部缺失中文，不使用 ASR 或外部 API。
- `final-dedupe`：在全部批次完成后，重新执行跨批次、跨目录和 App 全局去重，并刷新最终映射。
- `stage-formal / verify-staged`：按三库生成正式候选并验证，不修改正式题库。
- `apply-formal / verify-formal`：仅写入最终保留候选，失败自动恢复写入前快照。
- `build-release / verify-release`：生成并验证只包含三库和新增资源的增量发布包。

计划生成以下工作记录：

```text
docs/records/workstreams/web-question-bank-content-migration/
├── snapshots/          # App 与 Web 的只读基线摘要
├── reports/            # 候选、重复、资源和验证报告
└── decisions/          # 每个候选的最终处理决定及理由
```

生成文件采用稳定排序，重复执行 `audit` 不应产生无意义差异。

## 4. 候选识别与去重方法

### 4.1 多层证据

去重不能只看编号或单一相似度分数，按以下证据组合判断：

1. 稳定 ID 或可追溯源 ID 是否相同。
2. 删除纯展示差异和明确正文外标签后，核心英文文本是否相同。
3. 音频文件哈希是否相同；哈希不同只表示录音文件不同，不自动证明题目不同。
4. 听力题的问题、四个选项、正确答案和考点是否相同。
5. 陆空通话的任务文本、参考回答、呼号、飞行阶段和指令意图是否相同。
6. 故事复诵的正文事件、信息顺序和复述价值是否实质相同。

用于比较的规范化只忽略不影响语义的差异，例如大小写、普通空格、常规标点、说话人标签形式、三字呼号展示形式，以及已确认的 `(14 words)` 等正文外标签。它不能删改数字、单位、专名、否定词或事件内容。

### 4.2 结果状态

每个 Web 候选只能进入以下一种技术状态：

- `migrate-unique`：明确是净新增且满足迁移条件。
- `borderline-kept`：相似度处于中间区间，无法可靠证明重复；包括因关键事实不同而受到保护的高相似候选。保守迁移，并进入最终人工审核清单。
- `exclude-exact`：核心题目内容完全重复；理由中进一步记录稳定 ID、内容签名或音频证据。
- `exclude-high-confidence`：表面有差异，但在关键事实一致的前提下满足题型专属严格门槛，学习内容与考点没有独立价值。
- `exclude-invalid`：客观缺少必要字段、音频缺失/损坏，或只是一张不能独立学习的说明卡。

完全重复可以由确定性证据排除。高相似度分数只用于排列复核优先级，不能单独决定删除；必须记录相同考点和缺乏独立价值的具体证据。呼号、数字、跑道后缀、高度、航向、频率或单位不同构成关键事实保护，不允许自动排除。中间相似区间进入 `borderline-kept`，不暂停任务。

## 5. 三类题型的比对重点

### 5.1 听力

- 以“音频原文和问题 → 四个选项 → 正确索引 → 参考答案”为一个不可拆分的答题链路。
- 同一段内容即使使用不同录音，只要问题和考点相同，仍视为重复题。
- 独立候选必须归入现有四类。先判断内容形态：飞行员与管制员往返、标准通话交互归“陆空通话”；单人陈述、解释、广播或事故叙述归“航空英语”。
- 再模糊判断长短：约 18 秒以下优先为 `10s`，约 20 秒以上优先为 `20s`；18–20 秒标记 `duration-borderline`，以 19 秒作为确定性兜底分界并保留实际时长供集中复核。
- Web Stage 只作为来源追溯，不作为分类映射。
- 不以 ASR 重识别音频，不使用历史 Whisper 结果推翻现有文本。

### 5.2 陆空通话

- 以任务文本、标准回答、呼号、场景阶段和关键指令组合比对。
- 同一组文本的替代录音不作为新题迁移，可在报告中记录为可选资源但不进入活动题库。
- 独立候选按现有三字呼号分类，并加入对应场景；未知呼号必须人工确认，不能自动新建航司分类。
- 说明卡、字母或数字发音说明、学习操作提示不作为陆空通话卡片迁移。

### 5.3 故事复诵

- 先从混合字段中分离英文正文、中文译文和正文外标签，再比较英文故事主体。
- `Story 12`、`(145 words)`、来源备注等不参与正文相似度，也不能进入最终正文。
- 去重范围覆盖 Web 144 个候选内部和 App 四个故事子库的全部 296 道现有题，不能只与目标子库比较。
- 同一故事的标点、分段或翻译差异不构成新题；情节近似但可能有独立复述价值时由人工决定。
- 所有最终保留的 `migrate-unique` 与 `borderline-kept` 故事统一写入现有 `story-flight-basic`，即“飞行 ICAO → 基础题库”；其他三个故事子库只作为全局去重基线，不接收本轮新增。
- 写入后再次对四个故事子库和本轮新增集合执行全局重复检查，防止两个 Web 候选相互重复后同时进入题库。

## 6. 文本规范化与翻译补全

规范化发生在迁移候选冻结之后，不对全部 Web 数据或 App 现有数据批量重写。

- 只执行当前文本规范中的确定性展示规则，例如空格、标点、说话人标签、民航字母、三字呼号、进离场短线及 `Runway 36R`。
- 删除能明确识别的正文外内容，例如 `(14words)`、篇号、词数、来源备注和重复首尾标签。
- 混写的中英文拆入对应字段，但保持原句信息和顺序。
- 不润色、不纠正语法、不改数字、专名、航向、高度、频率、跑道、单位或事实。
- 自动工具不使用外部翻译 API。仅对确定迁移且缺失翻译的候选，由 Codex 依据现有英文补译并执行结构、术语和关键事实复核；不在中途等待用户逐题确认。
- 已有完整翻译不做风格性重译；不确定专名进入人工复核。
- 全程不使用 Whisper、其他 ASR 或外部翻译 API。

## 7. 分类、ID 与资源写入

- 听力只写入现有四个题组；陆空通话沿用现有航司和场景；故事复诵新增统一写入 `story-flight-basic`。
- 源 ID 未冲突且符合现有规则时优先保留。ID 冲突但被确认内容不同的候选，使用可追溯、确定性的命名空间 ID，并记录映射。
- 任务标题按目标题组现有自然顺序生成，不重排或重命名旧题。
- 只复制 `migrate-unique` 与 `borderline-kept` 候选所需的有效音频到 App 规范资源位置，并更新唯一映射。
- 已存在的同一资源不重复复制；替代录音不因文件哈希不同而自动进入题库。
- 正式源写入完成后才运行内容构建，刷新内嵌题库。
- 输出完整 `Web 源 ID → App 新 ID → 目标目录 → App 音频路径` 映射，所有新增题必须能够双向追溯。

## 8. 写入保护与幂等性

`apply` 前必须满足：

- 候选决定中不存在未处理或阻断状态；允许存在已记录、已保留的 `borderline-kept`。
- 每个迁移候选都有分类、完整字段、稳定 ID、音频来源和审核结论。
- `source-app-mapping.json` 必须绑定当前 `final-dedupe` 的 `ruleVersion` 和记录 checksum；最终排除项的正式 App ID、目标目录和音频路径必须为 `null`，最终保留项的四段映射必须完整。
- 当前正式题库与基线摘要一致；若基线后发生其他修改，必须重新审计，不能覆盖写入。
- 写入差异只能包含批准候选及其必要的目录计数、资源映射和发布元数据。
- 现有卡片的 ID、内容、顺序、音频路径和非目标字段摘要保持不变。

同一输入重复运行 `apply` 必须得到零新增、零修改。若迁移候选为 0，工具只生成审计与验证报告，不修改正式题库、内嵌题库、`releaseVersion` 或线上数据。

## 9. 本地验证

只有发生实际题库写入时，才需要依次验证：

- 新增数等于批准迁移数，三类总数和分类数正确。
- 新增题没有稳定 ID、规范化文本、答题链路或音频映射冲突。
- 所有新增题字段完整，听力答案索引与参考答案一致。
- 新增故事与 App 四个故事子库及本轮其他新增故事的全局重复检查为 0，并且只写入 `story-flight-basic`。
- 正式源和 App 内嵌题库完全同步。
- 原有三类题库内容摘要不变；900 句和 OPI 完全不变。
- 运行本次迁移工具的动态音频与映射校验、`pnpm content:build`、`pnpm content:check:full` 和 `pnpm check`。
- 现有 `pnpm content:audio:verify` 固定了迁移前数量和 ID，只用于确认旧基线，不作为新增题验收器，也不修改其历史规则。
- 重复运行迁移工具不产生新差异。

纯文本和题库资源变化不需要重建 Development Build。若没有批准候选，则只验证审计结果和工作区零题库差异。

## 10. 条件式发布

只有“迁移候选大于 0、本地检查全部通过”时才生成增量发布包；本任务已获得 ECS 上线授权：

- 题库 `releaseVersion` 仅在实际内容变化时递增。
- 发布包使用三库增量 manifest，只列出本轮变化的 `listening`、`radiotelephony`、`storytelling` 和必要新资源；不得直接导入包含五库统一版本的全量构建包。
- 新资源使用新发布版本命名空间下从未使用过的 `publicPath` 和 `objectKey`，不覆盖或复用旧资源键。
- 打包后在本地与 ECS 分别复算题库 JSON、资源 manifest、音频文件和归档 checksum。
- ECS 导入前备份 PostgreSQL，并保留当前发布包和回滚方式。
- 使用现有内容导入流程，不部署或重启 API 代码。
- 导入后检查 `/health/ready`、五套活动题库数量、版本、checksum、ETag/304、代表性新增卡及音频。
- 失败时在事务中删除本次新版本记录并重新激活原三库版本；数据库 dump 作为灾难恢复，不依赖简单重导旧包覆盖新版本。

若最终新增为 0，则不生成新发布版本、不操作 ECS，只以审计报告和收尾文档结束工作流。该分支在执行开始前不能预测；本轮实际最终新增 1409 题，已按阶段日志完成 v5 发布。
