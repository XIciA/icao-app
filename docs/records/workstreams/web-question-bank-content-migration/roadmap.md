# Web 三类题库优化与增量迁移路线图

状态：已确认，已完成

更新时间：2026-07-15

## 1. 执行原则

- 本路线图已确认，连续进入小流程实施，不设置试审暂停点。
- 每个阶段独立完成“实施 → 验证 → 记录 → 确认”，不跨阶段批量写入。
- Web 永远是只读候选源，App 当前正式题库是权威基线。
- 不使用 Whisper、其他 ASR 或外部翻译 API。
- 去重与质量优先于题量；允许出现新增 0 题的结果，但不能在全量审计前预判。
- 只有发生经批准的净新增内容，才更新题库版本和进入 ECS 发布阶段。

## 2. 阶段 0：冻结基线与清点输入

### 目标

建立可重复的 Web/App 基线，防止后续覆盖工作区中的其他修改。

### 工作

- 建立独立迁移工具骨架和工作流输出目录。
- 从 `/Users/zhouyide/Desktop/web题库/` 读取三类 Web 数据、资源清单、App 正式题库及当前内嵌题库。
- 同时读取 `banks/` 的 2251 条记录和 `quarantine/` 的 37 条记录，共 2288 条候选；保留来源区标记但统一按单题审计。
- 保存数量、稳定 ID、分类、目标字段、音频路径和非目标字段摘要。
- 记录当前发布版本和正式源 checksum。
- 保存 Web 全量文件清单、逐文件 checksum、大小和修改时间，后续阶段执行冻结校验。
- 以 225 条为固定检查点，2288 条候选形成 10 个完整检查点和最后 38 条尾批；每个检查点保存规则版本、范围、状态和 checksum。
- 检查源清单、报告与实际 JSON 的数量漂移。

### 产物

- Web 与 App 基线快照。
- 数据结构和资源清点报告。
- 目标文件白名单及非目标文件摘要。

### 验收门槛

- Web 源没有被修改。
- 基线能够识别后续新增、修改和删除的具体字段。
- 正式题库和内嵌题库在开始时一致。

## 3. 阶段 1：全量去重与候选报告

### 目标

为每个 Web 候选生成可解释、可复核的处理状态。

### 工作

- 按 ID、规范化核心文本、答案链路、场景和音频哈希建立对应关系。
- 听力整体比对原文、问题、选项、正确索引和参考答案。
- 听力不按 Stage 机械映射：先按对话/单人陈述判断陆空通话或航空英语，再按模糊时长划分 `10s/20s`。
- 陆空通话整体比对任务文本、标准回答、呼号和指令意图。
- 故事复诵剥离篇号、词数等正文外标签后，与 App 四个故事子库及 Web 候选内部比对故事主体。
- 将候选分为重复、高相似、说明卡、不完整、人工复核和唯一候选。
- 输出每个结论的证据，不用一个相似度分数自动决定迁移。
- 对呼号、数字、跑道后缀、高度、航向、频率和单位执行关键事实保护；中间相似区间保守保留并记录。

### 重点核验

- 740 道正式听力题是否完成答题链路整体比对，34 个问题标签异常是否被正确识别。
- 79 个陆空通话场景、1367 张卡是否按呼号、指令和参考回答完成比对。
- 144 个故事是否在移除篇号和词数等比较噪声后，与 App 全部 296 个现有故事及其他 Web 候选完成全局全文比对。
- 不同 ID、不同录音或不同标点是否被错误当作独立新题。
- `quarantine/` 的 37 条记录是否全部按单题进入迁移候选并保留来源标记。

### 验收门槛

- Web 三类每个候选都有且只有一个状态。
- 未解释的 ID 冲突、资源缺失和分类冲突数量为 0。
- 自动排除项都有可复现的确定性证据。
- `borderline-kept` 清单独立、精简且附具体问题、最相似对象和保留证据。

## 4. 阶段 2：规则化复核与候选冻结

### 目标

消除阻断项，冻结迁移清单；难判但可用的相似候选保守保留，不中断任务。

### 工作

- 按“目录/题号 + 明确问题 + 对比证据”生成最终人工复核清单，不在此阶段暂停等待。
- 对全局高相似故事判断是否具有独立复述价值，并确保不会与任何现有目录或其他新增故事重复。
- 对专名、分类、缺失翻译和疑似资源错配做人工决定。
- 无法证明字段或资源完整的候选暂缓；只是相似度处于中间区间的候选标记 `borderline-kept` 并保留。
- 冻结 `migrate-unique`、`borderline-kept` 清单和排除理由。

### 两种出口

- 若迁移候选为 0：跳过阶段 3–6，直接进入阶段 7 的零变更收口。
- 若迁移候选大于 0：进入阶段 3，且后续只能处理冻结清单中的候选。

### 验收门槛

- 未处理或阻断状态数量为 0；允许最终人工审核清单包含 `borderline-kept`。
- 明确迁移数、保守保留数和排除数之和等于 2288。
- 每道迁移候选均有完整字段、资源和可追溯决定。

## 5. 阶段 3：准备净新增内容

### 目标

把冻结的迁移候选转换为可写入 App 的完整数据，但暂不改正式题库。

### 工作

- 仅对 `migrate-unique` 与 `borderline-kept` 候选执行确定性文本规范。
- 删除 `(14words)`、篇号、词数、来源备注等明确正文外内容。
- 拆分混写的英文和中文字段，不改语义、数字或事实。
- 为缺失翻译的迁移候选补译并执行逐题结构、术语和关键事实复核；不重译已有完整内容，也不在中途等待用户确认。
- 听力按“对话/单人陈述 → 模糊长短”逐题归入四类；陆空通话按呼号/场景归类；所有批准的新故事统一归入“飞行 ICAO → 基础题库”。
- 分配稳定 ID、任务标题和自然排序位置。
- 校验并规划唯一音频资源路径。
- 生成 `Web 源 ID → App 新 ID → 目标目录 → App 音频路径` 完整映射。
- 全部准备与翻译完成后重新执行跨批次、跨目录和 App 全局去重；正式映射必须重新绑定最终去重规则版本和 checksum，最终排除项不得继续占用正式 ID、目录或音频路径。

### 禁止事项

- 不处理已排除候选。
- 不批量重跑历史文本校准规则。
- 不润色、纠正或重写 Web 原文。
- 不使用 ASR 或外部翻译 API。

### 验收门槛

- 每道候选字段完整、分类明确、ID 不冲突、音频可用。
- 听力题四个选项、正确索引和参考答案一致。
- 新增故事与四个现有故事子库及本轮其他新增故事的全局重复检查为 0。
- 所有新增故事的目标 topic 均为 `story-flight-basic`。
- 格式变化前后语义摘要一致，所有实质变化均为 0。
- 待写入新增数等于阶段 2 冻结的迁移数。

## 6. 阶段 4：条件式本地写入与构建

### 目标

以最小差异把冻结的迁移候选写入正式源，并刷新内嵌题库。

### 工作

- 写入三类正式题库的对应 topic，不重排旧卡片。
- 复制迁移候选必需的新音频并更新唯一映射。
- 更新相关分类、题组和题库计数。
- 运行正式内容构建，刷新内嵌题库。
- 只有实际内容发生变化时，才把 `releaseVersion` 从当前版本递增。

### 验收门槛

- 实际新增数严格等于冻结迁移数，没有旧题修改或删除。
- App 三类原有稳定 ID、目标字段、顺序和音频路径摘要保持不变。
- 900 句和 OPI 内容完全不变。
- 正式源与内嵌题库完全同步。
- 第二次运行 `apply` 不产生新差异。

## 7. 阶段 5：本地完整验收与发布包

### 目标

证明新增内容可在现有 App 中自然使用，并形成明确发布文件集。

### 工作

- 运行本次迁移工具的动态音频、映射和源冻结校验；现有硬编码旧基线的 `pnpm content:audio:verify` 不作为迁移后验收器。
- 运行 `pnpm content:build`。
- 运行 `pnpm content:check:full`。
- 运行 `pnpm check`。
- 在现有目录页和学习页抽查三类新增题的标题、分类、文本、答案和音频。
- 从明确变化集生成只包含三类目标题库和必要新资源的增量发布包、独立 checksum 及回滚清单；不得直接导入五库全量构建包。

### 验收门槛

- 所有内容和项目检查通过。
- 新增题无需 UI、API、类型或数据库结构特例。
- 没有已判定的重复或高相似题进入正式数据。
- 发布包文件集与本地已审核差异一致。
- 完成最终 Git diff 与生成文件范围审查；仓库最后一次编辑后刷新并核对共享 `APP_DISPLAY_VERSION`。

## 8. 阶段 6：条件式 ECS 增量发布

### 进入条件

本任务已获得直接上线授权。只有阶段 5 通过且实际新增数大于 0 才进入；新增为 0 时不操作线上环境。

### 工作

- 备份 PostgreSQL，记录备份位置和恢复命令。
- 分别保留三库当前活动版本、发布包和 checksum（迁移前基线：听力 v4、陆空通话 v3、故事复诵 v1），不得用单一“第 4 版”代替三库回滚基线。
- 使用现有内容导入流程导入增量题库，不部署或重启 API 代码。
- 新音频使用发布版本命名空间下未使用过的 `publicPath` 和 `objectKey`，导入前检查无冲突。
- 在本地和 ECS 分别复算题库、资源清单、资源文件和发布归档 checksum。
- 验证 `/health/ready`、五套活动题库数量、目标题库版本、checksum、ETag 和 304。
- 抽查三类代表性新增卡片的完整字段与音频下载。

### 验收门槛

- 线上数量等于本地冻结迁移后的数量。
- 新版本和 checksum 已刷新，缓存行为正常。
- 旧卡片和其他两套题库没有变化。
- 失败时已在事务中删除本次新版本记录并重新激活原三库版本；数据库 dump 保留为灾难恢复手段。

## 9. 阶段 7：收尾与结论归档

### 目标

记录真实结果，确保工作流可复查、可继续、可停止。

### 工作

- 写入阶段日志和收尾报告。
- 汇总候选总数、各排除原因、人工复核数、批准数和实际新增数。
- 固定生成 `reports/migrate-review.json` 与 `reports/migrate-review.md`，写入规则版本、checksum 和全部最终保留 `borderline-kept`；同时覆盖 `duration-borderline`、翻译/事实疑点和 `source-section-incomplete`。
- 记录本地检查、线上检查或零变更分支的证据。
- 记录复用的共享题库、资源映射和内容构建能力，确认没有第二数据源。
- 若新增为 0，明确记录“不迁移是去重后的正确结果”，且题库、版本和 ECS 均未变更。

### 完成标准

- 所有候选都有最终结论和可追溯证据。
- 路线图内没有未关闭阶段或不明线上状态。
- 实际变更严格受已确认需求、技术方案和候选决定约束。
- 最终阶段日志记录共享 `APP_DISPLAY_VERSION`、Git diff 审查和所有本地/线上验收结果。
