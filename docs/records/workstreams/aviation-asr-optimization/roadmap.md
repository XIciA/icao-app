## 1. 路线图目标

建立并执行可重复的 ASR 优化轮次。每轮由真实音频差异驱动，以小范围热词或规范化修改解决一类可泛化问题，并通过累计回归和新随机盲测防止过拟合。

首个活动已完成阶段 0–7：候选数据库、评测基础、五轮开发与盲测、累计回归、生产发布和证据收口均已落地。本路线图继续作为后续活动的执行门槛，而不是未开始计划。

### 首个活动结果

- 候选数据库：239 条；正式和线上热词：`aviation-hotwords:v2`，0 条，已同步。
- 五轮唯一样本：420 条；评测调用：453 次，所有单轮均低于 147 次上限。
- 规范化：`aviation-normalization:v2` → `aviation-normalization:v7`。
- 累计最终精确匹配：145 → 169；WER：17.76% → 15.46%；三个模块 WER 均下降。
- 三批热词候选全部因无效或退化被拒绝，没有为了数量强行加入正式热词。
- 线上已完成真实 ASR、临时音频清理、结果契约、健康检查和回滚证据验证。

## 2. 总体阶段

| 阶段 | 目标 | 核心产出 | 进入下一阶段标准 |
| --- | --- | --- | --- |
| 0 | 建立热词候选数据库 | 四个指定来源的正式候选资产和子集校验 | 候选可追溯、非频率直推，正式热词均为其子集 |
| 1 | 建立当前评测基础 | 空热词模式、版本化缓存、抽样和报告能力 | 能用同一版本稳定复跑并正确区分三类题库 |
| 2 | 冻结首轮开发集和基线 | 30+30+3 清单、基线结果、源数据复核 | 所有有效样本均有完整四层对照 |
| 3 | 逐条分类并形成候选 | 分类清单、问题族、最小热词/规则候选 | 主线程完成逐条复核，候选有正反例和边界 |
| 4 | 定向复听与开发回归 | 候选版本、定向前后报告、缓存回归结果 | 目标问题改善，相关保护样本无不可接受退化 |
| 5 | 新随机盲测 | 10+10+1 未见样本报告 | 无关键实体严重新增错误，整体无明显退化 |
| 6 | 轮次收口与按需发布 | 正式资产、同步状态、必要时的部署证据 | 版本可追溯，仓库与线上状态表达准确 |
| 7 | 后续轮次 | 重复阶段 2–6 | 每轮独立满足收口门槛 |

## 3. 全程硬约束

- 基础模型保持不变，不做微调或模型比较。
- 每轮开发集固定为 900句 30 条、听力 30 条、故事复诵 3 条。
- 盲测样本必须在候选冻结后才运行和查看，不得参与本轮调优。
- Codex 主线程亲自完成所有非完全匹配样本的复核、分类和最终候选判断。
- 子 agent 只能辅助整理、提出分类建议或做只读复核，不能替主线程决定正式资产。
- 可确定的批量读取、抽样、统计、差异、缓存、报告和校验必须优先脚本化；语义分析和规则取舍可以按清晰边界使用子 agent 分析或审查。
- 题库原文只用于评测，不能进入运行时转写输入或答案补全。
- 源数据噪点必须单独记录，不得为了贴合错误原文修改公共规则。
- 不建立第二套题库、音频索引、热词资产或规范化器。
- 热词候选数据库不直接进入 ASR；高频不等于候选，更不等于正式热词。
- 每个正式热词必须存在于候选数据库；差异中新发现的词必须在同一次变更中先补候选库。
- 开发者总览必须区分“仅候选、仓库已选、线上已部署”，并明确仓库与线上是否同步。
- 热词候选通过前不得覆盖生产热词资源。
- 修改仓库后更新 `APP_DISPLAY_VERSION`；服务端或正式热词上线按 ECS 部署规则验收。
- 低风险轮次常规控制在约 92–104 次 ASR 调用；高风险或发布轮次用完整第二遍开发集替代定向复听，单轮硬上限 147 次，预计超出时暂停。
- 候选引入新的错误数字、字母、呼号、跑道、航向、频率或应答机编码时禁止发布。

## 4. 阶段 0：建立热词候选数据库

### 目标

在首轮 ASR 优化之前，根据四个指定题库字段建立机器可读、版本化、经过领域审核的热词候选数据库。

### 主要工作

- 只读取 900句 `audioText`、陆空通话 `referenceText`、OPI `referenceText`、故事复诵 `audioText`。
- 用确定性脚本完成字段校验、文本归一化、候选提取、统计、去重、来源追踪和稳定排序。
- 输出原始候选统计和排除统计，记录各来源有效文本数量及缺失字段数量。
- 按民航领域性、基础 ASR 预计识别难度、语义重要性、跨场景复用价值、普通英语歧义和来源可靠性审核候选。
- 批量工作优先使用脚本；大批候选可拆给多个子 agent 分析或交叉审查，主线程统一标准、抽查边界项并最终合并。
- 建立正式候选数据库的格式、版本、重复、来源、类别和理由校验。
- 扩展正式热词校验，强制 `asr-hotwords.json` 的每个词条都是候选数据库中的唯一规范项。
- 用脚本合并候选数据库、仓库正式热词和最近一次已验证线上清单，生成按类别展示的开发者总览，明确候选总数、仓库已选数、线上已部署数和每个候选的三态状态。
- 校验开发者总览与输入资产一致且没有过期；仓库选择和线上部署状态不得人工猜测。
- 明确排除仅因高频出现的通用英语；以 `have` 等词作为负向验收样例。

### 产出

- `docs/resources/ai/assets/asr-hotword-candidates.json` 正式候选数据库。
- `docs/resources/ai/assets/asr-hotword-inventory.md` 开发者总览，显示全部候选、仓库已选状态、线上已部署状态及同步状态。
- 可重复运行的候选生成与校验命令。
- 原始统计、排除统计和审核摘要；临时大批量输出放在被忽略的生成目录。
- 正式热词属于候选数据库子集的自动检查。
- 开发者总览的确定性生成命令和新鲜度检查。

### 允许修改

- `docs/resources/ai/assets/` 中的候选数据库和维护说明
- `tools/asr-hotwords.mjs` 或职责清晰的候选处理脚本
- 对应命令配置、测试、阶段记录和展示版本

### 禁止范围

- 不把脚本提取结果未经审核直接写入正式候选数据库。
- 不把全部高频词、全部题库文本或完整原文复制进候选数据库。
- 不因候选入库而把它自动加入正式热词。
- 不读取指定字段之外的选项、中文、题目提示或其他答案字段。
- 不运行 ASR、不修改规范化规则、不创建供应商热词资源。

### 验收

- 四个来源的读取范围和非空数量可对账，OPI 缺失参考答案被明确排除。
- 相同输入和规则重复生成相同统计与正式候选结果。
- 正式候选均有来源、统计、代表样本和收录理由，且不存在大小写重复。
- 开发者打开总览即可看到候选总数、仓库已选数、线上已部署数、同步状态、全部候选及每项状态，不需要手工对比资产。
- 总览中的仓库状态与 `asr-hotwords.json` 一致，线上状态与最近一次部署后验证清单一致；输入变化后未重新生成总览会被检查拒绝。
- 抽查确认高频通用英语没有仅因频率进入候选库，低频高价值民航词不会仅因低频被自动拒绝。
- 空的正式热词 v2 通过子集检查；后续任意库外正式热词会被自动拒绝。
- `pnpm ai:asr:assets:check`、相关脚本测试和 `pnpm check` 通过。

## 5. 阶段 1：评测基础与空热词模式

### 目标

让当前 Fun-ASR 能够以“无热词 + 当前规范化”生成可信基线，并让所有结果绑定完整版本身份。

### 主要工作

- 扩展现有评测思路以支持 900句、听力、故事复诵。
- 复用共享题库和音频索引，建立带随机种子的无放回样本清单。
- 建立模型、热词摘要、规范化版本、音频摘要和原文摘要共同组成的缓存身份。
- 支持明确不提交热词资源的评测模式。
- 为候选热词准备与生产隔离的评测资源边界。
- 建立逐条分类、源数据审查、开发集、累计回归和盲测报告格式。
- 故事复诵按整篇、句段和关键实体分别报告。

### 允许修改

- 当前工作流文档和专属评测证据目录
- ASR 评测脚本及测试
- 热词资产校验与评测资源工具
- Fun-ASR 适配器中支持无热词评测所需的最小边界
- 对应配置示例和测试
- `src/config/app-version.ts`

### 禁止范围

- 不修改规范化规则效果。
- 不恢复或新增正式热词。
- 不覆盖生产热词表。
- 不运行首轮正式样本调优。

### 验收

- 空热词模式不会发送伪造词条或旧热词资源。
- 同一样本和完整版本身份可稳定复跑；版本变化不会误用旧缓存。
- 三类题库均可抽样，重复、缺音频和缺原文会被校验拒绝。
- 报告能区分原始识别、最终文本、源数据问题和规则变化。
- 相关单元测试、API 检查、`pnpm check:audio` 和 `pnpm check` 通过。

## 6. 阶段 2：冻结首轮开发集与基线

### 目标

使用空热词版本、当前模型和当前规范化规则建立首轮 30+30+3 开发基线。

### 主要工作

- 记录随机种子并冻结本轮样本清单。
- 分批运行 ASR，保留可续跑缓存和失败记录。
- 为每条样本生成音频、参考原文、原始识别和最终文本的四层对照。
- 先检查音频与原文是否基本对应，标记明显错配、合理变体、无语音和不确定样本。
- 生成按题库拆分的初始指标和差异清单。

### 允许修改

- 本轮样本清单、缓存、分类和报告
- 评测工具的阻塞性修复及测试
- 阶段记录和展示版本

### 禁止范围

- 不修改热词和规范化规则。
- 不查看或运行本轮盲测样本。
- 不因结果差而替换有效样本。

### 验收

- 900句 30 条、听力 30 条、故事复诵 3 条全部有稳定结果或明确失败分类。
- 源数据噪点没有被计为规则缺陷。
- 基线版本和每条证据可追溯、可重复生成。

## 7. 阶段 3：逐条分析与候选设计

### 目标

由 Codex 主线程逐条判断差异，识别值得公共化的问题族，并提出最小候选改动。

### 主要工作

- 检查所有非完全匹配样本，必要时结合音频复核参考文本。
- 使用统一分类标记领域 ASR、普通 ASR、规范化缺失、规范化退化、源数据噪点、输入问题和不确定问题。
- 将具有共同原因的差异聚合为问题族，说明共性、触发上下文和禁止边界。
- 热词问题优先查询正式候选数据库；库内已有候选可直接进入验证，库外新词必须同步补充候选记录、来源和理由。
- 为热词候选准备相似普通英语保护样本和候选前后原始识别对照。
- 为规则候选准备独立正例、相邻结构正例、反例和幂等性测试。
- 对单次偶发或无法解释的问题只记录，不强行形成改动。

### Agent 分工

- 可使用一个专门子 agent 对冻结差异做只读初步分类并列出疑点。
- 主线程必须逐条复核子 agent 输出、亲自决定问题类型、抽象范围和候选去留。
- 子 agent 不修改正式热词、规范化器或版本。

### 允许修改

- 分类记录、候选清单和测试草案
- 阶段记录和展示版本

### 禁止范围

- 不在分类完成前批量加词或加规则。
- 不从题库全文自动补充正式热词。
- 不把普通英语错误包装成民航规则。
- 不修改题库原文。

### 验收

- 每个有效差异都有且只有一个主分类，并带简短依据。
- 每个候选可追溯到具体样本，并写清适用模式和反例边界。
- 主线程明确批准进入实现的最小候选集合。

## 8. 阶段 4：小范围优化与定向复听

### 目标

实现已批准的最小候选，使用与候选相关的定向样本证明热词作用，使用缓存完成规范化开发回归，避免默认完整复听第二遍开发集。

### 主要工作

- 为每批热词候选组成定向复听集：全部目标错例、候选相关样本、相似发音普通英语反例和已有相关保护样本。
- 热词候选在隔离评测资源中验证，只重新调用定向复听集；普通小批候选预计约 8–20 条，不设脱离风险的机械数量。
- 规范化候选只修改现有唯一规则入口，并补齐正例、反例和幂等性测试。
- 分别报告热词对原始识别的影响、规范化对最终文本的影响和两者组合结果。
- 规范化变更在本轮全部开发缓存和累计缓存上回归，不重新调用 ASR。
- 只有短词、同音词、高权重、多词多类别、已出现退化或准备生产发布时，才完整重新识别开发集和累计 ASR 回归集；此时完整第二遍开发集替代定向复听，避免重复调用。
- 删除无效候选，收紧造成误改的候选；证据不足时撤销而不是扩大规则。
- 候选稳定后冻结待盲测版本。

### 允许修改

- 正式热词候选资产及校验
- 热词候选数据库中由本轮差异产生的必要增量
- 现有规范化器及其专属测试
- 评测证据、阶段记录和展示版本
- 候选评测资源，不含生产资源

### 禁止范围

- 不修改基础模型、录音链路或用户结果契约。
- 不使用大模型改写最终文本。
- 不为了单个样本加入题目专用答案映射。
- 不在候选冻结后继续查看盲测并调参。

### 验收

- 目标问题得到改善或候选被明确撤销。
- 没有新增民航关键实体严重错误。
- 没有新增错误数字、字母、呼号、跑道、航向、频率或应答机编码；出现任一项即阻止候选发布。
- 定向普通英语反例、既有规范化测试和适用的缓存回归通过。
- 热词与规则影响可以分别归因。

## 9. 阶段 5：新随机盲测

### 目标

用本轮未参与调优的新样本检查改进能否泛化。

### 主要工作

- 冻结候选版本后，随机抽取 900句 10 条、听力 10 条、故事复诵 1 条。
- 使用候选热词和候选规范化运行一次完整盲测。
- 主线程逐条复核所有非完全匹配和所有候选造成变化的样本。
- 报告按模块指标、关键实体错误、改善、退化、源数据问题和不确定项。

### 允许修改

- 盲测清单、结果、分类和阶段记录
- 仅用于修复评测工具阻塞的最小改动

### 禁止范围

- 不针对已经暴露的盲测样本继续修改候选。
- 不替换有效但表现不佳的盲测样本。
- 不把源数据噪点计为候选收益或退化。

### 验收

- 盲测没有出现候选引入的关键实体严重退化。
- 各模块整体无明显退化；任何退化都有逐条判断和处置结论。
- 若验收失败，撤销或收紧候选并回到开发阶段，下一次验收使用新的未见样本。
- 通过后的盲测样本从下一轮开始进入累计回归集。

## 10. 阶段 6：轮次收口与按需正式发布

### 目标

把通过定向复听、开发回归和盲测的候选固化为仓库版本，明确它是否仍是内部候选或已经完成生产发布。多个低风险内部轮次可以在生产里程碑前累计，但不得把未部署版本标为线上实际使用。

### 主要工作

- 只保留已证明有效的热词和规范化规则，提升各自版本。
- 验证正式热词仍是候选数据库子集；本轮新增候选的来源、差异证据和收录理由完整。
- 记录仓库选择状态、候选评测状态、线上部署状态和三者是否同步。
- 内部轮次只收口资产和证据，不要求立即覆盖生产资源。
- 准备正式发布时，先完整重新识别开发集和累计 ASR 回归集；通过后再审查待部署文件集。
- 正式发布时同步供应商热词资源；如无正式热词，按已确认的无热词生产边界处理。
- 按项目规则部署相关 API 变更到 ECS，保留回滚镜像和源码备份，重启容器并验证 `/health/ready`、代表性真实请求、实际版本和临时音频清理。
- 写入轮次记录：样本、分类、改动、开发结果、盲测结果、上线状态和遗留问题。

### 允许修改

- 已验收的仓库热词和规范化规则
- 同步、部署、验证和收口记录
- 受保护的生产配置，不写入仓库
- 为上线阻塞所需的最小修复及测试
- 展示版本

### 禁止范围

- 不发布未通过盲测和发布前完整回归的候选。
- 不部署无关脏工作区变更。
- 不在生产配置、日志或文档中暴露密钥、热词表 ID、签名地址、完整用户音频或敏感转写。
- 不在收口阶段追加未经开发集和盲测验证的新规则。

### 验收

- 仓库版本与开发、定向复听和盲测证据完全对应。
- 未发布轮次明确标记为内部版本；发布轮次具有完整开发集和累计 ASR 回归证据。
- 如本轮正式发布，ECS 健康检查和代表性线上转写通过，实际使用版本可追溯。
- `pnpm ai:asr:assets:check`、相关 API 测试、`pnpm check:audio`、`pnpm check` 和部署检查具有新鲜证据。
- 轮次遗留问题和下一轮候选方向已记录。

## 11. 阶段 7：后续轮次循环

下一轮重新执行阶段 2–6：抽取新的 30+30+3 开发集，使用上轮已验收的仓库版本建立基线，逐条分类、小范围优化，再使用新的 10+10+1 盲测。阶段 0 建立的候选数据库持续维护，不重复从零生成；阶段 1 的评测基础只在能力缺失或版本规则改变时调整。

每轮都可以得出“没有足够证据修改资产”的结论。衡量成功的标准是正确归因、稳定泛化和不退化，而不是热词或规则数量持续增加。

首个活动已经授权并完成五轮连续循环。后续新活动仍逐轮执行阶段 2–6；是否连续运行更多轮次由新活动的目标、成本和遗留问题优先级决定。

## 12. 暂停条件

出现以下情况时暂停小流程并回到大流程：

- 需要更换模型、修改用户体验或扩大到完整 900 句评测；
- 现有热词或规范化扩展点无法解决主要问题；
- 批量调用成本、供应商限制或生产风险明显超出方案；
- 需要修改题库原文、音频或内容发布版本；
- 盲测持续证明小样本改动无法泛化；
- 需要新的账号、权限、付费资源或不可逆生产操作。

## 13. 后续活动启动条件

重新进入阶段 2 前必须满足：

- 明确新活动轮数、调用预算和是否包含生产发布；
- 保持每轮开发集 30+30+3、盲测 10+10+1，且不复用前 420 条样本；
- 继续只用四个指定文本来源维护候选库，并保持正式热词是其子集；
- 从当前线上 `aviation-hotwords:v2` 和 `aviation-normalization:v7` 建立新基线；
- 先审阅本次遗留项，不把 ASDA、MSA、EICAS、wind-shear 等单轮发现自动升级为公共资产；
- 不存在与总战略、架构决策或其他并行改动的未解决冲突。
