# 历史归档：App 原生双端与 Web 手机形态在线版需求文档

状态：已确认

更新时间：2026-07-18

工作目录：`docs/records/workstreams/app-web-online-edition/`

## 1. 问题登记

当前产品以 iOS、Android 原生手机 App 为正式形态，尚未提供可直接通过浏览器访问、并与 App 保持一致的正式 Web 在线版。

本 workstream 要新增 Web 在线使用入口，但不把产品改造成传统桌面网站。Web 在电脑浏览器中仍以手机 App 的尺寸、视觉、导航和交互形态呈现，让用户获得与原生 App 几乎相同的使用效果。

本任务不同于已完成的 `rn-web-mobile-parity`：旧任务以历史 Web 设计稿为基线复刻 RN App；本任务以现有原生 App 为产品主体，新增与其同步演进的正式 Web 在线版。

## 2. 目标

- iOS 与 Android 继续交付原生手机 App，不因 Web 版而降级为网页壳。
- 新增可通过浏览器直接访问的 Web 在线版，用户无需安装 App 即可使用现有 App 的全部用户页面和功能。
- Web 不采用传统桌面站布局；手机浏览器和电脑浏览器均以同一个固定手机画布展示。
- Web 手机画布内的页面、内容、视觉、导航、交互和状态结果与 App 几乎一致。
- 后续产品功能默认同时考虑 iOS、Android、Web，平台例外必须明确记录，不让三端无序分叉。

## 3. 产品形态要求

### R1：原生 App 保持不变

- iOS、Android 继续作为独立安装、独立发布的原生 App。
- Web 在线版不得替代原生 App，也不得改变 App 已确认的导航、页面结构和设备体验。

### R2：Web 是正式在线版

- Web 是用户可直接使用的产品入口，不只是设计预览、截图工具或演示页面。
- Web 应承载纳入范围的真实页面、流程、内容和用户可见状态。
- Web 与 App 使用同一套产品定义；相同功能在三端应保持相同的名称、规则、内容结构和操作结果。

### R3：所有浏览器统一使用固定手机画布

- 用户通过手机浏览器或电脑浏览器打开 Web 时，均展示同一个固定手机内容画布，以 **375 × 812** 作为主要视觉基准。
- 手机浏览器与电脑浏览器使用相同的页面结构、尺寸关系和纵向布局，不因设备或浏览器类型切换成另一套界面。
- 当浏览器可用区域不足以完整容纳基准画布时，允许整体适配可用区域，但不得改变画布内部布局、信息层级或导航结构。
- 内容画布不因电脑屏幕变宽而改成桌面多栏、横向导航或大面积拉伸布局。
- 画布之外可以展示中性背景、品牌标识和手机外壳；这些只属于 Web 展示层，不属于 App 内容，也不得影响画布内布局。
- 页面较长时，应在手机画布内保持与 App 一致的滚动、固定顶部栏、底部导航和底部操作区关系。

### R4：接近 App 的视觉与交互

在相同数据、前置状态和操作步骤下，Web 手机画布内应与 App 保持：

- 相同的页面结构、信息层级、文案、图标、图片和品牌风格；
- 相同的字体角色、颜色、间距、圆角、边框、阴影和主要动效节奏；
- 相同的导航入口、返回关系、Tab、弹层、表单、滚动和学习操作；
- 相同的默认、选中、按压、禁用、加载、空、失败、播放、录音和完成状态；
- 相同的核心业务规则、流程结果和后续路径。

“几乎相同”允许浏览器与原生系统在权限弹窗、键盘、状态栏、手势、音频限制等系统级表现上存在差异，但不得无说明地改变产品内容、核心操作或结果。

### R5：平台差异必须可理解

- 浏览器能够提供等价能力时，Web 应完成同一用户流程。
- 浏览器因系统限制无法完全等价时，应给出明确提示、可用替代路径或降级状态，不得出现无响应、假成功或流程中断。
- 平台差异应被视为明确例外，不得演变成独立的 Web 产品流程和视觉体系。

## 4. 范围

### 4.1 纳入范围

- Web 在线版的正式访问入口，以及手机和电脑浏览器统一的固定手机画布形态。
- 现有 App 面向用户开放的全部页面、主导航、弹层、功能和学习流程。
- 页面所需的题库、内容、音频、图片、交互状态及错误反馈。
- 与 App 对照的视觉、交互和流程验收。
- 后续新增功能的三端一致性要求和平台例外管理。

全部页面和功能均属于首版最终范围；后续路线图可以分阶段实现和验收，但不得以阶段拆分为由缩减最终范围。

### 4.2 明确不做

- 不把 Web 设计成独立的桌面版产品、管理后台或多栏门户。
- 不为 Web 另建一套品牌、导航、页面结构或业务规则。
- 不用 Web 在线版替换 iOS、Android 原生 App。
- 不要求浏览器权限弹窗、系统键盘、状态栏和原生设备行为达到像素级一致。
- 本需求不新增或扩大账号、云同步、完整 AI、支付、会员、下载和完整离线学习范围；这些能力仍按各自已确认的 workstream 推进。
- 本需求阶段不决定代码复用方式、框架、依赖、文件结构、部署方案或平台适配实现；这些属于后续技术方案。

## 5. 验收效果

需求最终实现后，应满足：

1. iOS、Android 仍为可独立安装和发布的原生 App。
2. 用户通过正式 Web 地址可进入在线版，并使用现有 App 面向用户开放的全部页面和功能。
3. 在手机浏览器和电脑浏览器中，Web 均以同一个固定手机画布呈现，不出现平台专属布局、桌面化重排或横向拉伸。
4. 对照相同页面、数据和操作轨迹，Web 画布内与 App 不存在明显的内容、布局、导航、交互和状态结果差异。
5. 音频、录音、权限等浏览器差异有明确、可操作的处理结果，不出现无提示失败。
6. 三端共享同一产品规则；所有平台例外均有原因、用户效果和验收结论。
7. Web 的加入不破坏 App 现有页面、核心学习链路和原生设备能力。

## 6. 已确认的需求决策

1. 首版最终范围覆盖现有 App 面向用户开放的全部页面和功能。
2. 手机浏览器和电脑浏览器打开 Web 时采用相同效果，统一展示固定手机画布。
3. Web 画布外展示手机外壳，外部背景使用纯色；外壳和背景不属于 App 内容，不得影响固定画布内的三端一致性。
4. Web 页面、数据、业务流程、前台音频和录音体验与 App 基本一致；浏览器权限弹窗、系统键盘、后台播放、锁屏控制、浏览器返回和刷新等系统行为不要求与原生完全一致。
5. Web 采用同一 Expo / React Native 主工程，不创建第二套页面工程。
6. Web 支持目标仍包含 iPhone Safari、Android Chrome、电脑 Chrome/Safari/Edge 的近期版本；本 workstream 按用户后续决定只用电脑 Chrome 执行浏览器专项验收，暂不把其余浏览器写成已实测通过。
7. Web 登录允许长期保持，同时必须提供明确的当前设备退出和既有账号退出能力。
8. Web 完成验收并正式发布后允许公众直接访问，不要求先做封闭访问。
9. 正式域名确定为 `feizhuicao.com`。该域名当前已有其他内容，正式切换时应完整替换为本 Web 在线版；切换前必须备份旧站并保留可恢复回滚点，不得在新 Web 尚未通过验收时提前清空线上内容。
10. 隐私政策中关于浏览器存储、Cookie 和麦克风权限的补充暂不纳入当前方案讨论范围；公开发布前仍需执行一次合规检查，不在本文中预先承诺无需调整。
11. 实际验收中出现已声明的平台系统差异时，可以先按平台例外记录；若差异影响核心产品体验或用户不接受，再回到大流程决定替代方案。
12. 首版 Web 复用当前 Vercel 项目与域名，不把主站迁移到 ECS；正式切换前保留旧部署回滚点。
13. 暂不配置正式 SMTP，也不要求找回密码、换绑邮箱等依赖真实邮件投递的功能在 Web 首版可用；相关入口必须明确显示未开放或不可用，不得假成功。
14. 暂不做 Android 真机、模拟器或 Android Chrome 体验测试；Android 仍保留为产品支持平台，共享代码和音频敏感改动按工程规则保留必要的自动检查与构建门禁，但本 workstream 不声明 Android 体验已验收。
