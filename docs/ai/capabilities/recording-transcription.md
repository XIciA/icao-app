# 录音转写

## 目标

录音转写只做一件事：

```text
用户语音 → 展示给用户的文本
```

最终文本应忠实表达用户说出的内容，并正确呈现民航语音中的数字、字母、缩写、呼号和固定表达。

## 输入与输出

```text
输入：用户录制的语音
输出：展示给用户的最终文本
```

产品结果只需要：

```json
{
  "transcript": "展示给用户的最终文本"
}
```

模型原始结果、模型参数、热词、资产版本、脚本处理和性能数据都属于内部优化过程，不作为用户结果的一部分。

## 结果要求

- 忠实转写用户实际说出的内容。
- 正确保留民航关键内容：高度层、跑道、航向、频率、应答机编码、QNH/QFE、呼号、字母和缩写。
- 可以整理已经明确的民航格式，例如将 `flight level one eight zero` 展示为 `FL180`。
- 不得补写用户没有说出的内容。
- 不得在转写阶段做语法纠错、表达润色、评分或生成标准答案。

## 当前实现

当前线上工作流固定为：

```text
App multipart 音频
→ 服务端私有临时存储
→ fun-asr-2025-11-07 + aviation-hotwords:v2（无热词）
→ 供应商原始文本
→ aviation-normalization:v7
→ transcript
```

- App 继续使用原有 `/v1/ai/transcribe`，不直接调用供应商。
- 临时音频使用短期签名地址，请求结束立即回收，并有残留对象兜底清理。
- ASR 热词的唯一运行时来源是 `docs/ai/assets/asr-hotwords.json`。
- 数字和 ICAO 字母不依靠整表热词替换，而由 `aviation-transcript-normalization.ts` 在明确民航上下文中规范化。
- 供应商原文、任务状态和内部版本不进入用户结果契约。

实现与维护记录见 [`aviation-asr-optimization/closeout.md`](../../workstreams/aviation-asr-optimization/closeout.md)，五轮证据见 [`evidence/campaign-01/README.md`](../../workstreams/aviation-asr-optimization/evidence/campaign-01/README.md)。

## 后续性能验收资产：900句

900句的音频与文本已经完成校准，是 ASR 性能优化的主要验收资产，不是基础工作流是否接通的完成门槛。首个活动已从中无放回抽取 200 条开发/盲测样本，未运行完整 900 句。

```text
输入：900句音频
标准答案：对应的 audioText
验收：最终文本尽可能与 audioText 一致
```

验收时：

- 单词内容应一致。
- 民航关键内容必须完全一致。
- 大小写、纯空白和句末标点差异可以单独记录，不作为首要识别错误。
- 漏词、多词、错词，以及数字、字母、缩写识别错误，均视为转写错误。

后续活动继续划分开发集和冻结盲测集；开发集用于调优，盲测集只用于本轮验收，避免针对测试答案过度优化。

## 优化方向

不把目标放在重新解决“普通英语识别”上。应先选择英语识别能力足够强的基础 ASR，再集中处理民航领域识别和规范写法。

```text
用户语音
→ 基础 ASR 识别英语
→ 民航领域适配
→ 民航规范写法
→ 最终文本
```

民航领域适配可以使用：热词、上下文、领域词表、模型微调或其他模型能力。数字读音、字母读音和高频词等资产用于帮助模型识别民航内容。

民航规范写法可以使用保守的非 AI 脚本，例如将已经明确识别出的高度层、跑道、频率和 QNH 整理为统一文本格式。

## 后续优化顺序

1. 冻结 900 句评测清单并划分开发集和盲测集。
2. 以当前 Fun-ASR、热词和规范化版本建立基线。
3. 分别迭代热词资产和确定性规范化规则，并记录版本。
4. 使用同一冻结样本验证最终文本是否提升且没有回退。
5. 只有现有扩展点无法解决明显领域错误时，才重新评估模型、部署或微调方向。

不预设必须继续使用当前模型、当前 API 或当前后处理方案。唯一判断标准是：最终文本是否更接近 900句的 `audioText`。

## 禁止方式

- 不使用通用大模型在 ASR 后自由润色或猜测文本。
- 不为了让结果“更像标准答案”而补写用户没有说出的词、数值、呼号或程序内容。
- 不把语法纠错、表达润色、评分混入转写流程。
