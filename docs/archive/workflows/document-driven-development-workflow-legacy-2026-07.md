# 历史归档：通用大流程——文档管理式开发

> 本版本已于 2026-07-30 被精简大流程替代，仅用于追溯。

## 极简速览

```text
问题登记
-> requirements.md：做什么 / 不做什么 / 验收效果
-> technical-plan.md：怎么做 / 取舍 / 风险
-> technical-audit.md：真实现状 / 缺口 / 证据
-> roadmap.md：阶段顺序 / 每阶段验收
-> 用户确认路线
-> 交给小流程自动执行
-> phase-log.md / closeout.md
```

一句话：**大流程负责决策，小流程负责执行。**

## 适用范围

适用于中大型任务，例如跨模块功能、架构改造、数据整理、上线准备、工具建设、多人或多 agent 接力任务。

不适用于小 bug、小文案、小样式、单文件小改；这些直接按项目常规开发处理。

## 核心原则

1. 先判断任务是否需要大流程。
2. 需求、方案、路线必须由人确认。
3. 确认后的执行默认交给小流程自动推进。
4. 执行阶段不反复确认已写清楚的事项。
5. 执行越界、路线失效或风险扩大时，暂停回到决策层。
6. 文档只记录决策、边界、方案、验证和风险，不写流水账。
7. 文档保持短而准，同一原则只写一次。
8. 特别是需求文档一定保持语言精炼，只讲核心，相同观点不要反复论述。

## 人与 Codex 分工

人负责：

- 提出和确认真实需求。
- 确认需求文档、技术方案、技术盘点和路线图。
- 仅在范围、成本、风险或战略变化时重新做宏观决策。

Codex 负责：

- 把聊天中的想法分流到正确文档。
- 基于真实项目状态做方案、盘点和路线图。
- 技术方案优先选择便于 Codex 稳定实现、验证、维护和后续扩展的路线。
- 四份大流程文档确认后，按小流程持续完成代码实现、验证、问题修复和阶段收口，不要求用户逐步接管。

## 标准文档组

推荐目录：

```text
docs/workstreams/<workstream-name>/
  requirements.md
  technical-plan.md
  technical-audit.md
  roadmap.md
  phase-log.md
  closeout.md
```

复杂任务尽量使用稳定路径，方便后续 agent 读取。任务很小时可以只写一个 `task.md`。

## 文档分工

### requirements.md

只回答：**做什么、做到什么效果、不做什么。**

必须包含：

- 目标
- 范围
- 模块要求
- 明确不做
- 验收效果

要求：

- 第一版只写最核心、最明确的需求。
- 不写技术路线、脚本目录、字段设计、执行阶段或排期。
- Codex 可以提出补充建议，但必须等人确认后再写入。

当需求要求按既有产品“1:1 复刻”时，必须写明对照基线；1:1 指用户可见的 UI、交互、状态和内容结构一致，不指复制源代码。具体采用何种原生实现，留给技术方案决定。

### technical-plan.md

只回答：**怎么做、为什么这样做、为什么不选其它方案。**

必须包含：

- 推荐方案
- 可选方案和不采用原因
- 关键技术、脚本、模块或数据处理方式
- 关键取舍、风险、成本和可迁移性

要求：

- 承接已确认需求，不重新扩写需求。
- 不写阶段排期，阶段顺序留给路线图。

### technical-audit.md

只回答：**真实项目现状是什么，离目标还有哪些缺口。**

必须来自只读检查，不能凭印象写。

可包含：

- 相关路径、数据、脚本、JSON、资源引用
- 已有能力和可复用部分
- 缺口、风险、不能破坏的旧行为
- 验证方式和回滚点

简单任务可以省略深度盘点，但不能省略需求确认和方案确认。

### roadmap.md

只回答：**按什么顺序做，每阶段怎样验收。**

必须包含阶段总览：

```text
阶段 | 目标 | 核心产出 | 进入下一阶段标准
```

每个阶段应包含：

- 阶段目标
- 主要工作
- 阶段产出
- 允许修改范围
- 禁止范围
- 验收标准
- 暂不做
- 验证命令或检查方式

路线图确认后，才能进入小流程。

### phase-log.md

只服务 Codex 接续执行，不写过程流水。

只记录：

- 当前阶段
- 完成了什么
- 关键文件
- 验证结果
- 剩余风险
- 是否能进入下一阶段

### closeout.md

任务结束时写：

- 完成了什么
- 验证结果
- 未做事项
- 剩余风险
- 后续建议

## 新增要求分流

用户在决策或执行中提出新要求时，先判断属于哪一层：

- “做什么 / 不做什么 / 验收效果” -> `requirements.md`
- “怎么实现 / 是否用 API / 脚本方式 / 技术取舍” -> `technical-plan.md`
- “真实项目现状 / 已有能力 / 缺口 / 风险证据” -> `technical-audit.md`
- “先后顺序 / 阶段目标 / 阶段验收” -> `roadmap.md`

如果新要求影响已确认决策，必须暂停并说明要回到哪个决策层。

## 批量外部劳动规则

涉及大批量模型劳动、外部 API 或子 agent 重复处理时，方案文档必须写清：

- 主线程是否允许直接调用外部 API。
- 输入输出的严格结构。
- 分批大小、缓存位置、失败重跑方式。
- 抽检节奏和暂停条件。
- 哪些字段由主线程最终校验后写入正式数据。

原则：先用本地确定性脚本解决能确定的问题，再让模型或子 agent 做重复劳动。

## 大流程步骤

### 0. 问题登记

先记录问题本身：

- 要解决什么问题
- 已知背景或现象
- 目标结果
- 禁止范围
- 是否涉及数据、账号、权限、支付、部署或删除

### 1. 需求文档

生成 `requirements.md`，等待用户确认。

### 2. 轻量预盘点

方案前做小范围只读检查，避免方案脱离真实项目。

检查项目类型、相关模块、已有实现、明显风险和验证命令。不要大规模读全仓库。

### 3. 技术方案

生成 `technical-plan.md`，给出推荐方案、可选方案、不采用方案和关键取舍，等待用户确认。

### 4. 技术盘点

任务复杂、跨模块、涉及数据或存在未知风险时，生成 `technical-audit.md`。

盘点必须聚焦当前方案，不做泛泛扫描。

### 5. 技术路线图

生成 `roadmap.md`，把需求、方案、盘点转成阶段路线，等待用户确认。

### 6. 进入小流程

路线确认后，大流程不再逐步讨论“下一步做什么”。Codex 按小流程自动执行：

```text
读取文档 -> 定位阶段 -> 规划切片 -> 执行 -> 审查 -> 验证 -> 记录 -> 下一阶段
```

## 暂停条件

执行中遇到以下情况，暂停小流程并回到大流程：

- 需求和现有实现冲突。
- 需要改变已确认的用户体验。
- 需要删除、迁移、合并或覆盖重要数据。
- 需要新增生产依赖。
- 需要账号、权限、支付、部署或第三方平台选择。
- 需要密钥、私有凭证或外部付费资源。
- 外部 API 调用范围、成本或风险扩大。
- 实现成本明显高于原方案。
- 验证失败且修复会扩大范围。
- 发现用户或其他 agent 正在改同一区域。
- 路线图缺少必要阶段或阶段顺序不合理。
- 需求、方案、盘点和路线图互相矛盾。

## 质量控制门

| 控制门 | 确认者 | 目的 |
| --- | --- | --- |
| 需求门 | 人 | 确认做什么和不做什么 |
| 方案门 | 人 | 确认实现路线 |
| 路线门 | 人 | 确认阶段顺序和验收标准 |
| 执行门 | Codex | 按路线自动执行 |
| 验证门 | Codex | 确认命令、数据、页面或输出通过 |
| 变更门 | 人 | 范围、成本、风险变化时重新确认 |

## Token 节约规则

1. 用文档传递上下文，不复制完整聊天记录。
2. 只读当前阶段相关文件。
3. 不让 agent 输出长篇过程，只要结论、证据和风险。
4. 大批量处理必须脚本化。
5. 文档按职责拆分，不混成一个长文档。
6. 每份文档只保留能指导决策或执行的内容。

## 理想完成效果

一个合格的大流程应做到：

- 需求能独立说明目标、范围、边界和验收。
- 方案能独立说明技术路线和关键取舍。
- 盘点能说明真实项目现状和缺口。
- 路线图能让后续 agent 直接进入小流程。
- 人不需要在执行阶段反复确认已写进文档的事项。
