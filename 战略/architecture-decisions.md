# App 架构决策记录

## 技术选择总原则

- 技术方案首先要方便 Codex 持续完成开发、验证、维护和问题修复。用户负责提出需求、确认范围与最终效果，不需要掌握或决定过细的技术实现。
- 技术决策以能够稳定实现最终产品效果为核心标准，同时兼顾开发效率、运行成本、可靠性和后续演进空间。
- 本文只固定会影响项目长期方向、系统边界或产生较大返工风险的宏观选择，不提前锁死具体库、版本、目录结构、数据表细节、同步算法或代码实现方式。
- 在不违背已确定技术方向和职责边界的前提下，Codex 可以根据实际兼容性、构建与测试结果、维护成本和最终效果，自主选择或调整具体实现方案。
- 各阶段可以暂不实现后续能力，但当前实现不得与最终技术方向冲突；对后续账号、云同步、AI、商业化等能力，应保留清晰、可替换的接入边界。
- 如果实现过程中需要改变本文已经确定的宏观技术方向，应记录改变原因、收益、代价和迁移影响，并交由用户确认。

## 项目背景与决策原则

- 当前阶段：MVP。
- 主要用户：中国大陆用户。
- 预估规模：首阶段约 300 DAU。
- 开发团队：1–2 人。
- AI 方式：调用外部模型 API，不在 ECS 上运行模型。
- 当前资源特点：以音频为主，初始资源总量不到 1 GB。
- 决策原则：在产品效果、开发效率、运行成本和后续演进空间之间取得平衡。

## 一、移动客户端

### 客户端技术（ADR-005）

- 状态：已决定。
- 决策：移动客户端使用 React Native，前端代码使用 TypeScript。

### 原生工程工作流（ADR-011）

- 状态：已决定。
- 决策：采用 Expo + Development Build + Continuous Native Generation（CNG/Prebuild），不以 Expo Go 作为生产开发环境。
- 原生能力：允许使用第三方原生库、Config Plugin 和自定义原生模块；录音优先使用 `expo-audio`。微信、Apple 登录、支付、推送等能力在选型后进入自定义 Development Build。
- 构建方式：EAS Build/Update 是可选服务；也可以使用本地 Xcode/Android Studio、`npx expo run` 或自有 CI 构建，避免必须依赖 Expo 云服务。
- 退出条件：只有在项目出现大量需要长期手工维护的原生工程改动、核心 SDK 无法稳定通过 Config Plugin/CNG 集成，或需要深度定制原生启动及构建链时，才转为维护 `ios/`、`android/` 的 Bare React Native 工作流。

### 支持平台（ADR-013）

- 状态：已决定。
- 决策：产品必须支持 iOS 和 Android；两端共用 React Native + Expo + TypeScript 主代码库。
- 尚未决定：双端是否同日首发、首发审核顺序，以及 Android 首批上架哪些中国大陆应用市场。

## 二、认证与客户端会话

### 认证系统（ADR-006）

- 状态：已决定。
- 决策：使用自托管 Supabase Auth；不引入 Better Auth，不自建认证，MVP 不接入其他第三方身份服务平台。

### 登录方式与会话管理（ADR-007）

- 状态：部分已决定。
- 已决定：MVP 支持 Supabase Auth 匿名游客登录；游客拥有独立用户 ID 和受限业务能力。
- 尚未决定：是否在 MVP 同时提供手机号短信、公开邮箱、微信或 Apple 登录；游客数据如何绑定、升级或合并到正式账号。
- 开发与审核测试：保留邮箱密码测试账号。
- 当前建议：公开 MVP 可增加手机号短信 OTP；微信和 Apple 登录延后共同评估。如果 iOS 主账号采用微信等第三方社交登录，应同步评估符合 App Store 规则的 Apple 登录选项。
- RN 会话：使用 iOS Keychain/Android Keystore 封装的安全存储保存会话；开启自动刷新；支持当前设备退出、全部设备退出和退出其他设备。MVP 暂不提供逐台设备列表与单设备远程撤销。

### 学习数据同步效果（ADR-014）

- 状态：已决定。
- 决策：用户登录后，App 自动恢复该账号的学习进度、标注和笔记，并支持同一账号跨设备恢复。
- 同步体验：正常联网时自动同步，不要求用户手动操作；同步失败时提供明确提示并自动重试，尽量避免学习数据丢失。
- 当前边界：暂不承诺断网状态下继续学习，不建设完整的离线学习和复杂双向离线冲突系统。
- 本地保存：客户端仍可使用必要的轻量本地持久化，防止 App 退出、网络波动或同步暂时失败造成数据丢失；该能力不等同于正式离线学习功能。
- 实施弹性：具体本地存储、同步协议、重试机制和冲突处理方式由 Codex 在实现阶段根据可靠性、复杂度和最终效果确定。

## 三、业务后端

### 后端语言及职责（ADR-008）

- 状态：已决定。
- 决策：MVP 线上后端统一使用 TypeScript；Python、Go、Rust/C++ 暂不进入线上运行环境。
- TypeScript 职责：产品 API、业务编排、外部模型 API 调用、Prompt 组装、Few-shot 选择、输出校验、流式响应、模型路由和用量统计。
- 演进边界：仅在出现自部署模型、训练评测、Python 专属 ML/音频库或重型离线处理时考虑 Python；仅在压测证明某个独立服务存在无法经济解决的性能瓶颈时考虑 Go 或 Rust/C++。

### 后端框架与服务形态（ADR-010）

- 状态：暂定，可在实现阶段调整。
- 当前默认：NestJS，HTTP Provider 使用 Fastify Adapter。
- 服务形态：优先采用模块化单体，即单一代码库和单一部署单元；按 Auth 集成、用户、题库、练习、录音、AI Gateway、额度等业务模块划分边界。
- 实施授权：后续交由 Codex 开发时，不把 NestJS + Fastify 作为不可变约束。Codex 可根据实际依赖兼容性、流式响应实现、代码复杂度、维护成本、测试结果和最终效果，调整为纯 Fastify、其他 NestJS HTTP Adapter 或更合适的 TypeScript 后端方案。
- 调整约束：仍须遵守 TypeScript 主语言、Supabase 技术边界和单 ECS 的 MVP 范围；如果改变框架或服务形态，应记录变更理由、收益、代价和迁移影响。

## 四、数据库与数据访问

### 主数据库（ADR-002）

- 状态：已决定。
- 决策：使用自托管 Supabase 内置的 PostgreSQL（Supabase Postgres），不引入 MySQL。
- 说明：Supabase Postgres 不是第三种数据库，而是由 Supabase 的集成和管理方式增强的 PostgreSQL；Auth、RLS、PostgREST、Realtime 和 Storage 元数据均围绕 PostgreSQL 工作。

### 数据库与 Supabase SDK 的访问边界（ADR-012）

- 状态：已决定。
- 业务数据库：NestJS 后端的业务数据访问和事务使用 Drizzle ORM。
- Supabase 能力：React Native 和服务端涉及 Auth、Storage 及必要平台管理能力时，继续使用 Supabase SDK。
- 职责边界：Drizzle 负责业务表查询、写入、关联和多步骤事务；Supabase SDK 不作为 NestJS 复杂业务数据访问的主要工具。
- 数据库变更：以版本化 SQL Migration 作为唯一生产变更路径。业务表可由 Drizzle Schema/Drizzle Kit 生成 SQL；RLS、Policy、Trigger、Function 和 Supabase 特有能力使用补充 SQL Migration。
- 禁止事项：不只在生产 Supabase Studio 中手工改表；不在生产环境直接执行未经审查的 schema push。
- 实施弹性：PostgreSQL 驱动、连接池参数和 Drizzle 的具体稳定版本，由 Codex 在实现阶段依据自托管 Supabase、Node.js 和部署环境兼容性确定并锁定。如需更换 ORM 或 Query Builder，应记录理由和迁移影响。

## 五、文件与对象存储

### 文件存储方案（ADR-004）

- 状态：已决定。
- 决策：MVP 使用自托管 Supabase Storage；后续根据流量、稳定性和商业化需求考虑迁移到阿里云 OSS。
- 数据分工：权威题库及其结构化字段导入 Supabase Postgres；题库原始 JSON 作为导入源归档；题目音频、图片和用户录音存入 Supabase Storage。
- 元数据：Postgres 只保存 object key、归属、类型、大小、状态等文件元数据，不存储文件本体。
- 私有文件：用户录音使用私有 Bucket，通过 Supabase Auth 与 Storage RLS 控制上传和访问；删除文件时同步更新业务数据库状态。
- 迁移约束：业务表不保存带域名的永久完整 URL，只保存稳定的 object key；文件操作通过项目自有的 `ObjectStorage` 接口封装，避免业务代码直接绑定 Supabase Storage SDK。

### 客户端资源使用效果（ADR-015）

- 状态：已决定。
- 决策：题库、音频和图片以联网访问为主要方式，暂不提供题库下载、音频包下载或离线资源管理功能。
- 缓存边界：允许客户端使用必要缓存提升加载速度和减少重复请求，但缓存不作为正式离线能力或产品承诺。
- 失败处理：网络不可用、资源缺失或加载失败时，App 应提供明确状态、失败提示和重试入口，不得无提示卡死或崩溃。
- 实施弹性：具体资源版本标识、缓存机制、失效策略和加载实现由 Codex 在开发阶段根据资源规模、稳定性和最终体验确定。

## 六、缓存与后台任务

### Redis（ADR-003）

- 状态：已决定。
- 决策：MVP 不部署 Redis。
- 首个可能引入场景：出现必须脱离 HTTP 请求、可以重试且不能因进程重启而丢失的 AI 或音频后台任务时，将 Redis 作为任务队列 Broker。
- 暂不引入条件：如果仍是单实例和短时流式 AI 请求，则继续不使用 Redis。

## 七、部署与基础设施

### Supabase 部署位置（ADR-001）

- 状态：已决定。
- 决策：Supabase 自托管到阿里云中国大陆 ECS。
- 直接影响：核心数据库与认证数据保留在中国大陆；ICP备案、HTTPS、安全加固、备份恢复、监控和 Supabase 升级由项目方负责。

### MVP 部署拓扑（ADR-009）

- 状态：已决定。
- 决策：MVP 的应用后端、Supabase 必要组件和当前后台任务部署在同一台阿里云中国大陆 ECS，通过 Docker 容器或独立进程隔离；外部 AI 模型运行在供应商侧。
- 演进条件：只有出现明确的资源争用、GPU/CPU 专用算力、独立扩容或可靠性要求时，才将相应服务迁出该 ECS。

## 八、尚需由人决定的事项

以下内容会影响产品、商业、合规或账号权益，不能只由实现阶段的 Codex 自行决定：

1. MVP 的完整产品功能范围和上线验收标准。
2. 除游客登录外，MVP 是否加入手机号、微信、Apple 或公开邮箱登录；游客升级后的数据和权益合并规则。
3. iOS 与 Android 是否同日发布；Android 首发应用市场范围。
4. 产品目标年龄范围，以及是否涉及未成年人。
5. 哪些用户文本、音频或个人数据可以发送给外部 AI；数据处理地区、保存期限、模型训练授权和用户同意方式。
6. AI 输出质量标准、单用户额度、延迟目标和成本预算。
7. 用户录音、业务数据和账号注销后的保留与删除规则。
8. 商业模式、付费能力、订阅或购买后的权益规则。
9. 云资源、AI、短信等服务预算，以及可接受的停机时间和数据丢失风险。
10. 题库、音频、图片等内容的版权来源和 AI 内容安全规则。
11. 上线主体、域名与 App 名称、开发者账号、Bundle ID/Package Name 和证书归属。
12. 数据分析范围、隐私政策要求和用户支持渠道。
